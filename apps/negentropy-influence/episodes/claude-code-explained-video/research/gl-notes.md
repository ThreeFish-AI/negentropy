# 精读：Learn Claude Code「工具与执行」

> [1] shareAI-lab, "Learn Claude Code," GitHub 仓库，s01_agent_loop / s02_tool_use / s03_permission / s04_hooks 四章。所据版本双轨钉点：站点轨 fix 分支 `67a9126c`（2026-07-29，README.md 中文默认，站点 learn.shareai.run 实况与该钉点 2026-10-07 逐章对账一致）与 main 轨 `ce8f9f18`（upstream/main，2026-09-28，README.md 英文默认 / README.zh.md 中文）。访问日期 2026-10-07。两轨在循环判据上有实质差异，本文以站点轨为组织骨架、main 轨作对照并逐处注明。

**一句话定位**：把会说话的模型变成会动手的 Agent，全部秘密是一个把工具结果喂回模型的循环；Tool Use 让它的手更多，Permission 在动手前设闸门，Hooks 把闸门和一切扩展逻辑挂到循环的固定挂点上，而循环本体四章一路没有改过一行。

**SCQA 导读**。共识背景是：大模型早已能写出正确的命令行，你让它「列一下目录、跑一下脚本」，它给你一段可以复制粘贴的命令。痛点是：输出完了它就停了，不会自己跑，也看不到结果，更不会基于结果走下一步；你手动执行、把输出贴回对话框，下一个命令出来你再跑一遍，每一个来回你都在当人肉中间层。就算把「执行」自动化了，还有第二个问题跟着来：一个真能删文件、真能改系统的程序，凭什么敢让它跑？本文回答的问题就是这一对：模型如何获得在真实机器上动手的能力，靠什么装置保证它敢用且不出事。课程用四章给出答案：s01 Agent Loop 造出「执行-回喂-再调用」的回路（§3），s02 Tool Use 把单一 bash 换成查表分发的专用工具（§4），s03 Permission 在执行前插入三道闸门（§5），s04 Hooks 把检查与扩展逻辑移出循环、挂上固定事件（§6）；§7 给关键数字，§8 是配套原型与五次破坏性实验，§9–§10 收拢规律与争议，§11 划适用边界。原型代码在 `docs/research/agent-harness/assets/lcc_tooling_lab.py`，纯标准库可直接运行。

> [!TIP]
> **白话主线**：模型一次调用给完回答就结束，内部没有「做事、看结果、再思考」的回路，所以需要一个外部程序替它跑腿：执行它要的工具、把结果作为新消息塞回对话、再调它一次，直到它的回答里不再带工具调用。难的从来不是这个循环本身（约 30 行），而是往它上面长东西的方式：加工具用查表、加安全用闸门、加扩展用钩子，核心循环一行不动。验证靠三层对照：每章一个可独立运行的教学实现、材料作者对 Claude Code 生产源码的核查、以及官方文档的独立口径。

## 1. 它要解决什么问题

s01 的开场白把这个痛点写得极准：你问模型「帮我读取下我的目录下有哪些文件，并且执行 XXX.py」，它能输出一条命令，然后就没有然后了。自动化这个来回，得到的不是「更快的问答」，而是一个能在真实环境里连续行动的程序——这同时意味着它获得了搞破坏的能力。所以这四章真正要满足的是一份四项规格，缺一项整个方案就不成立：

| 规格 | 通俗版 | 对应机制 |
|---|---|---|
| 持续 | 模型一停就续、一呼就应，回路永不断 | s01 主循环：两信号判据 + tool_result 回喂 |
| 可扩展 | 手（工具）越多越好加，加东西不动老东西 | s02 工具分发：TOOLS 定义 + TOOL_HANDLERS 查表 |
| 可拦截 | 动作落地之前有人（或规则）点头 | s03 权限：硬拒绝 → 规则 → 用户审批三道闸门 |
| 可插入 | 日志、审计、自动化之类的扩展有地方挂 | s04 钩子：事件注册表，循环只喊号不干活 |

读这四章的正确姿势是盯着这条主线：每一章都对上一章的循环「只动一个点」。s02 把循环里写死的 `run_bash()` 换成 `TOOL_HANDLERS[block.name]` 查表；s03 在执行前插一行 `check_permission(block)`；s04 把这一行再换成 `trigger_hooks("PreToolUse", block)`，检查逻辑降格为注册表里的普通回调。三次演进，循环骨架不变。材料每章开头都标了一行「Harness 层」（循环、工具分发、权限、hook），Harness 指的就是模型外圈这层运行装置：模型负责决策，装置负责执行与守门。

前置概念三个，第一次用到时讲清。其一，「调一次模型 = 发一串消息、收一段回答」：对话不是连续的意识流，而是一次次独立调用，每次调用之间什么都不发生，除非程序自己把上次的结果放进下次的输入。其二，命令行（shell / bash）：用文字命令操作电脑的方式，列目录、读写文件、跑程序都靠它。其三，JSON：一张自描述的结构化数据表（字段名加值），程序之间用它交换工具定义与执行结果。

## 3. Agent Loop：主循环——模型获得手的唯一通路

### 3.1 会写命令的模型没有腿

模型能写出一条正确的命令，这件事和「会做事」之间隔着一条沟。命令只是文本；把它变成动作，需要有人按下回车，看到输出，再决定下一步。s01 之前这个人是用户自己：跑一遍、贴回去、再跑一遍。麻烦倒在其次，真正的问题是这个回路里模型只贡献了「下一步做什么」的判断，执行与观察全靠人。把它自动化，就是给模型装上腿：程序替它执行、替它观察、替它把观察结果递回它眼前。

### 3.2 机制解构：三十行循环与两个信号

教学实现（站点轨 s01 code.py）的全部逻辑是五个步骤的循环。第一步，用户的问题作为第一条消息进入 `messages` 列表。第二步，程序带着 `messages` 和工具定义（`tools=TOOLS`）调用模型。第三步，模型的回答原样追加为 assistant 消息，然后查一个信号：回答里有没有工具调用。第四步，对每个工具调用块执行 `run_bash(block.input["command"])`，把输出包成 `tool_result`（携带该调用的 `tool_use_id`）。第五步，这些结果作为新的 user 消息追加回 `messages`，回到第二步。判断只有两个出口：有工具调用就继续转，没有就 `return` 退出。

这里有一条容易看漏的结构约定：工具结果是以 user 角色回塞的。对话里 assistant 说「我要调工具」，紧接着一条 user 消息说「这是你要的结果」——角色名看着别扭，机制上说得通（推断：对模型而言，凡不是自己产出的内容都属于输入）。官方 API 语义同口径：模型以 `stop_reason: "tool_use"` 结束并返回一个或多个 tool_use 块，你的代码执行操作后以 tool_result 回传 [2]。

### 3.3 单步走查：一条「改文件」请求的完整往返

给一个具体输入走全程。用户输入：「帮我在清单里加一行牛奶，然后把清单念给我听」。此刻 `messages` 只有一条 user 消息。程序第一次调用模型，模型回答里带一个 tool_use 块（写文件，参数是清单路径和新内容），`messages` 变成两条：user 提问 + assistant 的调用请求。程序执行写入，磁盘上的清单多了一行，`messages` 追加第三条（user 角色的 tool_result：「已写入 N 字节」）。程序第二次调用模型，模型这次回答里又带一个 tool_use 块（读文件），于是再执行、再回喂，`messages` 长到五条。第三次调用，模型回答纯文本「清单现在是……」，没有工具调用块，循环退出。整个会话三次调用、两次执行，模型每一次决策都建立在程序喂回的结果上。

### 3.4 判据之争与生产版差异：认内容块，不认收尾字段

判据怎么选，两轨给出了不同答案，这是本篇最值得停下来看的一处分歧。站点轨教学版查 API 响应的收尾字段：`stop_reason == "tool_use"` 就继续。概念上干净，但有个隐患：流式场景下回答像打字机一样逐字到达，收尾字段可能比内容晚更新——程序已经看到工具调用块时，字段还停在上一个值。等字段再决定，就等于把行动绑在一个可能迟到的信号上。火警接警的比方到这里为止：接警员听到「着火、地址」就派车，不等这通报警电话说完的官方收尾；CC 同理，用 `needsFollowUp` 标志，流式过程中只要检测到 tool_use 块就置真、循环照跑，收尾字段另作他用（材料引 CC 源码注释：stop_reason 在流式下不可靠）。失配边界：接警员听完还能补派，循环对同一次响应没有补判语义。main 轨已经把教学代码也改成内容块判据（先筛出 `tool_calls` 列表、为空才退出；对应提交 `168fff8`「Fix empty tool-use response handling」，本仓 git 实测），与生产实现对齐；副作用是顺手消灭了一个教学版边界情况——为空的工具结果消息不会被追加。

生产版的其余差异都是「往这个核心上叠保护」（材料对 `src/query.ts` 1729 行的核查）：教学版只维护一个 `messages`，CC 的 State 对象有十个字段，各自追踪一类运行状态（压缩追踪、token 恢复计数、停止钩子状态、轮次计数等），材料的总结是「所有复杂字段和退出路径都是保护机制」；教学版一条退出路径，CC 有阻塞上限、提示超长、模型报错、中止、钩子停机、轮次上限、token 预算续跑、响应式压缩重试等多条路径。**三十行的骨架就是 1729 行的核心**，其余全是保险丝。

### 3.5 原型实景

本篇原型（`lcc_tooling_lab.py`，模型用确定性脚本替代、文件系统在内存中）跑通了同一条主线，实际运行日志（`--selftest` 基线）：


## 4. Tool Use：工具分发——加一个工具只加两行

### 4.1 用 bash 拼生活

只有 bash 一个工具时，模型想的是「读这个文件」，说出来的却必须是 `cat path/to/file`；想写文件得拼 `echo "..." > file.py`，想改文件得动用 `sed`。s02 点破了这个损耗：模型在自己的意图和 shell 语法之间做了一层翻译，浪费 token，还容易拼错。更深一层，bash 是个万能但无形状的口子，程序侧没法对「读」和「写」区别对待——所有命令都是字符串。给每个动作一个有名字、有参数结构的专用工具，模型直接说意图，程序侧也第一次拿到了「这个调用想干什么」的结构化信息。

### 4.2 机制解构：定义与注册，查表分发

加一个工具只需要两处：`TOOLS` 数组加一条 JSON 定义（名字、描述、参数 schema——schema 就是参数的格式说明书，写明每个参数叫什么、什么类型，告诉模型「我能做什么、参数长什么样」），`TOOL_HANDLERS` 字典加一行映射（名字到实现函数）。循环里的执行从硬编码的 `run_bash()` 变成一行查表：`handler = TOOL_HANDLERS[block.name]; output = handler(**block.input)`。教学版从 1 个工具长到 5 个（bash、read_file、write_file、edit_file、glob），循环零改动。文件类工具同时获得了 `safe_path` 校验：路径解析后必须落在工作目录内，越界直接报错——安全边界第一次有了结构化的着力点。

### 4.3 多工具调用与 tool_use_id 配对

模型经常一次返回多个工具调用：「读一下 a.py 和 b.py，然后列出所有 .py 文件」。API 允许这样，每个 tool_use 块自带唯一编号，执行侧把每个结果包成携带对应编号的 tool_result 回喂。编号配对像快递并发派送：一次下多个订单，每个包裹贴单号，先到后到乱了序，签收时凭单号对回订单；失配边界是快递单号跨天有效、还有物流状态可查，而这里的编号只活一轮对话、结果是一次性回执。教学版按返回顺序逐个执行；配对的意义在乱序与并发场景下才显形——§8 实验 2 把配对拆掉，两个结果当场错绑。

### 4.4 生产版：连续批并发、五步验证与结果落盘

材料对 CC 源码的核查补齐了三个生产细节。其一，并发不是「只读都能并发」这么粗：`isConcurrencySafe(input)` 按具体输入判定，`ls` 可并发、`rm` 不可，TaskCreate（任务创建工具，课程 s12 讲）改状态却因为每次写不同文件而可并发——写操作并发会互相干扰（两个写抢同一份东西、一读一写交错读到半成品），所以写要隔离出并发批。分区算法 `partitionToolCalls()` 把一串调用按原始顺序切成连续批——`[读 A, 读 B, glob, bash "rm x", 读 C]` 切成三批，前三个并发、删除单独串行、最后一个再并发，批与批之间严格保序。其二，CC 里每个工具调用过五步验证管线：schema 校验、工具级输入校验、PreToolUse 钩子（可改输入可拦截）、权限检查、执行。其三，每个工具有结果长度上限，超过就落盘、模型看预览加路径；唯独读文件的上限是无穷大——否则读文件的结果被落盘成新文件，下次再读那个文件又触发落盘，无限循环。

## 5. Permission：三道闸门——动手之前的裁决

### 5.1 rm -rf / 与「信任模型」的破产

s02 结束时的 Agent 已经能读写文件、跑任意命令，而 bash 完全没有保护。s03 的开场判断成了整门课的安全观，原话是「安全不能靠信任模型，要靠代码——在工具执行之前做判断」。官方文档同口径说得更直白：权限规则由 Claude Code 执行，不由模型执行；提示词或 CLAUDE.md 里写什么，影响的是模型会尝试做什么，改变不了程序允许什么 [4]。这句话划清了一条信任边界：模型在边界内决策，边界本身由边界外的代码持有。

### 5.2 机制解构：硬拒绝、规则匹配、用户审批

三道闸门串在工具执行之前，顺序固定。闸门 1 是硬拒绝表（`DENY_LIST`，教学版 7 条字符串：rm -rf /、sudo、shutdown、reboot、mkfs、dd if=、重定向裸设备——裸设备指整块磁盘这类最底层的设备文件，重定向写入就是绕过文件系统直接写盘），命中即拦，不问任何人。闸门 2 是规则匹配（`PERMISSION_RULES`，每条规则指定作用工具加检查条件：文件类工具路径越界，bash 命令含删除文件、向系统配置目录写入、放开全盘权限一类的关键词，教学版列的是 rm、> /etc/、chmod 777 三种），命中的操作交给闸门 3。闸门 3 是用户审批：打印原因，停下来等一个 y 或 n。三道都没命中的直接执行——大部分日常操作走这条直通路，这个设计的隐含目标是「打扰密度最低化」：默认快、例外问、极少数零商量。还有一个容易被问到的细节：s02 给文件工具的 safe_path 硬界在 s03 的教学代码里没有保留，越界读写改由闸门 2/3 裁决，用户批准后即放行——教学版把「界」完全交给了权限层。教学版自己给闸门 1 挂了免责声明，原话是「简单字符串匹配不是可靠安全机制，命令变体和 shell 展开可能绕过」。

### 5.3 单步走查：一条删除命令过三关

模型发起 bash 调用，命令是 `rm old-notes.txt`。闸门 1 逐条比对硬拒绝表：不含 rm -rf /、不含 sudo……七条都不命中，放行到下一关。闸门 2 检查 bash 规则：命令含「rm 」关键词，命中「有潜在破坏性的命令」，标记。闸门 3 暂停打印警示，等用户输入；用户敲 y，命令执行，删除结果作为 tool_result 回喂，模型继续；用户敲 n（或其他任何键），该调用拿到「Permission denied.」回喂，模型知道这条路被拒了，通常会换安全的做法。另一个分支：若命令以 sudo 开头，闸门 1 直接拦下，用户根本不会被问——零商量区不打扰人，也不给人犯错误的机会；拦下后同样以拒绝结果回喂模型，它知道这条路走不通。闸门放在执行之前而不是之后，道理只有一条：这些动作不可逆，文件删了就是删了，事后惩罚挡不住既成事实。

### 5.4 生产版：四种裁决、八个来源与自动分类器

CC 的实际裁决比三闸门厚。裁决值有四种（allow / deny / ask / passthrough，最后一种是「工具不表态、交给通用管线（由一串固定处理步骤组成的常规裁决流程）」）；验证分布在多个阶段（schema 校验、输入校验、PreToolUse 钩子、钩子与管线的裁决协调、多层规则检查）；规则不止一张表，而是八个来源（用户设置、项目设置、本地设置、特性开关、企业策略、命令行参数、内联命令、会话内授权），高优先级覆盖低优先级。`isDestructive` 标记纯属界面展示、不参与裁决，这是材料专门澄清的一个易误解点。auto 模式下审批还能再自动化：先看「接受编辑」模式（自动放行工作区内的文件改动）是否已允许，再查安全白名单，最后把工具调用连同对话上下文交给一个分类器（专门判断安不安全的小模型）判断，连续拒绝太多次就回退人工 [1][4]——教学版的「问用户」在生产里被拆成了一台分级判案机器。官方文档当前列出六种权限模式（default、acceptEdits、plan、auto、dontAsk、bypassPermissions），并对 bypassPermissions 写明只应在容器或虚拟机这类隔离环境使用（截至 2026-10-07）[4]。

## 6. Hooks：钩子注册表——扩展不进循环

### 6.1 每加一个检查，循环烂一分

s03 的权限检查是直接写在循环体里的。假设此后要加「每次执行前记日志」「某些操作后自动 git add」，每项都改一次 `agent_loop` 函数，很快循环就成了材料里展示的那副样子：log、check、notify、auto_git-add 一行行往里堆，「很快循环就认不出来了」。病灶不在任何一行代码，而在依赖方向：你想扩展的是行为，改动的却是核心流程。

### 6.2 机制解构：四个事件，一个注册表

Hooks 的解法是墙面插座式的：回路（循环本体）和一排插座（固定事件）装修时就位，之后添什么电器（回调函数）插上就用，不用拆墙布线；失配边界是插座只供电、没有返回值控制流，而钩子的返回值能拦工具、能续循环。注册表就是一个字典，事件名映射到回调列表；循环里只保留 `trigger_hooks(event, ...)` 的喊号，具体跑什么由注册表决定。四个事件覆盖一个完整周期：UserPromptSubmit（输入提交后、进模型前，可注入上下文）、PreToolUse（执行前，可拦截——s03 的三闸门整个降格为挂在这里的普通回调）、PostToolUse（执行后，副作用与输出检查）、Stop（循环即将退出时，收尾统计）。循环从此不含任何具名的检查逻辑。

### 6.3 单步走查：Stop 钩子拦住「做完了」

Stop 事件的语义最反直觉：循环判据已经说「没有工具调用、该退出了」，钩子却还能拦。教学实现是退出前先 `force = trigger_hooks("Stop", messages)`，钩子返回了内容就把这段话作为新 user 消息塞回对话、continue 续跑；返回空才真正退出。效果是模型说「我做完了」，钩子说「还没，这是没做完的理由」。原型实际运行日志（`--t5` 模式，钩子第一次返回核对指令、之后放行）：

```text
[HOOK] Stop: session used 8 tool results
[HOOK] Stop: session used 9 tool results
turns 10/10 · stop_continued 1
注入的新消息条数: 1 · 角色: user
```

第一次停机被拦、注入一条 user 消息、多跑一轮核对，第二次放行退出；全程没动循环一行代码。

### 6.4 生产版：事件全表、结果字段与两条防循环保险

教学版 4 个事件，材料对 CC 源码的核查数出 27 个（工具、会话、用户交互、子 Agent、压缩、团队等类别），官方文档截至 2026-10-07 已列 33 个（新增用户命令展开、并行批完成、消息展示、目录添加、模型切换前后等 6 个）[3]——事件清单单调增长，四个核心事件始终是理解骨架。钩子结果在生产里是一个 14 字段的对象：阻塞错误会注入对话让模型自纠、`updatedInput` 能在执行前改写工具参数、`permissionBehavior` 直接表达权限裁决。两条保险最见功力。其一，不变式（无论走哪条路都不许违反的规则）：**钩子说 allow，也压不过设置里的 deny / ask 规则**，官方文档原文是「Deny and ask rules are still evaluated regardless of what the hook returns」[3]——允许需要各方一致，拒绝只要一方摇头，任何一个来源（包括用户自己写的钩子）都不能单方面放行被禁的操作。其二，stopHookActive：Stop 钩子阻塞错误会让循环带标志重入，后续迭代看到标志就不再触发，防止「模型自纠、钩子再报错、模型再自纠」的永不停机循环。PostToolUse 还有优雅停机通道：返回阻止续跑的标志时循环平静退出，是完成而非崩溃。

## 9. 底层规律与核心争议

### 9.1 底层规律

**规律 1：核心循环不变，能力正交叠加**（正交指各维独立变化、互不牵连）。能力清单可以一直加长，主循环从第一课到最后一课一行不改；每个新能力都是在固定挂点上加东西（工具加查表行、权限插一道门、钩子注册回调），不是改核心。没有它，每次加功能都改核心，每改一次都可能弄坏既有功能的风险，随功能数线性增长。演示：s02 加 4 工具只改一行、s03 只插一行、s04 检查上钩后循环零硬编码；反面是材料 s04 展示的膨胀循环。[5][6]

**规律 2：安全靠机制，不靠模型自觉**。安全约束写在模型管不到的地方（代码与配置），提示词说什么改变不了执行面。没有它，输入里被夹带恶意指令或一次误解就能变成一次真实破坏。演示：s03 的立场句与官方「Permission rules are enforced by Claude Code, not the model」同口径。[7]

**规律 3：拒绝票比允许票重**。多个来源都点头才放行，任何一个摇头就拦下；钩子的 allow 压不过 deny / ask 规则。没有它，任何一个被攻破的来源都能单方面放行危险操作。演示：不变式的官方原文；§8 实验 3 把这条拆掉的实测后果。[7][8]

**规律 4：协作靠契约与配对回执**。模型与程序只通过「工具定义 + 带编号的调用与结果」沟通，一次多个、乱序返回，编号对号入座。没有配对，并发结果张冠李戴；没有稳定的参数说明书（schema），模型不知道有什么可调。演示：教学代码的 tool_use_id；官方「一个或多个 tool_use 块 + tool_result 回传」。[9]

**规律 5：简洁内核加保护外圈**。生产与教学的差别不在核心而在外圈，复杂性全部以「出事时怎么办」的保护层叠上去，每个保护层都映射回核心的一个判据点（needsFollowUp 对判据、stopHookActive 对 Stop、八个来源对闸门 2）。没有它，复杂度压进核心，核心变成无人敢动的泥球。[10]

五条的分工：规律 1 管生长，规律 2、3 管安全，规律 4 管协作接口，规律 5 管工程形态；合起来是一个「长得大又不出事」的完整答案。

### 9.2 核心争议

**争议 1：该不该拦，规则说了算还是分类器说了算**。规则派要白纸黑字：字符串、正则、来源层级，可审计、零延迟；分类器派要语义判断：命令组合变形无穷，静态匹配永远有绕过的口子，让小模型看上下文才够用。分歧源于两派见过不同的失败模式——被变体绕过的人信分类器，被误放行又问不出理由的人信规则。本质是把安全判定当成能写成明确规则的模式匹配，还是需要理解含义的语义判断；工程上正走向混合（模拟放行、白名单、分类器、连续拒绝回退人工的分级判案），不可消除的是语义判断的可审计性缺口。课程自己在这个谱系上走了三步：字符串表（自认不可靠）→ main 轨换成词边界正则（按词的边界精确匹配文本的规则写法）→ CC 分类器。[1][4]

**争议 2：判据跟规范字段走，还是跟内容事实走**。站点轨用 API 明文定义的收尾字段当判据，一行判断；main 轨与 CC 翻内容找工具调用块，不信派生信号。分歧源于处境：教学版非流式一次性响应，字段总是就绪，字段判据无懈可击；生产版流式逐字到达，字段晚于内容，等字段就丢调用。本质是简洁性与鲁棒性在「规范定义对实况时序」上的选址；可克服（main 轨已改），张力永存——规范说字段存在，实况说字段晚到。[1]

**争议 3：自动放行该走多远**。自动化派说每次都问人，Agent 就退化成要人盯着的工具，auto 让分类器替你审、bypass 干脆跳过提示；审慎派说官方文档白纸黑字警告 bypassPermissions 只该在隔离环境用，「不用问」换来的每一分效率都是风险敞口。分歧源于环境：可回滚的受控环境里放行成本低，不可逆的开放环境里高。本质是权限自动化收益与损失的不对称性；不可消除只能对冲（dontAsk、企业管理开关、分类器回退人工都是对冲件）。[4]

## 11. 适用边界

### 成立条件

定义域：CLI（命令行）编码助手形态的工具执行机制；输入是对话消息与工具调用，输出是工具结果与最终回答；架构假设是单 Agent、单主循环、client 工具（模型发起、本地程序执行）。成立工况：工具结果可文本化回喂；用户在场可审批，或显式选择 auto / bypass 等自动模式；单用户会话。Out-of-Scope：多 Agent 协作与权限冒泡（子助手的审批弹窗转回主助手终端，课程第五部分）；规划、记忆、并发调度（第二至四部分）；沙箱隔离与网络权限（在受限环境里跑命令的官方机制，另有专章）；server tools（运行在 Anthropic 服务器上、客户端不经手的工具）；真实攻防安全的完备性证明。

### 材料没有证明的事

1. 材料附录的全部生产数字（1729 行、27 个事件、14 字段、8 来源、五步管线）来自作者对某时点 CC 源码的核查，未锁定所查 CC 版本号；官方文档 2026-10-07 快照已显示事件清单增至 33 个，说明这类计数随时点漂移。
2. 三闸门与词边界正则的防御力没有任何攻防实测；材料自认字符串匹配可被命令变体与 shell 展开绕过，正则版的绕过面同样未测。
3. auto 模式分类器的准确率、误放行率，材料与官方文档都没有给数字。
4. 连续批并发相对顺序执行的吞吐收益没有实测。
5. 「后面所有章节都叠在这个循环上、循环不变」是课程的结构性主张，材料未提供逐章代码层面的验证。
