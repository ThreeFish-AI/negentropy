## P0 接工具的老办法

> 画面：系列片头装置之后冷启动——画面深处一片工具星海（千千万件外部工具微光），近处一道窄门紧闭；三张「接入申请单」拍上窄门被弹回（单上字样：定义 / 参数格式 / 调用代码）；右下角常驻署源角标（信源名，首部署源位，随画面淡入）

- [p0-01] 这是接工具的老办法：外面的工具千千万，接一个，重写一套。
- [p0-02] 想接个工单系统？手写定义、参数格式、调用代码，一整套。
- [p0-03] 再接部署系统？对不起，再写一套。
- [p0-04] 服务一升级，你还得跟着改。
- [p0-05] 接得越多，写得越多——这条路养不起千千万。

> 画面：窄门上方亮起标准徽记（兰紫）——门框向两侧展开成一条双向通道；「MCP」三字母与全称 Model Context Protocol 以角标浮现

- [p0-06] 好在有一条新路：一个开放标准，把这事切成了两半。
- [p0-07] 它叫 MCP，模型上下文协议。
- [p0-08] 两半怎么分、工具怎么不写代码就进门？今天拆开看。

> 角标：MCP · Model Context Protocol

## P1 两半与三步

> 画面：分工线亮出——（左）外部服务卡（兰紫描边）两个入口：「给工具清单」「执行工具调用」；（右）主程序（深空蓝）四件职责牌：连接、命名、权限、交给模型

- [p1-01] 先看分工：服务只做两件事——报清单，接调用。
- [p1-02] 剩下的连接、命名、权限、交给模型，全归主程序。

> 画面：第一步发现——主程序伸出通道接上部署服务卡；回传一张清单卷轴，卷上两件工具卡（查状态 / 触发部署），件件带名字与说明小字；「教学版计数」口径小条：内置 5 + 连接 1 = 6（不口播）

- [p1-03] 第一步，发现：连上服务，拿回清单，件件带名字和说明。

> 画面：第二步命名——两件外部工具卡挂上前缀牌（前缀字样进角标）；另一服务的 search.user 名字卡上，斜杠与圆点被白名单网格拦下、逐字符翻成下划线，落成全名卡；「>64 拒收」红字小牌

- [p1-04] 第二步，命名：前缀、服务名、工具名，双下划线隔开——拼出来的，就是它的全名。
- [p1-05] 两个服务都有同名的工具？挂牌之后，谁也顶不掉谁。
- [p1-06] 怪字符有规矩：斜杠、圆点这类，白名单外一律换下划线。

> 画面：教学版硬线帧——同名卡清理完仍相撞、弹回「报错」；「>64 拒收」红字小牌独立成帧（承原命名 beat 备注）

- [p1-07] 教学版还画了硬线：名字清理完仍撞名，直接报错；全名超六十四字符，拒收。

> 画面：第三步组装——深空蓝池子每轮重新灌装：内置与外部工具汇进同一个池；池边立一张对照表（左列全名、右列原始名），一次调用沿表翻译

- [p1-08] 第三步，组装：每轮把内置与外部工具，拼成同一个池。
- [p1-09] 模型看全名，执行用原始名，中间靠一张对照表翻译。
- [p1-10] 三步连起来：发现、命名、组装——顺不顺，走一个看看。

## P2 连一个服务，走全程

> 画面：走查舞台——主程序连上部署服务（兰紫通道点亮），清单回传：查状态、触发部署两件工具卡落位挂牌（全名卡 mcp__deploy__check / mcp__deploy__trigger）

- [p2-01] 走个例子：连接部署服务，清单回来，查状态、触发部署两件。
- [p2-02] 挂牌、进池、随池交给模型，一口气走完。

> 画面：模型气泡发出一次调用（全名卡 mcp__deploy__check 升起）——对照表左列命中、滑向右列原始名；执行流（青碧）落进服务卡，回执「web: running」沿原路回流

- [p2-03] 模型开口点名，用的是全名。
- [p2-04] 对照表把全名翻回原始名，递给服务执行。
- [p2-05] 结果原路回喂：网页服务，正在运行。
- [p2-06] 这条链走完，主程序没为它写过一<行|HANG2>接入代码。

> 画面：命名边界帧——另一服务的 search.user 工具卡飞入，斜杠与圆点字符被网格拦下翻成下划线，落成全名卡（实测标记「在案」）

- [p2-07] 斜杠圆点进不了白名单，一律翻成下划线——实测在案。

## P3 池是活的

> 画面：环体〔M-001〕高亮调模型前的一拍——深空蓝池子每轮重新灌装（旧池清空、新池注入）；池沿贴着一张「缓存」标签的快照卡，内容停在旧清单

- [p3-01] 别小看「每轮组装」：工具池是活的，不是一份固定清单。
- [p3-02] 连上新服务，池就变了；依赖清单的东西，得跟着变。
- [p3-03] 最要命的是缓存：它把上一轮的提示词存下来复用，省钱提速——里面存的工具清单，还是旧的。

> 画面：左红右绿消融同屏——左「沿用旧池」：调用 mcp__docs__search 全名卡被池子弹回，回执「Unknown tool」（警示红）；右「重建后」：同一调用落进服务卡，结果正常回流（确认绿）

- [p3-04] 实测说话：连接文档服务，两件新工具，不重建直接调。
- [p3-05] 池子回得冷冰冰：不认识的工具。
- [p3-06] 服务明明连上了——卡住的，是那份旧快照。
- [p3-07] 重建工具池，再调一次：结果正常返回。
- [p3-08] 两条实测，双双坐实：不重建，调不到；重建，立刻恢复。

> 画面：金句卡预亮（衬线体）「池一变，缓存作废」——旧快照卡燃尽动画；旁边浮出另一选项牌「干脆不缓存」

- [p3-09] 也有干脆不缓存的：每轮现拼，一了百了。
- [p3-10] 教训一句话：池是动态的，依赖它的缓存，必须随它失效。

> 角标：prompt cache · Unknown tool: mcp__docs__search · mcp__docs__search / get_version

## P4 通道与权限闸

> 画面：六条传输通道并排点亮（兰紫渐进；通道名进角标）——本地子进程、远程网页协议、开发工具内嵌；本地与远程两批并发连接动画；「认证」徽记与「重连」回路小图

- [p4-01] 真实的 Claude Code 呢？
- [p4-02] 拆解过 Claude Code 源码的同学们应该知道：光是把工具连过来的通道——传输——就有六种。
- [p4-03] 本地起子进程，远程走网页协议，开发工具里也能内嵌，还有进程内直接调用的。
- [p4-04] 本地远程，分批并发；远程有整套认证，断线按类重连。

> 画面：权限闸特写——服务自我介绍卡（「我是只读的」字样）飘向闸门；闸门不看介绍，翻出宿主名单（四条目：三绿一黄）；名单外的工具卡一律弹到「问用户」位

- [p4-05] 更值得记的是权限：服务自称「只读」——这<行|HANG2>字，不算数。
- [p4-06] 授权只认宿主配置：宿主，掌管工具执行的主程序。
- [p4-07] 教学版名单四条：三件只读放行，那件会动手的，就是触发部署，每次都问。
- [p4-08] 名单之外，一律先问用户。

> 画面：官方印证条——权限规则卡（按完整工具名书写）、项目服务批准卡（.mcp.json 角标）、插件工具全名卡（多一段插件名）；三卡同排落位

- [p4-09] 官方同一路数：权限按全名写，项目服务批准了才加载。
- [p4-10] 插件——装进主程序、成包扩展功能的那种——自带的工具也走这条路，全名里多一段插件名。
- [p4-11] 值得记的就一条：外部服务的自我描述，不能当授权依据。

> 角标：stdio / HTTP / SSE / WebSocket / IDE / SDK · OAuth · MCP_HOST_POLICY · readOnlyHint · .mcp.json · mcp__plugin_{plugin}_{server}__{tool}
