## 一、s12 Task System —— 大目标拆成小任务

### 定位与标语
- 【二】标语「大目标拆成小任务，排好序，持久化」；Harness 层「任务——持久化的目标，可恢复的进度」。

### 问题（原文）
> 【一】「它列了清单开始写 API，写到一半发现没数据库表，回头补；加测试时发现接口又变了。
> 盖房子不能先盖屋顶再打地基。」
> 【一】s05 的清单是**会话内存**里的执行清单；这里要的是跨会话、可认领、有依赖的**任务系统**。

### 机制【一】
- **一个任务一个 JSON 文件**（`.tasks/` 目录）：id / subject / status / owner / blockedBy 五字段。
- **依赖成图**：`blockedBy` 声明前置；`can_start` 检查**全部前置 completed** 才放行；
  ★ **不存在的依赖也算被挡**——引用错 ID 不会崩溃，只会挡住（防御性设计）。
- **两个动作三个状态**：pending --认领→ in_progress --完成→ completed；认领时写 owner（防重复认领）；
  完成时扫描看板，报出**刚被解锁**的下游任务。
- 完成即解锁：做完「建表」，「接口」「文档」同时解锁——依赖图自动排序。

### 生产版对照【三】
- 顺序 ID + **高水位文件**防 ID 重用（教学版用时间戳+随机）。
- **认领在文件锁内完成读-改-写**（`utils/tasks.ts:541-612`，`proper-lockfile`）；更严谨的
  「忙检+认领」用任务表级锁做成**原子操作**（614-692）——防「检查时没人、下手时已被抢」的竞态。
- 队友终止时，系统把它未完成的任务**解除归属、状态重置回 pending**，让别人能接手——教学版省略。

## 二、s15 Agent Teams —— 一个搞不定，组队来

### 定位与标语
- 【二】标语「一个搞不定，组队来」；Harness 层「团队——多 Agent 协作，消息总线」。

### 问题（原文）
> 【一】「重构整个后端：认证、数据库、API、测试。修 API 路由时，认证的细节已经不在上下文里了。
> 一个的注意力覆盖不了所有模块。」
> 【一】关键对照：「s06 的子代理是**临时工**，叫来干一件事就走了。有些任务需要能通信、能协作的**队友**。」

### 机制【一】
- **信箱就是文件**：每个成员（领队和队友都算）一个收件文件；发消息 = 往对方文件里**追加一行**；
  读消息 = 读文件 + **删掉**（消费式）。读一条少一条。
- 领队启动队友：队友是自己的线程，有自己的系统提示、自己的对话、精简的工具
  （跑命令/读/写/发消息）；干完把总结发回领队信箱；领队每轮结束收信，注入自己的对话。
- 队友是**多轮**的：不是干一件走人，教学版限十轮；干完活等新消息。

### 生产版对照【三】（★本集深挖点之一）
- 收件路径在用户目录的团队文件夹下；写文件加**文件锁**（最多重试十次）防并发写冲突。
- **十五种结构化消息类型**（普通消息/空闲通知/权限请求与回复/计划审批与回复/关机请求-同意-拒绝/
  任务分派/权限广播/模式修改/沙箱权限/移除通知）——文本消息包在专用的 XML 标签里交付给模型。
- ★ **权限冒泡**：队友遇到要审批的操作 → 发请求到领队信箱 → 领队**每一秒**收一次信，路由到审批队列 →
  你在主屏幕审批（对话框带队友名字和颜色）→ 回复发回队友信箱 → 队友**每半秒**收一次，继续或停。
- 领队收信也是每一秒轮询；队友之间**不许再孵队友**（源码明文禁止）。
- 队友真实形态：跑在终端分屏窗格里，各有颜色，注册在团队配置文件里。

## 三、s16 Team Protocols —— 队友之间要有约定

### 定位与标语
- 【二】标语「队友之间要有约定」；Harness 层「协议——Agent 之间的结构化握手」。

### 问题（原文）
> 【一】「直接杀线程，Alice 写了一半的文件留在磁盘上。需要握手。」
> 【一】两个场景同构：关机（领队→队友）与计划审批（队友→领队）——一方发请求，一方给回复。

### 机制【一】（★本集深挖点之二）
- **同一个编号串起来**：请求带编号出去，回复带同一个编号回来；一张状态表追着记：
  pending → approved / rejected。
- **类型校验**：关机的回复不会误批一份计划——回复类型必须与请求类型配对，编号对不上、
  类型不对、已经处理过的，一律跳过。一次握手，三重对号。
- **四步**：发请求（建记录）→ 对方按消息类型分派 → 回复（带编号）→ 发起方对号销账。
- 队友改为**等待而非退出**：干完活进空闲态，轮询信箱，收到关机请求就收尾退出，收到新消息就接着干。
- 教学版只演了消息流程，**没有**做执行门控（未批准就拦住工具）——README 明示。

### 生产版对照【三】
- 真实关机是**三向**通信：请求 → 同意/拒绝（拒绝可附原因）→ 系统再发「队友已终止」通知各方；
  确认后自动清理窗格、解除任务归属、从团队名册移除。
- 计划审批有两条路径：自动回写 + 交领队作上下文；显式批准时可同时设置队友的权限模式
  （「批准，但按计划模式跑」），回复里还能带反馈让队友改了再交。
- 消息是带校验的结构化 JSON；字段命名在权限/关机/计划三处**不统一**（课程作者如实指出）。

## 四、s17 Autonomous Agents —— 自己看板，自己认领

### 定位与标语
- 【二】标语「自己看板，自己认领」；Harness 层「自治——队友自组织，不依赖领队分配」。

### 问题（原文）
> 【一】「看板上有十个没认领的任务，领队得手动分十次。这不能扩展。」

### 机制【一】
- 队友生命周期三段：**干活 → 歇着 → 走人**。
- 歇着的时候每**五秒**看两样东西（信箱优先，看板其次）：信箱有关机请求立刻收尾退出；
  有新消息回干；看板上有能做的活就**认领**（三查：是待办、没主人、依赖全完成）。
- **六十秒**没等到新活，自动收工：发总结给领队，退出。
- 认领失败不硬来：已有人做、依赖没齐，返回失败原因，不把失败当成功。
- 压缩后**身份重注入**：对话被压得太短时，把自己的名字和职责重新插回去——「我是谁、我该干嘛」。

### 生产版对照【三】
- 真实的空闲机制是**四件套组合**而非单一轮询：空闲通知（干完告诉领队）+ **每半秒**的信箱轮询
  （关机请求优先处理，不会被普通消息饿死）+ 任务**文件监听**（目录一变、一秒防抖后触发检查）
  + 等待期间**主动认领**。
- 产品里**没有固定六十秒**：队友一直活着，领队手动关机（对照表如实给出）。
- 依赖判断语义一致：「没有未完成的前置」而非「没有前置」。

## 五、s18 Worktree Isolation —— 各干各的，互不干扰

### 定位与标语
- 【二】标语「各干各的目录，互不干扰」；Harness 层「隔离——并行执行的目录隔离」。
- 【二】题记：「任务管目标，worktree 管目录，按 ID 绑定。」

### 问题（原文）
> 【一】「Alice 和 Bob 在同一个目录。Alice 改 config.py，Bob 也改 config.py，互相覆盖，
> 而且无法干净回滚——分不清哪些改动是谁的。s15-s17 解决了『谁干什么』『怎么通信』，
> 没解决『在哪干』。」（★递进主线的第四问）

### 机制【一】（★本集深挖点之三）
- **同一仓库，各开一张桌**：每个任务可绑定一个独立工作目录（git worktree），各有各的分支；
  名字只许字母数字点横线（防路径穿越）。
- **绑定不改状态**：领队可以提前建好任务和桌子；任务仍待办，队友认领时才开工——桌子先摆好，
  不耽误看板语义。
- 队友认领带桌子的任务时，自己的跑命令/读/写**全部切到那个目录**下执行。
- ★ **收尾二选一 + 脏桌不删**：任务完成，保留（留分支等人审）或删除；**但目录里还有未提交的
  改动时，删除默认被拒**——必须明说「丢弃改动」才能删。宁可留着，不可悄悄丢工作。
- 每次创建/删除/保留都写一行事件日志（`events.jsonl`）——可审计。

### 生产版对照【三】
- 真实实现是**进程级**的目录切换（`process.chdir()`），子代理用目录覆盖包住执行；
  产品里**任务与目录不强制绑定**（对照表给出）。
- 名字校验同款；`-b` 建分支；删除先查改动数。

  用户输入 → 输入前钩子 → 定时/后台通知注入 → 压缩 → 记忆/技能/外接状态组装垫纸 →
  问模型 → 有工具调用？→ 执行前钩子+权限 → 分发（内置/外接/后台）→ 执行后钩子 →
  结果回填 → 下一轮；没有工具调用 → 停机钩子 → 返回。

## 十、站点可视化文字规格（供 Remotion 重建）

1. **Task DAG（s12）**：任务卡+依赖箭头的有向图；完成时下游卡解锁闪光；「不存在的依赖」
   虚线卡带「算被挡」标记。
2. **Team Topology（s15）**：领队环 + N 个队友小环；各自信箱文件；消息行飞入文件、读取即划掉。
3. **Permission Bubble（s15）**：队友的审批卡沿虚线上浮到领队屏幕，用户点头后回执下落。
4. **Protocol FSM（s16）**：请求卡带编号出发 → 状态表 pending 行亮起 → 回执带同号归来对号销账；
   类型校验：一张错类型的回执被弹开。
5. **Idle Loop（s17）**：队友三段生命周期环（干活/歇着/走人）；歇着态 5s 心跳；60s 表盘走满收工。
6. **Separate Desks（s18）**：同一仓库底座上向两侧长出平行目录；两枚同名 config.py 各归各桌；
   乱桌抖动拒绝删除（`deny` 边框）。
7. **Full Turn（s20）**：七段传送带走一整轮（进料/护栏/选面/执行/外接/补救/记账），
   每段亮起前几集机制小图标；环在传送带正中。
8. **MCP Plug（s19）**：标准插头插入工具池；工具名前缀铭牌（`mcp__jira__create`）防重名。
