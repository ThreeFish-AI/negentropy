## P0 一个到一群

> 画面：开场直入（系列片头铺开 2026-10-08：五层栈落板与多 Agent 平台层点亮职责已由系列片头 series-intro.tsx 吸收，0-A=常驻条 Badge 淡入）；主问题字卡（「一个人」三字 mech 金点睛）；结尾五物件预告剪影（mech 金 ×5 自右缘挂入，不触碰左中 core 橙传送带锚位）。角标：`多 Agent`。回溯：§二·定位与标语（单 Agent 上下文覆盖不了）、§一·定位与标语（待办是会话内存）、分幕主线（五物件）

- [p0-01] 场景请回来：一间通宵不打烊的工坊。
- [p0-02] 模型是里面的师傅，手很快，但从不记事。
- [p0-03] 替他张罗一切的这套东西，行话叫 Harness。
- [p0-04] 前面亮灯的几个区，解决的都是他一个人怎么干得快。
- [p0-05] 这最后一区回答另一个问题：活多到一个人干不完，怎么办？

> 画面：台面溢出装置——师傅台面（coreDeep 矩形）上物件堆叠滑落；「重构整个后端」任务字卡拆成四色子活卡（认证／数据库／路由／测试）。回溯：§二·定位与标语（上下文窗口就那么大）、§一·定位与标语（TodoWrite 表达不了依赖、跨不了会话）

- [p0-06] 拿重构整个后端当例子：认证、数据库、路由、测试一起动。
- [p0-07] 师傅修到路由时，认证的细节早滑出了台面。
- [p0-08] 一个人的台面就那么大，摆不下整间工坊。
- [p0-09] 一双手也只有一双：互不拖累的活，照样串着做。
- [p0-10] 更要命的是，待办记在会话里——断电重启，什么都不剩。

> 画面：悬念立碑——「更聪明的师傅」字卡划掉 → 五物件剪影自右缘点亮（mech 金）；金句卡衬线体；`多 Agent` 角标随锚句出现。回溯：分幕主线（缺的不是更聪明的模型，是共享的朴素物件——175 §1 五物件缺口表）

- [p0-11] 答案不是请更聪明的师傅，是把工坊改成一群人也能共用。
- [p0-12] 从一个师傅到一群师傅——多<Agent|EY1 JH AH0 N T>平台，解的就是这道题。
- [p0-13] 这间多人工坊，缺五件朴素物件。
- [p0-14] 一块排工板、几个收件格、一套班次、各自的隔间、一个标准插口。
- [p0-15] 造完这五件你会发现：车间中央那条传送带，还是原来那一条。

## P1 排工板

> 画面：工坊入口排工板首现（mech 金卡片 ×N 钉板；卡片字段标签：编号／标题／状态／归属／依赖）；「次序」字卡——地基先于屋顶。角标：`.tasks/`、`blockedBy`。回溯：§一·定位与标语（次序隐喻）

- [p1-01] 第一件物件，挂在工坊入口：排工板。
- [p1-02] 为什么先造它？大目标得先拆开，活和活之间有先后。
- [p1-03] 盖房子不能先盖屋顶再打地基——任务之间，有依赖。

> 画面：一文件一活——卡片落盘动画（卡片＝文件图标钉上板）；六字段逐一点亮；三态环＋两动作按钮。角标：`task_*.json`、`pending → in_progress → completed`。回溯：§一·机制 1–2/5/8

- [p1-04] 排工板的做法朴素到夸张：每张活，就是一个文件。
- [p1-05] 文件里写六样：编号、标题、说明、状态、归属、依赖。
- [p1-06] 状态只有三档：待办、进行中、已完成；动作只有两个：认领、完成。
- [p1-07] 活放在板上，不放在谁的脑子里。
- [p1-08] 进程死了目录还在，重启扫一遍板，进度全回来。

> 画面：依赖检查分屏——依赖列表逐条核验（全绿放行／缺失项 deny 红锁）；「缺失＝被挡」字卡；完成时全板扫描播报刚解锁的卡。角标：`can_start`、`complete_task`。回溯：§一·机制 4/6、§一·README 引语（缺失的依赖视为被阻塞）

- [p1-09] 想开始一张活先过依赖坎：挡在前面的活全做完，才轮得到你。
- [p1-10] 其中一条判得特别狠：依赖的文件根本不存在，也算被挡住。
- [p1-11] 坏掉的前提，不会变成放行的理由。
- [p1-12] 做完一张活还有讲究：扫一遍全板，把刚解锁的活播报出去。

> 画面：认领动画——两师傅同时伸手同一卡，先到写归属、后者被拒（deny 红短闪）；「撕卡只能一个人撕」金句卡。角标：`claim_task`、`owner`。回溯：§一·机制 5、§四·机制 3（自陈无锁竞态）、轨C #2（官方文件锁）

- [p1-13] 认领是改归属的动作：领走的人写进归属栏，别人就领不走。
- [p1-14] 教学版自己承认这里没上锁：同时抢一张活，还是可能撞上。
- [p1-15] 官方文档说，产品的认领上了文件锁，专治这种竞争。
- [p1-16] 规律也就出来了：看板人人能看，撕卡只能一个人撕。

> 画面：官方限制卡——任务状态滞后（官方 Limitations 引语卡，mono 引语态）；活锁小动画（依赖箭头卡成死循环，需人手解扣）。角标：`Task status can lag`。回溯：轨C #3（§一·官方文档对照）、175 §5（活性被上游限制）

- [p1-17] 但官方文档明写过一个已知限制：任务状态会滞后。
- [p1-18] 有队友干完了活，却忘了把状态改成完成。
- [p1-19] 依赖它的活就永远等下去——挡得住坏前提的门，挡不住有人忘了结单。

## P2 收件格与派工单

> 画面：组队动机——领队帽（Lead 角标）＋常驻工位升起 ×2；临时工 vs 常驻同事对照卡（生命周期／通信／上下文／数量四轴）。角标：`Lead`、`subagent → teammate`。回溯：§二·定位与标语（临时工金句）、§二·四轴对照

- [p2-01] 有了板，第二件事是有人。
- [p2-02] 以前也请过帮手：叫来干一件事，交完工就走——临时工。
- [p2-03] 可有些活要的是常驻同事：能通信、能协作、随叫随到。
- [p2-04] 于是工坊改了编制：一位领队，带多名常驻队友。

> 画面：官方 Warning 引语卡（实验性／默认关闭，mono 引语态）＋「实验标签」徽标。角标：`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`。回溯：轨C #6（§二·官方文档对照）

- [p2-05] 官方文档明写：整套班组机制还标着实验性，默认关闭，得手动开。
- [p2-06] 机制是真的，标签还是实验的——往下每一条，落在产品上都得带着这个前提。

> 画面：收件格首现——工位门口格子（mech 金）＋投条动画（追加一行）；读格动画（整摞拿走、格子清空）；只看不取的探格动作；宿主侧轮询唤醒示意（事件队列）。角标：`.jsonl`、`peek`、`inbox_poller`。回溯：§二·机制 1–3/10

- [p2-07] 第二件物件，解决传话：每个工位门口，钉一个收件格。
- [p2-08] 每个格子是一个文件：发消息，就是往对方格子里添一行。
- [p2-09] 读的方式很狠：整摞拿走、格子清空——消息只被读到一次。
- [p2-10] 另配一个只看不取的探格动作，给工坊判断要不要叫醒师傅。
- [p2-11] 等消息的不是师傅，是工坊：它一遍遍替他盯格子，有新条就唤醒新一轮。

> 画面：工具单卡——队友侧（干活、读写、传话）vs 领队侧（招队友、开活、批单）；「招队友」「开新活」两行 deny 红删除线。角标：`sub_tools`、`create_task`。回溯：§二·机制 5（队友简化工具集）、§四·机制 9（＋任务三件）、175 §4（工具集就是班组边界）

- [p2-12] 一群人的边界，写在工具单上：发什么，他就能干什么。
- [p2-13] 队友的单子里，没有招队友的工具，也没有开新活的工具。
- [p2-14] 生不了下属、开不了新工单——靠的不是拦他，是压根没发给他。

> 画面：副台渐变卡——临时工挂牌「命名」后可按名叫醒（官方引语卡）。角标：`subagent names`、`resume`。回溯：轨C #42（分歧 D7）、轨C #14

- [p2-15] 官方又给临时工和常驻同事那条分界，补了一层渐变。
- [p2-16] 给临时工起个名字，就能按名叫醒它，全部记忆都还在。
- [p2-17] 名字一挂，这条界线在产品里就不是一刀两断了。

> 画面：派工单首现——一式两份单据（编号章样式）往返动画；三道验证闸门（编号存在／类型配对／未结案）逐一点亮；「先翻账再交消息」先后动效。角标：`request_id`、`match_response`、`shutdown / plan_approval`。回溯：§三·机制 1–5/7–8

- [p2-18] 光能传话还不够：要人拍板的事，得有凭证。
- [p2-19] 收件格上头再添一层——派工单，一式两份，编号清清楚楚。
- [p2-20] 请求带着编号出去，回复带着编号回来——传话不看脸，看编号。
- [p2-21] 回执进门过三道验证：编号存在、类型配对、单子还没结案。
- [p2-22] 关机的回执批不了计划的请求；结过案的单子，对重复回复免疫。
- [p2-23] 一张单子，只认得出它自己那一份回执。
- [p2-24] 消费格子还有个讲究：先翻协议的账，再交消息。
- [p2-25] 这套单据机制是通用的：关机靠它，计划审批也靠它。

> 画面：计划门三拍之一——队友递单、传送带继续转动；教学版自陈卡（「协议层的请求，不是代码层的门」mono 引语态）。角标：`submit_plan`、`plan_approval_request`。回溯：§三·执行门控边界（自陈）、分歧 D3 第一拍

- [p2-26] 计划审批，值得多说两句。
- [p2-27] 队友动大手笔前，把计划写成单子发给领队；批复回来，再动手。
- [p2-28] 但教学版自己承认：这只是协议层的请求，不是代码层的门。
- [p2-29] 队友会不会真停下等批复，靠的是它自觉。

> 画面：权限冒泡链路图——队友审批请求 → 领队界面弹窗 → 用户批准（dim 灰＝人色节点）→ 回执回流；【三】归属徽标＋官方引语卡。角标：`permission_request`。回溯：分歧 D4、§二·生产版对照 6（【三】五步冒泡）、轨C #40

- [p2-30] 权限这块教学版也省了：队友要审批时怎么办？
- [p2-31] 这个开源项目的作者拆过真实实现后说：队友的审批请求会一路冒泡。
- [p2-32] 官方文档确认：队友的权限提示出现在领队会话，由人在那儿批准。

## P3 班次

> 画面：领队派工过载——派工箭头 ×10 堆积（deny 红拥堵）；翻转：队友自行扫板认领（mech 金箭头分流）。角标：`scan_unclaimed_tasks`。回溯：§四·定位与标语（不能扩展）

- [p3-01] 这回，麻烦出在领队身上：手动派工，派不过来了。
- [p3-02] 板上十张没人领的活，就得手动指派十次——这不叫扩展。
- [p3-03] 第三件物件是班次，解的就是这道题：自己看板，自己认领。

> 画面：班次三拍状态机——干活／待命／关机三态环；轮数上限护栏；待命节拍器（先格子后板的顺序箭头）。角标：`idle_poll`、`WORK / IDLE / SHUTDOWN`。回溯：§四·机制 1/4

- [p3-04] 队友的一天是三个节拍：干活、待命、关机。
- [p3-05] 干活有轮数上限，防着师傅原地转圈。
- [p3-06] 待命时每隔几秒看两样，顺序有讲究：先门口的格子，再排工板。
- [p3-07] 格子里躺着的可能是关机请求——指令，永远排在临时发现的活前面。
- [p3-08] 等太久没人理就自己下班，走前留一张总结条给领队。

> 画面：认领三条件合取卡（待办 ∧ 无主 ∧ 依赖全完）＋「有依赖≠不合格」对照行；回执验「领到」闸。角标：`claim_task`、`Claimed`。回溯：§四·机制 2–3、§四·定位金句（依赖语义）、§四·机制（演示剧本·领班不派活）

- [p3-09] 扫板认领，资格是三个条件的合取。
- [p3-10] 状态是待办、没有归属、依赖全做完——三条全中才能领。
- [p3-11] 最容易读错的是第三条：有依赖，不算不合格。
- [p3-12] 被没干完的活挡着才算；依赖全清的活，照样领。
- [p3-13] 认领结果也要验：回执真写了领到，才把活注入上下文。
- [p3-14] 失败不当成功，是这个系统反复出现的脾气。
- [p3-15] 领队全程只干两件事：建活、开机——分配，从没干过。

> 画面：教学 vs 产品双向卡——超时下班（教学）vs 无固定超时·手动关机（产品）vs 原地复活（官方）；完成事件两种数法对照（一条消息 vs 通知内含答案）。角标：`idle_notification`。回溯：§四·交叉参照（轨C #11）、轨C #19（分歧 D5）

- [p3-16] 讲到这，教学版和产品走出了两个方向。
- [p3-17] 教学版等不到活，就超时下班、自己走人。
- [p3-18] 产品反而不赶人：说明写着没有固定超时，关机由领队发起。
- [p3-19] 急着下班的，反而是教学版。
- [p3-20] 官方文档还有个说法：已停的队友收到新消息，能原地复活。
- [p3-21] 至于干完了怎么报信，有两种数法。
- [p3-22] 教学版发一条结果消息；官方文档说，产品的空闲通知本身就带着最终答案。
- [p3-23] 一件事，一次说清。

## P4 隔间

> 画面：覆盖事故——两师傅同写同一文件，后写盖先写（deny 红覆盖闪）；「分不清谁的改动」回滚困境卡。角标：`config.py`（事故卡，不口播）。回溯：§五·定位与标语

- [p4-01] 队友各自领活，新麻烦跟着来：俩人改的是同一个目录。
- [p4-02] 一个改认证、一个改登录页，前后脚写同一文件，后写盖掉先写。
- [p4-03] 想回滚都难——分不清哪些改动是谁的。

> 画面：隔间拓扑——主仓库下方开出两间带门牌隔间（各挂分支），任务卡与隔间以编号绳相连；认领即切目录、交活切回的路径动画。角标：`git worktree`、`wt/{name}`。回溯：§五·机制 1–3、§五·拓扑（code.py 文件头）

- [p4-04] 第四件物件登场：给每张活，隔出一间带门牌的小隔间。
- [p4-05] 不是新建仓库，是同一个仓库开出的几个工作副本，各挂各的分支。
- [p4-06] 任务管目标，隔间管地盘，一根编号绳子拴住两样。
- [p4-07] 绑定还有个细节：只写档案不改状态——活还是待办，等人认领。
- [p4-08] 领队可以提前备料：先把活挂上板，再一间间把隔间开好。
- [p4-09] 队友认领带隔间的活，读写自动落进那间目录；交完活切回公共区。

> 画面：拆除守卫流程——清点（未提交／未推送）→ 非零拒绝 → 查不动也拒绝；三出口卡（默认不拆／强删连分支／保留等审）；流水日志条目追加。角标：`remove_worktree`、`discard_changes`、`events.jsonl`。回溯：§五·机制 4–5/7/9

- [p4-10] 拆隔间的默认答案，是不拆。
- [p4-11] 拆之前先清点：没提交的文件、没推走的提交，一律拒绝。
