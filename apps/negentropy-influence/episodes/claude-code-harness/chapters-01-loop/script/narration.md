## P0 大模型的行动瓶颈

> 画面：系列片头装置之后冷启动——终端窗口中央一条写好却无人按下的命令行，光标孤闪；右下角常驻署源角标（信源名，首部署源位，随画面淡入）

- [p0-01] 这是一个会写命令、却永远在等你按回车的模型。
- [p0-02] 你让它列目录、跑脚本，它能写出正确的命令。
- [p0-03] 但输出完文字，一切就停住了。

> 画面：用户头像在「模型—终端—模型」之间来回搬运箭头，搬运次数计数器疯涨

- [p0-04] 复制、粘贴、按回车，贴回输出，下一条命令才出来。
- [p0-05] 每一个来回，你都成了它和电脑之间的中间层。

- [p0-06] 把这段搬运交给程序自动跑，这个驱动外壳，工程上就叫 Harness。
- [p0-07] 它简单得出奇：一个循环，把执行结果喂回给模型，给它接上一双手。

## P1 一个循环就够了

> 画面：陶土橙环体闭合成循环主角；双信号做成物理闸门——工具调用块到达则放行、环体转动，空手到达则侧门开启、循环退出；随后源码三十余行完整函数面板自上而下铺开（while True 行高亮，五步行号预埋括号锚）

- [p1-01] 整个解法，就是一个不停转的循环：模型调工具，就继续；不调，就停。
- [p1-02] 判断只认一个信号：回答里，有没有工具调用块。
- [p1-03] 有，执行、喂回、继续转；没有，立刻退出。

- [p1-04] 整套翻译成代码，核心只有三十多<行|HANG2>。
- [p1-05] 一个工具，加一个循环，就是一个 Agent。

> 角标：while True · tool_use

## P2 五步工作原理

> 画面：三联画舞台＝左真实代码编辑器（源码逐行落定）/ 右消息列表（角色色块）/ 角上环体站位灯；每步一次「代码行落定→消息块生长→环体走一格」三联动

- [p2-01] 拆开来看，正好五步。
- [p2-02] 第一步，把你的问题，存成对话里的第一条消息。

- [p2-03] 第二步，带上全部对话和工具清单，调用模型。

- [p2-04] 第三步，把回答原样存档，然后查那个信号：里面有没有工具调用。
- [p2-05] 没有调工具，任务完成，循环就此退出。

- [p2-06] 第四步，照着参数，把命令在真实环境里跑出结果。
- [p2-07] 每份结果，都挂上这次调用的编号，包成一条工具消息。

> 画面：消息角色标签特写——assistant「我要调工具」之后紧跟一条 user「这是你要的结果」，角色色块对比闪两下；编号配对签 #01 全程可追

- [p2-08] 第五步，结果以用户的身份塞回对话，回到第二步。
- [p2-09] 注意这个身份：凡不是模型自己产出的内容，都算输入。

- [p2-10] 五步组装成一个函数，就是最小可运行的 Harness 内核。
- [p2-11] 要不要调工具、调哪个，模型说了算；跑命令、送结果，程序来干。
- [p2-12] 后面的章节都在这个循环上叠机制，循环本身，始终不变。

> 画面：拉回全函数——五枚括号锚全亮＝三十行内核；分工铭牌；后续章节以匿名小方块叠上环体外缘而环体本身一格不动

> 角标：messages · run_bash · tool_result · tool_use_id

## P3 试一下

> 画面：仿真实终端会话——prompt 逐字敲入、消息列两轮生长、命令真执行回喂；「观察重点」双字幕卡（调工具→循环继续 / 不调→循环结束）；安全提示（建议在临时测试目录运行）为视觉角标不口播

- [p3-01] 跑起来试一下：帮我列出这个目录下的 Python 文件。

- [p3-02] 第一轮，模型开口要工具：一条列目录的命令，参数已经写好。
- [p3-03] 程序照单执行，目录清单当场喂回对话。

- [p3-04] 第二轮，模型给出纯文字回答，没有再要工具。
- [p3-05] 这次没有调用，循环平稳退出。

- [p3-06] 再问一句当前的分支名，还是同样的两拍：一轮调用，一轮作答。
- [p3-07] 观察重点：调工具，循环继续；不调，循环就结束。

> 角标：ls · git branch · 观察重点

## P4 生产版源码对照

> 画面：基线标尺——三十与一千七百多两根悬殊柱 + 约 57 倍比例参考线；流式打字机逐字到达、工具调用块前半段就位而收尾字段停在旧值（迟到徽章）；needsFollowUp 开关致动连线；State 十槽外圈；退出路径族；保险丝层收束

- [p4-01] 真实的 Claude Code 怎么做？
- [p4-02] 负责主循环的文件，足足有一千七百多<行|HANG2>。
- [p4-03] 内核完全一致：还是同一个循环，只是判断上，更较真。

- [p4-04] 判断还有一种更直观的写法：查 API 返回的收尾字段。
- [p4-05] 可是生产环境必须用流式传输：回答像打字机一样，逐字到达。

- [p4-06] 这时候，工具调用块前半段已经到位，收尾字段却还停在旧值。
- [p4-07] 等字段再做判断，很容易误判成已经结束，要的工具调用被悄悄丢掉。

- [p4-08] 所以生产版不认字段，改用一个继续运行的开关。
- [p4-09] 流式接收中，只要检测到工具调用块，开关立刻拨通。

- [p4-10] 教学版只守一个对话列表；生产版的状态表，十个字段，各管一类。
- [p4-11] 退出路径也不止一条：超长、报错、中止、轮次上限，各有处置。

- [p4-12] 这些多出来的逻辑，全是系统面对不确定性的保险丝。
- [p4-13] 真保险丝一烧就断路；这里的保护，多数还能重试、还能续跑。
- [p4-14] 三十<行|HANG2>骨架是恒定核心，一千七百多<行|HANG2>全在外层守护它。

> 角标：query.ts · needsFollowUp · State
