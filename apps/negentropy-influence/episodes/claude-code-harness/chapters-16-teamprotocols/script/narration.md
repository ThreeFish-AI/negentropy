## P0 一句「行」不算数

- [p0-02] 队友一多，口信满天飞——最悬的，就是那句「行」。

> 画面：左右分屏问题现场——左：队友的执行流被硬掐，写到一半的文件碎片悬空闪烁；右：队友举着一份标「高风险」的计划，等一个点头

## P1 一张登记表

> 画面：登记表主视觉首次亮出（靛蓝）——表头：编号 / 类型 / 发给谁 / 状态（完整行七字段缩略进画面）；三态胶囊「待处理 / 已批准 / 已拒绝」依次点亮

- [p1-01] 答案，是一张登记表。
- [p1-02] 每单协商，先开一张请求单，领一个号。
- [p1-03] 单上记着：编号、类型、发给谁，和状态。
- [p1-04] 状态只有三种：待处理、已批准、已拒绝。

> 画面：回执簿类比镜头——簿页一单一号，回执联撕下、与存根对号重合（兰紫落定拍）；两三句即切回登记表

- [p1-05] 像一本回执簿：开单、等回执、按编号销账——对上号，才算办结。
- [p1-06] 边界说死：簿子不担保对方一定回——它管销账，不管催账。

> 画面：左侧聊天记录无限滚动、渐虚化；右侧登记表一行定格、状态清清楚楚；环体〔M-001〕远景掠过

- [p1-07] 答应没答应、办没办结，从此看表说话。
- [p1-08] 这本账怎么转？拿一单关机，走四步。

> 角标：request_id · ProtocolState · pending / approved / rejected

## P2 四步走一单

> 画面：四步动线之一——主代理侧生成 142 号请求卡（靛蓝）；登记表落一行「142 / 关机 / 队友甲 / 待处理」

- [p2-01] 第一步，开单：领号 142，类型关机，发队友甲，先记待处理。
- [p2-02] 第二步，投递：请求进甲的收件箱；一看类型是关机，甲先收尾。

> 画面：请求卡滑入队友甲的收件箱格；甲头顶亮起「收尾中」进度环；回执卡（兰紫）携同一枚 142 号徽章沿回流线返回

- [p2-03] 第三步，回执：甲回一条回复，带回同一个 142 号和同意与否。
- [p2-04] 第四步，销账：翻表对号，才把状态改成批准或拒绝。
- [p2-05] 账一销，甲收摊退场——这单协商闭环了。

> 画面：登记表长出新行——一单「计划审批」走同款三态流转；「+ 类型」分支按钮点亮，机器本身零改动

- [p2-06] 换成审批，一个字不用改：同一张表，同一套状态。
- [p2-06b] 这张对上号才改状态的表，<行|HANG2>话叫协议状态机。
- [p2-07] 加新协商？不造新机器，多开一个类型分支就够。
> 画面：「对号」二字放大、拆成三枚碎片悬浮：号 / 类型 / 状态
- [p2-08] 听着挺稳？「对号」两个字里，还藏着三道检查。

> 角标：dispatch_message · shutdown_request / shutdown_response

## P3 三道检查

> 画面：三栏检查卡依次点亮——① 编号：回复带的号在表上查无此行，弹开 ignored；② 类型：关机回复撞上计划单，弹开；③ 状态：已办结的单再收回复，弹开

- [p3-01] 销账那一刻，三道检查挨个过，一道拦一种错。
- [p3-02] 第一道查编号：号在表上没有？不理——拦住认错单的回复。
- [p3-03] 第二道查类型：类型对不上？不理——关机的回复，批不动计划的单。
- [p3-04] 第三道查状态：这单已办结？不理——同一句话，不许生效两次。

> 画面：消融实验台——左绿「类型检查在位」：一条错配回复被弹开（type_mismatch → ignored），计划单仍「待处理」；右红「拆掉类型检查」：同一条关机回复撞进计划单，状态被改成「已批准」

- [p3-05] 嫌它死板？实测说话：把第二道拆了，编号照留。
- [p3-06] 一条关机回复，把一单挂着的计划审批，硬改成已批准。
- [p3-07] 编号对上，只是找对了单；类型对上，才是同一件事。

> 画面：防重双屏 + 改写计数器——左：状态检查在位，第二遍投递被弹开（already approved → ignored），计数停在 1；右：关掉后同条「同意」投两遍，计数 1→2；再投一条「不同意」副本，绿色「已批准」翻成红色「已拒绝」，计数跳 3

- [p3-08] 第三道也拆过：关掉状态检查，同一条「同意」投两遍。
- [p3-09] 表被改写两次；再投一条反话，已批准当场翻成已拒绝。
- [p3-10] 一个请求，只决议一次——这条底线，第三道兜着。
- [p3-11] 三道齐了就万无一失？还有个更隐蔽的坑：谁来读那条回复。

> 角标：match_response · unknown_id / type_mismatch / duplicate

## P4 入口与真实版

> 画面：收件箱特写——一封信被取走即消失（读即消费）；两条「读者」箭头（查信工具 / 循环）同时伸向箱口，只有一只手拿到信，另一只扑空

- [p4-01] 坑就在那只收件箱：规矩还是那条。信，取走就没了。
- [p4-02] 查信的工具、还有循环本身，各读各的：先读的拿走回复，账，一笔没销。
- [p4-03] 实测就坏成这样：关机那单，永远销不了——再去看，箱子空了。
- [p4-04] 解法一句话：读即消费，单点入口。进门先销账，再把信交给对话。

> 画面：拉远到真实版全景——十五枚消息类型卡片阵列；三向关机时序：请求 → 批准或拒绝（附理由）→ 系统通知 → 自动清场

- [p4-05] 那真实的 Claude Code 呢？这一路的请求单和回复，那边叫什么？
- [p4-06] 拆解过 Claude Code 源码的同学们应该知道：叫协议消息，格式不对就拒收，一共十五种。
- [p4-07] 关机是三向的：请求、批准或拒绝附理由，再补一条系统通知。

> 画面：闸门对照——教学版侧无闸，跑命令 / 写文件直行；同一门课的新版闸门落下，未批准的跑命令 / 写文件被弹回

- [p4-08] 咱们这台教学版，自己承认：没有执行闸门。批没批，靠自觉。
