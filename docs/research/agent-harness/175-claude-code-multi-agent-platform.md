# ⑤ 多 Agent 平台：从一个到一群

> **一句话本质**：把「多 Agent」拆开，全是朴素物件——一张板、几个格子、带编号的单据、各自的隔间；而循环还是那一个。

## 1. 这一层要解决什么问题

上一层把时间还回来了，可整间工坊自始至终只有一位师傅、一条传送带。一个人只有一双手：两件互不依赖的活串着做，慢的拖住快的；而待办、台面、工序卡全是**会话内的物件**，进程一关什么都不剩。要「从一个到一群」，缺的不是更聪明的模型，是一整套**共享的朴素物件**：活要放在人人可见处（排工板）、传话不能挤进同一张台面（收件格）、拍板要留凭证（派工单）、各自的活各自改（隔间）、别人家的机器要接得进来（标准插口）。课程把这些物件一件件造出来，模型还是那个模型。

| 上一层留下的缺口 | 本层机制 | 大白话 |
|:---|:---|:---|
| 活与待办都是会话内的，进程一关全没 | 排工板：一文件一任务落盘，三态两动作 | 活挂在磁盘上，不挂在谁的脑子里 |
| 谁在干哪张活、先后顺序说不清 | 认领守卫（owner 检查）+ 依赖 fail-closed | 看板人人能看，撕卡只能一个人撕 |
| 一群人传话会挤爆同一张台面 | 每人门口的消费式收件格 | 通信挪出台面 |
| 口说无凭的「批准了」「收工了」 | 带编号、验类型、验未结案的派工单 | 单子只认得出自己那一份回执 |
| 没人盯着时队友干什么、什么时候走 | 三拍班次：干活 → 待命 → 关机 | 指令压过临时活，超时即下班 |
| 几个人同时改一个目录必打架 | 各自的隔间（worktree），任务按 ID 绑地盘 | 隔的是工作副本（教学版口径） |
| 别人家的机器怎么接进工坊 | 标准插口（MCP）：重起名进同一个号码簿 | 自我介绍不构成放行理由 |

## 3. M1 · 入口排工板：任务图（站点轨 s12《Task System》）

> [!TIP] **类比**
> 工坊入口挂一块排工板，每张活是一张卡片钉在板上：写清干什么、被谁挡着、被谁领走。卡片在板上而不在任何人口袋里——人来了读板，人走了板还在。

**不变式一 · 一文件一活，跨会话即重读目录。** 任务是磁盘上的 JSON 文件（`Task` 含 id / subject / description / status / owner / blockedBy），没有任何内存态；重启恢复＝重新扫目录【一】。官方产品同构：任务列表落在 `~/.claude/tasks/{team-name}/`、本地持久、resume 保留，而班组配置会话末即删——连生命周期的差异都长在文件布局上【官】（agent-teams §Architecture）。

**不变式二 · 三态两动作，所有权是钥匙。** 状态机严格 `pending →claim→ in_progress →complete→ completed`；认领要求 status 为 pending，完成要求 in_progress——已完成的活结不了，不是自己的活也结不了【一】。官方同为三态＋依赖未完不可认领【官】（agent-teams §Assign and claim tasks）。

**不变式三 · 依赖判坏是 fail-closed。** 依赖的文件缺失、或状态不是 completed，一律判「被阻塞」，而不是「无依赖 → 可开始」。坏掉的前提不会变成放行的理由【一】——但见第 12 节：fail-closed 撞上「人忘标完成」，官方自陈就是活锁。

**不变式四 · 完成即解锁并播报。** 完成时全量扫描所有 pending 且被依赖挡着的任务，把「刚刚可做」的播报附在返回串里【一】。注意是**全量重列**而非差集快照——早就解锁却无人认领的活，会在别人每次完工时被**再播报一次**（main 演进才改回差集，见下）。

**排工板与待办是两层，不是升级。** 待办是会话内、整表替换、无依赖无归属——帮单个师傅不漂移；排工板是跨会话、单条 CRUD、带依赖与归属——支撑班组协作；终点站两者并存【二】。产品侧同构：无 Task 工具的 Agent 降级走消息协调【官】（agent-teams §Assign and claim tasks）。

**教学缺口是自陈的，不是藏着的。** 站点轨 README 明写：DAG 环检测未实现；并发认领无文件锁、可能竞争——owner 检查只挡住「最明显的后写覆盖」【二】。产品用文件锁防竞态【官】（agent-teams §Assign and claim tasks）；【三】更细：`claimTask` 用任务文件锁＋列表级锁双重防护，锁内重读防「检查与使用之间被抢」，且只设 owner 不改状态（状态迁移由另一工具负责），ID 用递增整数加高水位标、删掉的编号永不复用。

**main 轨演进注记（@ 0dcafa2a，main 轨 s10_task_system）**：两阶段建图（同轮多个工具调用拿不到彼此 ID，须先建全部节点再连边）；连边时反向可达性环检测；认领收进「进程内锁＋任务目录跨进程文件锁」的双层锁内原子完成；一人一活互斥；临时文件原子替换；完成播报从全量重列改回差集快照。站点自陈的并发与建图缺口，main 补了一半。

> [!IMPORTANT] **实景**
> `s12_task_system/code.py @ 67a9126`（claim 守卫摘引，锚点 111–123；注释为本文所加）
>
> ```python
> if task.status != "pending":              # 已被认领或已完成 → 拒绝认领
>     ...
> blocked = [d for d in task.blockedBy
>            if not _task_path(d).exists()  # 缺失的依赖也算被阻塞
>            or load_task(d).status != "completed"]
> if blocked:
>     return f"Blocked by: {blocked}"
> ```
>
> 三个守卫一句话：状态不对不领、前提坏了不领、领了就写 owner。锁是 main 与产品的事，守卫是这一版自己的事。

**口播落点**：大目标拆成小任务，排好序，持久化——活挂在磁盘上，不挂在谁的脑子里。

## 4. M2+M3 · 收件格与派工单：消息总线与协议（站点轨 s15《Agent Teams》＋s16《Team Protocols》）

> [!TIP] **类比**
> 每个工位门口钉一个收件格：传话就往对方格子里投一张条，读的人把整摞条一起拿走，格子清空才算读过。要人拍板的事不走口传——填一张一式两份的派工单，编号写得清清楚楚，批复也凭编号认领。

**先立产品前提（本节最重要的一条轨 C 校准）。** 官方把整套班组机制标为**实验性、默认关闭**：不设 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`，就不会建队、不写目录、不生成队友【官】（agent-teams 页首 Warning）。课程教的是机制，产品还戴着实验标签——本节以下全部机制断言，落在产品上都以此开关为前提。

**不变式一 · 消费式读。** 一人一个 JSONL 收件格；发送是追加一行，读取是**读出全部行然后删掉整个文件**——「读一条撕一条」的物理形态是「读一摞撕一叠」；另有 peek 非破坏探测，供宿主侧决定要不要唤醒一轮【一】。教学版自陈 read＋unlink 两步之间有竞态，「对教学场景可以接受」【二】；【三】产品用文件锁写收件箱（读→追加→写回，带锁重试）；官方同构：邮箱是一人一个 JSON 文件，读取时逐条校验、坏条目剔除、好条目照送【官】（agent-teams §Architecture）。

**不变式二 · 唤醒不靠模型轮询。** 把「有消息」变成「起一轮」的是宿主层：统一事件队列＋一秒收件格轮询器，队友消息与后台结果不等用户输入就唤醒新回合【一】；官方口径同向——消息自动投递，Lead 无需轮询【官】（agent-teams §Context and communication）。模型桌上虽有 check_inbox 一件查询工具，注入链路不依赖它。

**不变式三 · request_id 是贯穿全链路的关联键。** 每次请求生成一个六位编号，请求带着它出去、回复带着它回来【一】。

**不变式四 · 回复匹配三重校验。** 依次验：**编号存在**（未知编号打日志跳过）、**类型配对**（一个 shutdown 回执不会意外批准一个计划请求）、**仍是 pending**（已结案的请求对重复回复免疫——幂等）【一】。官方同向且更广：收方被告知消息来自另一 Claude 会话、队友不得代用户批权限、被拒动作不得经队友转手绕过【官】（agent-teams §Messages between agents）。**身份校验不在这份清单里**——「回复人身份对得上」是 main 演进才加的第四重（见下），站点轨防不了「别人替你批复」这一层。

**不变式五 · 先路由后返回。** Lead 消费收件格的函数在同一次调用内，先对所有协议回复完成状态翻转，再把全部消息返回给调用方——不存在「消息读走了、协议状态没翻」的中间态；代码注释自标 "s16 fix"【一】。官方同构：结构化协议消息与普通消息同一信道、写文件成功才算送达【官】（agent-teams §Architecture）。

**不变式六 · 按类型路由，加协议只加分支。** 队友的收件格同时收普通消息与协议消息，按 type 字段分发到处理分支，「新增协议类型只需加新的 if 分支」【二】；**两种协议一套机制**——关机（Lead→队友）与计划审批（队友→Lead）共用同一个 pending→approved/rejected 状态机【一】。【三】产品的十五种结构化消息类型同样共用 request id 关联机制。

**工具集就是班组边界。** 站点轨队友的工具从 4 件（bash/read/write/send_message）长到 8 件（＋submit_plan＋任务三件），`spawn_teammate` 与建图改图工具始终只在 Lead 的工具表里——队友生不了队友、也改不了排工板，**靠的是发给他什么工具，不是运行时拦他什么调用**【一】。官方与【三】同向确认：无嵌套班组、只有 Lead 管队【官】（agent-teams §Limitations）。副台与队友的分工（四轴对照【二】）：副台一次性、只回传结论；队友常驻、收发消息、双向协作——但官方产品里这条分界是**渐变**的：给副台起个名字它就能被按名 resume 并保留完整对话史，Agent 工具带 name 即升格为队友——队与副台是同一工具的两个档位【官】（sub-agents §Subagent names；agent-teams §How Claude starts agent teams）。

**计划门要分三拍讲（本维最大的口径反转）。** ①**s16 无门**：教学版自陈「演示了请求-响应消息流程，没有实现执行门控」，提交计划后队友线程继续跑、仍能调 bash/write，「真实执行依赖模型自觉等待批复」——docstring 原话 "This is a protocol-level request, not a code-level gate"【一】。②**s20 真门**：终点站把它做成代码级强制——submit_plan 后队友**停止一切模型与工具步骤**、等待期只轮询协议回复不跑模型、同一响应里后续 tool_use 块被忽略【一】。③**产品自动批**：官方明写计划请求「一到 Lead 会话就批准，不经 Lead 审阅」，修改型动作改由权限提示兜底【官】（agent-teams §Have teammates plan before implementing）。课程越把门做真，产品越把门自动化——安全责任整体移给了权限层与生命周期 hooks（TeammateIdle / TaskCreated / TaskCompleted，exit 2 可阻止并反馈【官】）。这就留下一道真争议：**审批归协商层还是执行层**——门保留在协议里但自动通过，换来的是计划内容不再进入人类决策回路，这个损失权限层补不回来（见第 14 节问答 2）。

**权限冒泡是省略项，产品是标配。** 站点轨教学版省略权限冒泡，对比表明示「真实 CC 有冒泡机制」【二】；【三】给出产品五步链路：队友发 permission_request 到 Lead 收件箱 → Lead 侧一秒轮询器检测并路由到审批队列 → 用户在 Lead 界面批准 → 回执流回队友收件箱 → 队友侧 500ms 轮询器接力。官方确认：「队友的权限提示出现在 Lead 会话」，权限模式随 Lead 继承（dontAsk 除外）【官】（agent-teams §Permissions）。「权限不冒泡」只能当教学实现口径讲。auto 权限模式下官方还多一层**投递前审查**：每条智能体间消息（含关机请求、审批回执这类协议消息）送达前先过审、被拦的不达收件人，转发来的「已获批准」声明一律视为不可信输入【官】（agent-teams §Messages between agents）——教学版没有这一层。

**完成事件的两种数法。** 站点轨队友跑完只发**一条** result 消息；「空闲通知」是【三】产品机制（s16 自陈教学版省略）；main 演进拆成**两条**（结果＋空闲）；而官方产品是**一个通知内含最终答案**，API 出错时通知失败并附错误文本【官】（agent-teams §Context and communication）——一件事一次说清，与课程「两个状态分两个事件」是两种事件模型。

**main 轨演进注记（@ 0dcafa2a，main 轨 s13 整合章）**：消息总线线程安全（锁＋条件变量）；身份校验入回复匹配（四重）；结果与空闲拆成两个事件；**陈旧审批作废**——计划请求绑定提交时的任务 ID 与工序版本号，认领/释放/完成都会递增版本，换了活旧批自动作废；执行门禁下沉到工具分发层（未批拦 bash/write_file/edit_file 与完成任务）。

> [!IMPORTANT] **实景**
> `s16_team_protocols/code.py @ 67a9126`（match_response，锚点 389–413）
>
> ```python
> state = pending_requests.get(request_id)
> if not state:
>     return                                          # unknown request_id
> if state.type == "shutdown" and response_type != "shutdown_response":
>     return                                          # type mismatch, skip
> if state.status != "pending":
>     return                                          # already resolved, skip duplicate
> state.status = "approved" if approve else "rejected"
> ```
>
> 三段早退对应三重校验；最后落定状态。main 演进在中间再加一段身份比对（发件人须为请求目标、收件人须为请求发起人）——站点轨的清单里没有它。

**口播落点**（M2）：一个搞不定，组队来——但队友不是临时工，是常驻工位、门口有自己收件格的同事。**口播落点**（M3）：传话不看脸，看编号：请求带着编号出去，回复带着编号回来，编号对不上就不算数。

## 5. M4 · 班次：队友的自治（站点轨 s17《Autonomous Agents》）

> [!TIP] **类比**
> 队友不是招之即来的临时工，是常驻工位的师傅：干完手上的活不散伙，坐回工位等两样东西——门口格子里的新指令，或板上没人领的新活。等太久没人理，就自己下班。

**班次是三拍：WORK → IDLE → SHUTDOWN。** 外层循环让干活与待命交替；单次干活有轮数上限（防无限循环）；待命每几秒轮询一次，**先收件格、后排工板**——格子里的指令可能就是关机请求，必须压过临时发现的活；两拍都能响应关机；待命超时即自动关机，收尾发总结给 Lead（轮询间隔、超时与轮数等常数随修订漂移，参数见对应集 notes）【一】。这个「超时即走」要跟产品对照着读：README 自陈产品侧「无固定超时，Lead 手动 shutdown」——**教学版反而比产品更激进地自动退出**【二】；官方产品更进一步：已停队友收到消息可原地复活并恢复对话，但 /resume 不还原队友【官】（agent-teams §Use subagent definitions for teammates / §Limitations）。

**不变式一 · 扫描资格的合取（最容易读错的一条）。** 候选＝`pending` 且无主 且依赖**全部已完成**。第三项判的是「每条依赖都完成了」，不是「没有依赖」——**有依赖不等于不合格，被没完成的依赖挡着才算**【一】【二】。官方同向：干完自领下一张，判据 unassigned＋unblocked——恰是课程三条件的子集【官】（agent-teams §Assign and claim tasks）。

**不变式二 · 认领失败不当成功。** 自动认领处检查返回串含 "Claimed" 才注入上下文，失败只打印不下账【一】。

**不变式三 · 领班不派活。** Lead 只创建任务与启动队友，分配靠队友自己看板——演示剧本里 alice/bob 并行认领、Lead 一次手动 assign 都没有【二】。

**不变式四 · 身份放在了会被压缩的地方（本版的反面教材）。** 队友身份块写进消息流，压缩后消息过短就重插一块补救；README 自陈产品靠「压缩时保住 system 提示」解决，教学版的简化需要手动处理【一】【二】。main 演进给出正解：身份是每次模型调用单独传的参数、从不进消息数组——**补救是放错位置的供词**，这条提炼成立，但要标明不变式属于 main 轨，站点轨恰是它的反例。

**并发仍是自陈缺口。** 无文件锁，并发认领可能竞争；owner 检查挡住最明显的后写覆盖，【三】产品侧用任务文件锁在锁内完成读-检查-改-写，官方文档化为 file locking【官】（agent-teams §Assign and claim tasks）。**规律**：发现可以并发（看板人人能看），所有权变更必须独占（撕卡只能一个人撕）——三个口径同一教训。

**交叉一条产品限制**：官方自陈任务状态会滞后——队友忘标完成会卡住依赖方，需人工改状态或让 Lead 提醒【官】（agent-teams §Limitations）。自治认领的活性，被上游「忘结单」直接限制。

**main 轨演进注记（@ 0dcafa2a）**：待命从定时轮询改「阻塞等消息、超时空手才扫板」；不设固定轮数上限、不因空闲超时自行退出（只在关机请求时退）；**人走活退回**——线程收尾把名下未完成的活改回 pending 清空归属（站点轨 README 自陈省略了这条恢复路径）；扫描加第四条件「隔间绑定可解析」（fail-closed 第二次出场）；租约保留到轮次边界；身份移出消息数组。

## 6. M5 · 各自的隔间：worktree 隔离（s18《Worktree Isolation》）

> [!TIP] **类比**
> 几位师傅同时改东西，工坊就给每张活隔出一个带独立门牌的小隔间，各改各的工作副本。课程用一根 ID 绳子把「这张活」拴在「这间隔间」上——注意，这是教学版的绑法。

**开篇先立架构事实（轨 C 第一分歧）。** 课程把隔间编进班组：任务带 worktree 字段、认领即切目录、整章围绕绑定展开；而官方 agent-teams 页**通篇不提 worktree**（队友以 in-process / 分屏窗格形态运行），worktrees 是独立定位的「手动并行」机制，子代理另有 `isolation: worktree` 声明式隔离；任务与 worktree 的绑定，官方两页**零记载**【官】（worktrees 页；agent-teams §Next steps）。【三】源码佐证：产品的持久化隔间会话没有任务标识，两个系统靠 Agent 的上下文理解去关联——「任务—隔间硬绑定」是课程明示的教学简化。所以「教学版比产品更严」的旧判，如今有源码与官方文档的**双重负证据**，保留并升格。

**不变式一 · 名字按路径的规矩审。** 隔间名走白名单正则（`[A-Za-z0-9._-]{1,64}`），拒空名、拒 `.` 与 `..`；【三】产品用同样的规则校验 slug——「教学版用同样的规则」【三】（worktree.ts:48/76-84）。

**不变式二 · 绑定不改状态。** 绑定只写任务的 worktree 字段，任务保持 pending 等自治认领推进——Lead 可以提前备料（建任务＋开隔间），自治认领流不被打断【一】。

**不变式三 · 有改动默认不拆，查不动也不拆。** 拆除前清点未提交文件与未推送提交，任一非零即拒绝、须显式 discard 才强删；**连状态都查不出来（清点返回异常）同样拒绝**——fail-safe【一】。keep 则留分支等人工 review【一】。要记住站点轨的一处硬边界：**discard 强删连分支一起删**（`git worktree remove --force` 之后跟 `git branch -D`）【一】。

**不变式四 · 生命周期可审计。** create/remove/keep 都追加写 events.jsonl，且**只在 git 命令成功后写**——日志只记真实发生的事【一】。

**不变式五 · 认领即切目录，完成即切回。** 队友认领带隔间的任务，bash/read/write 自动在该目录下执行；完工显式触发后才切回共享目录【一】。教学实现是每队友一个路径字典；【三】产品是两条真路径：一条进程级 `chdir` 切换整个会话目录、退出时恢复，一条只给子代理套目录覆盖、不动全局会话状态。

**隔离强度的口径必须分轨。** 课程两轨教的都是「换目录」：站点轨切工具 cwd，main 轨自陈三处「隔间不是沙箱、shell 仍能访问一切」。而官方现行文档是**四项工具调用级硬阻断**——指向主 checkout 的编辑（Edit/Write/NotebookEdit）、工作目录解析到主 checkout 的命令、把 git 重定向进主 checkout 的命令、无法从命令文本核验的命令形状——且明写 "You can't turn this check off"【官】（worktrees §How Claude Code enforces isolation）。「只是换目录、不是沙箱」这句对当前产品**不再成立**：隔离强度上产品反超了教学版。于是本维「教学≠产品」是**双向**的：绑定上教学版更严，隔离上产品更严。清理口径也三方不同：官方干净时未命名会话连分支自动删、显式 remove 删分支＋工作，sweep 只清自己造的隔间、运行中持 worktree lock【官】（worktrees §Clean up worktrees）——而 main 轨「两条移除路径都保留分支」反而是三轨中最保守的一个。另有两条产品级细化：出 `.claude/worktrees/` 边界的 EnterWorktree 必问且权限规则压不住这道问【官】；worktree 里点下的「不再询问」放行规则写回主 checkout、跨隔间生效、目录删了规则还在【官】（worktrees）。

**main 轨演进注记（@ 0dcafa2a）**：拆除收归宿主（`remove_worktree` 不进任何工具表——能开隔间的手不给它拆隔间的权）；创建前十二项全量前置校验（任务须 pending 且无主等）；部分失败不删 Git 数据、逐项列残留请人工处置；租约每次重验（目录与记录逐字节一致）。

> [!IMPORTANT] **实景**
> `s18_worktree_isolation/code.py @ 67a9126`（remove 守卫摘引，锚点 229–250）
>
> ```python
> files, commits = _count_worktree_changes(name)
> if files > 0 or commits > 0:
>     return (f"Worktree '{name}' has {files} uncommitted file(s) "
>             f"and {commits} unpushed commit(s). "
>             "Use discard_changes=true to force removal, "
>             "or keep_worktree to preserve for review.")
> ...
> run_git(["worktree", "remove", "--force", ...])   # discard 强删

**口播落点**：各干各的目录：任务管目标，worktree 管地盘，一根 ID 绳子拴住两样——不过这是教学版的绑法，产品里这两件是分开的。

## 7. M6 · 标准插口：MCP（s19《MCP Plugin》）

> [!TIP] **类比**
> 标准插口上外接别人家的机器：接上就进同一个转接号码簿，名字统一重起。但外接机器递来的自我介绍——说自己是只读的——在门禁那里一句都不算数，放行与否只看工坊自己的登记表。

**不变式一 · 工具池每轮重装。** 连接发现新服务后，装配函数在主循环**每一轮之内**把内置工具与所有已连外接工具合并成单池——接上新服务，**下一轮**工具池自然含新工具，循环本身一行不改；当轮检测到连接动作还会立即重建【一】。官方殊途同归：服务器发 `list_changed` 通知即可动态增删工具、免断开重连——目标一致（动态工具面不改循环），机制不同（通知驱动 vs 每轮重装）【官】（mcp §动态发现）。

**不变式二 · 命名空间加归一化。** 外接工具名为 `mcp__{服务名}__{工具名}`，两段**各自**过归一化——字母表之外的字符统一替换为下划线【一】；【三】产品同规则，官方文档化为三段式全名（多出 plugin 一段）、权限规则与工具检索都用全名【官】（mcp §工具命名）。

**不变式三 · 缓存服从工具池的动态性（三层口径）。** 站点轨这一章**主动去掉**了前面攒了九章的提示缓存——README 自陈取舍：缓存里的工具列表是旧的、会让模型调不到新工具，代价是多花序列化时间【二】；【三】产品**保留**缓存，做法是把全局缓存断点放在最后一个内置工具之后——正因如此，内置与外接必须**分开排序而不能混排**【三】；main 轨则全仓无任何缓存标记【一】。真正的机制不是「取消缓存」，而是**把会变的排在不会变的后面、断点卡在中间**——顺序纪律在五层里第三次登场。

**「自我介绍不算数」的证据要摆四层。** ①站点轨 s19：工具描述带 (readOnly)/(destructive) 文本标注，**仅是文本、不拦截**——教学版自陈真实产品用结构化标注让权限系统判断【一】【二】；②终点站 s20：权限是分发前的 PreToolUse hook，破坏性外接工具（`mcp__*deploy*`）需交互确认【一】；③【三】：产品的权限系统让工具声明参与判定；④【官】：组织级工具控制 ask/blocked 两档，blocked 的工具**在模型可见之前**就从工具列表滤掉（mcp §组织 connector 工具控制）；项目级 `.mcp.json` 同样先问后用【官】（mcp §.mcp.json）。四层并列，别只引其中任何一层。

**main 轨演进注记（@ 0dcafa2a，main 轨 s14_mcp_plugin）**：归一化**撞名即中止装配**——维护来源表，外接撞外接或撞内置直接抛错、错误串点名冲突双方（归一化会把不同名字压成同一个名字，碰撞检测是它必须配套的后半句）；宿主侧「（服务，工具）→ 放行/需确认」硬策略表、查不到默认需确认。

## 8. M7 · 传送带：机制很多，循环一个（s20《Comprehensive》）

> [!TIP] **类比**
> 班组搭起来了、隔间隔好了、外接机器插上了——可车间中央那条传送带还是原来那一条，一步没改。新机制全都在它边上找了个挂点。

终点站不发明新机制，把前面全部机制放回同一个可运行的 `while True`。它的核心五步循环（README 结尾原样）：

```python
while True:
    response = LLM(messages, tools)
    if not has_tool_use(response.content):
        return
    results = execute_tools(response.content)
    messages.append(tool_results)
```

**不变式一 · 续轮判据看内容块。** 循环是否继续不信任 stop_reason，以响应中**实际出现的 tool_use 块**为信号；代码注释自陈 "Do not rely on stop_reason alone"【一】。（CC 同口径为课程转述，非源码定位。）

**不变式二 · 多 Agent 机制只以两种身份入场。** 一是**注入的消息**（收件格、后台完成、定时到点），二是**池子里的工具**（生成队友、协议、隔间、外接服务）——循环体从头到尾没有为「多 Agent」写过一支分支；README 用一张十二行的组件位置表把每个机制钉到循环的具体环节【一】【二】。

**不变式三 · 权限是循环分发前的 hook，不是工具内部的 if。** deny 名单直接拒、破坏性命令交互确认、路径越界确认、破坏性外接工具确认——权限不写死在工具执行行里【一】（名单制的结构性弱点见第 12 节）。

**不变式四 · 两层计划并存。** 会话内轻量待办防单个师傅漂移（数轮未动工序卡就插一条提醒）；跨会话、可依赖、可认领的任务文件支撑班组【一】【二】。

**不变式五 · 计划门在终点站是真门。** 提交计划后队友停止一切模型与工具步骤、等待期只轮询协议回复、同一响应里后续 tool_use 块被忽略——s16 那句「不是代码级门」的自陈，到这一版被代码推翻【一】（门的完整三拍见第 4 节）。

**其余机制归位**：压缩管线、错误恢复、后台任务、定时调度、记忆、技能目录按需加载——机制本体属前面各维度，本层只取「都挂在同一条循环的位置表」这一总括事实【二】。副台（一次性、五件工具、三十轮上限、系统提示明写不许再生成）与队友（八件工具、最近二十条消息窗口）在同一循环里各就各位（参数见对应集 notes）【一】。

**官方没有对应页。** 轨 C 四页（agent-teams / sub-agents / mcp / worktrees）按功能切分产品能力，**无「总括循环」专页**——「机制很多，循环一个」是课程的教学收束观点【二】，不冒充官方口径。

**main 轨演进注记（@ 0dcafa2a，main 轨 s15_integrated_harness）**：同构扩写（对站点轨 s20 diff 218 行）＋新压缩管线回灌；执行序里定时消费并入「权威请求」字段、压缩后目标不丢。

**口播落点**：机制很多，循环一个：队友、协议、隔间、插件，全都以「一条注入的消息」或「一个池子里的工具」的身份，挂在同一条循环上。

## 9. 教学版、演进版与产品版的距离

先分三轨再下笔：**站点轨**（机制主体）自陈的缺口清单——认领无文件锁、无环检测、读删两步竞态、s16 无执行门控、权限冒泡省略、MCP 无鉴权；**main 轨**（演进注记）把其中一半补成了更严的机制（双层锁、环检测、真门、人走活退回）；**官方产品**走了第三条路。结构性结论四条：

1. **教学版能省略，是因为它不需要活的产品环境。** 单进程单用户，所以收件格敢留两步竞态；宿主自备 mock 服务端，所以 MCP 完全无鉴权。产品的对应物（文件锁、OAuth、审批冒泡【官】）都是在多用户、多会话、真网络里才被迫长出来的。
2. **main 与产品补的不是同一副药。** 同一个安全目标，main 往「更严的机制」补（把门做真、把锁加厚），产品往「自动化与移层」走（门到达即自动批、拦截移给权限提示与生命周期 hooks【官】）。读演进时别把 main 当产品路线图。
3. **有两处教学版不是产品的简化，而是理想化。** 其一，任务—隔间硬绑定：教学版绑得很硬、fail-closed，产品没有绑定、靠模型理解关联——【三】源码与官方零记载双重佐证。其二（反向），隔离强度：教学版只是换目录，产品已是不可关闭的四项硬阻断【官】。两处都极易被误当成产品行为——前者机制讲得越清楚误读越顺，后者方向相反、同样单向讲不得。
4. **「缓存被取消」是教案取舍，不是机制必然。** 产品的解法（内置在前、外接在后、断点卡中间【三】）说明顺序纪律与缓存可以并存；站点那一版去掉缓存，是因为它不想在这一章同时教排序纪律。

**口播落点**（轨 C 校准总句）：课程教的是一间教室里的教学版；官方文档说，产品已经把这间教室改成了带门禁的厂房——两句都要讲。

## 12. 批判性边界

全局五条跨章成立，见[总纲 · 全局批判性边界](./170-claude-code-harness-overview.md)；以下五条是这一层独有的。

1. **fail-closed 撞上「人忘标完成」就是活锁。** 机制把「前提坏了」挡得越死，越依赖每个队友都记得结单；官方把这条列为产品已知限制——任务卡住时须人工改状态或让 Lead 提醒【官】。机制自洽与运行时纪律是两件事，材料只证明了前者。
2. **门禁是名单制，不是能力制。** s20 的权限 hook 拦的是字面清单（deny 名单、破坏性子串、`mcp__*deploy*` 模式），main 分发层拦的是三个字面工具名——任何日后新增的修改型工具，只要不叫这些名字就自动绕过。官方以生命周期 hooks（TeammateIdle/TaskCreated/TaskCompleted，exit 2）实现质量门，事件驱动天然避开名单制绕过【官】——这是「门是真的」的另一条更稳的路线。
3. **并发自洽从未被并发验证。** 站点轨自陈两处竞态（认领无锁、读删两步），全靠 owner 检查挡「最明显的后写覆盖」；main 补了锁、产品有文件锁【官】，但课程材料内没有任何并发压测用例——「认领原子」这类不变式只被代码结构保证，未被实验证明。
4. **【三】不可独立复核，且部分与官方对不上。** 十五种消息类型、28 小时超时、缓存断点位置、结构化标注参与判定，都无法在官方文档验证（官方页无记载）；方向能对上的（OAuth、命名、文件锁）可作旁证，对不上的只能挂「官方未述」。引用永远带归属，不得作为产品现状的最终依据。
5. **教学版有一处是产品的理想化，极易被误读成产品行为。** 任务—隔间硬绑定加 fail-closed（绑定坏了拒绝干活），上游产品没有绑定、靠模型理解关联，【三】源码与官方零记载双重佐证。机制写得越漂亮，这条边界越需要在引用时显式声明——同章反向的一条（隔离强度产品反超）同理，单向讲任何一侧都会失真。

## 14. 验收问答

1. **为什么「发现」与「认领」必须分成两步？** 扫描只产生某一时刻的快照候选，多个队友可以同时看见同一张活；认领是改归属的动作，必须「检查—写」连贯完成。站点轨用 owner 检查挡住最明显的后写覆盖、并自陈仍有竞态；main 演进把整个读—判—写收进双层锁；官方产品用文件锁防同类竞争【官】。三个口径同一教训：**看板人人能看，撕卡只能一个人撕**。
2. **计划审批这道门，为什么课程越做越真、产品却自动化了？** 课程主线把审批当队友协商语义的核心：s16 教握手但自陈「不是代码级门」（靠模型自觉等待），s20 改成真门（未批不跑模型、同响应后续 tool_use 忽略），main 下沉到分发层拦工具。产品选了第三条路：请求到达即自动批准、不经 Lead 审阅，安全责任移给权限提示与生命周期 hooks【官】。本质是同一安全目标在「模型间协议」与「宿主强制」两层的归属之争——自动批准换来的，是计划内容不再进入人类决策回路，这个损失权限层补不回来。
3. **「有依赖不等于不合格」——依赖语义怎么判？** 候选资格＝pending＋无主＋每条依赖都完成；判的是「被没完成的依赖挡着」，不是「没有依赖」，缺失的依赖同样判阻塞。反过来，官方自陈「队友忘标完成会卡住依赖方」【官】——fail-closed 挡得住坏前提，挡不住上游忘了结单：那是活锁，要人来解。
4. **说「教学版比生产版更严」，指哪一处、为什么危险？** 任务与隔间的绑定：教学实现是硬绑定（任务带 worktree 字段、认领即切目录、绑定坏了拒绝干活），站点自陈是教学简化，【三】产品的持久化会话没有任务标识、官方两页零记载。危险在于它是「理想化」而非「简化」——机制讲得越自洽，读者越容易当成产品行为照搬。同章还有反向的一条：产品的隔离是四项不可关闭的硬阻断【官】，教学版只是换目录——教学与产品的差是**双向**的。
5. **队友的身份为什么会被压缩吃掉、又该怎么救？** 站点轨把身份写进消息流，压缩后消息过短就重插一块补救——补救是放错位置的供词。main 演进给出正解：system 提示是每次模型调用单独传的参数，从不进消息数组，压缩管线碰不到它。提炼成不变式：**身份若不放进会被压缩的地方，就不需要事后补救**。
