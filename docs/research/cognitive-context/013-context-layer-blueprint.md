## 0. 判定面总则：怎么读、怎么证伪这份蓝图

本章先把判定纪律立起来，再让后续各章的设计接受它的约束：证据按什么分级、数字带什么限定、机制到什么程度才算存在、失效按什么协议入账——全篇每个承重论断（表格行与含数字的断言句）都据此挂徽挂锚，读者可逐条复核或推翻。

### 0.1 三级徽：证据按出处分级

徽只有一个职责：标明证据从谁手里来。分级判据承 [011](./011-horizon-context.md) §5 的读表纪律（谁测的、厂商自报 vs 第三方独立），三级徽记号（实线/虚线/实心）为本文新立：

| 徽 | 判据 | 本文典型来源 | 读法 |
| :-- | :-- | :-- | :-- |
| 实线 | 第三方实测/中立锚——与论断无利害关系的第三方测量或学术实证 | arXiv 四篇＋FinanceBench 论文；Anthropic 独立复测 21%（011 §1[5]；Snowflake 转述 Anthropic——测量者无利害、按规则 3 例外承实线并注转述）；Classmethod 咨询方实测（011 §2 M6[25]） | 可承重，仍须带条件限定 |
| 虚线 | 官方自报（厂商利害）——产品方、品类卖方、竞对、投资方的自报数字、叙事例与经验观察，无论一手二手 | Snowflake 增益基准（011 §5）；Redis 调研页；a16z 构造例；typedef 判词（竞对利害已标） | 可引用，限定必须随行；利害方为竞对时注明 |

四条适用规则：

1. **挂徽对象是承重论断**：表格每行、含数字的断言句必挂；散文里的例证数字随所属论断，不单独重复标。
2. 徽标出处与利害，不标真伪：虚线数字可用，但「谁测的、什么条件」必须随行；实线也会过期（§0.4）。
3. 转引一手研究按虚线处理并注「转引」；一手核验通过后升为实线（例外：测量者为与论断无利害的第三方、且转述限定随行者，可承实线并注「转述」——21% 即此类）——本轮已闭合五组高频转引数字（46/19＝工具面饱和实验、−39%＝多轮对话分片退化、99.6/54.3＝长会话关键信息保留、+15.8%~243.7%＝记忆个性化攻击面、19/50/85＝检索实现方式三档），完整处置表在 §13；不可升级项（如 Redis n=1000、Gartner 60% projection 口径）如实标注。
4. 徽与接线态（§0.5）是两套记号：徽回答「证据从谁手里来」，接线态回答「机制在本仓什么状态」，不得互相代用。Claude Code 范本证据按其四级分级（【一】【二】【三】【官】）引用，徽映射恒为虚线带归属（【官】=官方文档口径、课程实测=一手课程仓库、闭源分析=带归属的第三方分析）；仅本仓复跑的 lcc/090 原型产物为实心。

### 0.2 考卷三问：每个数字先过三关
任何验收数字入文，先答三问：谁测的、什么条件、截至何时。三问背后是一条已升为纪律的观察——失效量化是考卷的函数，跨考卷数字不可比、不可平均：同一 GPT-4-Turbo 在 FinanceBench 上按检索设置三档摆动 19%→50%→85%（实线，三档条件与逐条限定见 §7.1）；裸问企业题的准确率随考卷难度在 25%（Snowflake 内测，虚线）与 64.5%（dbt 全题集裸 text-to-SQL，品类卖方，虚线）之间摆动（011 §7.2 争议 2）。增益端数字尤其如此——86.3% 一类的厂商增益基准全部虚线、无一第三方复现（011 §5）。高频转引数字的逐条限定见 §1 表后警示与 §13 转引处置表。
### 0.3 失败形态一等公民

两条纪律构成本文的验收观。其一，失败形态优先：系统可信度不取决于「对的时候多对」，取决于「错的时候长什么样」——可见失败（显式拒答、blocked、显式缺口）恒优于不可见错误（自信错数、表面合规放行），验收判据必须先回答「错的时候长什么样」，再回答「对的时候多对」。其二，反事实存在性：机制存在性的证明不是「有这个组件」，而是「拆掉它有具体、可复现的坏法」——[011](./011-horizon-context.md) §6 的十次破坏实验（D1–D10，2026-10-09 复跑全绿，§13 摘录逐字）是该纪律的执行样本；没有对应破坏实验支撑的机制宣称，一律按装饰性处理。判装饰性治理只问一句「绕开这个点会发生什么」——答得出「什么都拦不住」的，策略文本写得再全也不承重（执行点律：强制力来自求值点而非定义点，§5 权威轴展开）。由此派生调试纪律：**Agent 失败先查上下文供给链，再查模型**（context-first debugging）——失效登记簿的行号比模型参数更可能定位问题。

### 0.5 接线三态：存在、接线、在线

「代码存在」不等于「机制在工作」。本文对每个机制区分三态：存在——设计物或代码在场（函数有定义、目录在、表建了），最弱判定，只证明有人写过；接线——进入生产调用路径（调用方非零、真实装配面持有）；在线——端到端回路在生产路径上可观测地工作。回路类机制（巩固、进化、自纠）的在线判定另有一条硬标准：触发器、消费者、水位三件都在生产路径上，缺任一即回路不存在（复利三在线律，§8 复利轴展开）。判例即 ISSUE-195：巩固函数有定义、有测试（存在），但生产调用方为零、队列表只入队无消费者、水位列全仓零命中——三件缺两件，回路不存在。全篇执法方式：§1 登记簿每行带接线态列（其取值——未启/断/部分/接线/未立/在册/存在·非权限契约等——是三态在本仓语境下的细分：未启/未立/存在·非权限契约＝存在或设计位、断/部分＝接线不完整、接线/在册＝接线；在线仅在回路类机制由三在线律判定）；§12 映射表以「执行点为空即接线态断＋判定列」承载同等信息；销账只认「接线/在线」证据，不认「存在」。判定符号另有一套：✅ 对齐 / 🔶 部分或方案 / ⏸ 暂缓带触发（用于 §12 映射表与各轴实例化表），与接线三态分属两个维度、不得互代。

## 2. 第一性对象与理论锚

§1 的登记簿把失效形态列成了总账；本章往回追一步，回答「这些失效为什么集中爆发」——因为它们共享同一个第一性对象：Agent 运行时上下文。本章依次给出它的问题定义（三症状三病灶）、形式定义（Context Engineering 2.0 一手锚）、产品侧定义（a16z 与 Atlan）与分析单元（每轮装配事务），并以研究范围收束。§3 的三面蓝图在这个对象之上展开。

### 2.1 为什么需要：三症状与三病灶

（症状与病灶为 [011](./011-horizon-context.md) §1 冻结口径；徽义见 §0。）

**症状一：同一个问题，两个数。** 销售负责人问 AI「Q3 收入」，答 $14.2M；CFO 同一天问同一份数据，答 $12.8M（虚线，Snowflake 官方博客开场案例）。指标定义散落在 BI 模型、报表公式、甚至手写进 prompt 的 instruction——各团队各抄一份、各改各的。

**症状二：裸问业务问题，大面积答错。** 不给业务上下文、让 Agent 直接对裸库提问：Snowflake 内部产品分析题（需跨表 join、指标口径、过滤惯例）准确率约 25%（虚线）；Snowflake 并转述 Anthropic 独立测得 21%（实线，转述口径、非一手发表）——两个口径量级互证。Spider 2.0 企业工作流基准（632 题、千列级库、百行 SQL）上 GPT-4o 仅 10.1%（实线，论文口径）：模型会写 SQL，但不知道 `amt_ttl_pre_dsc` 列存的是「折前总金额」、不知道收入该先聚后连、不知道周末快照不能跨天相加。

**症状三：门禁管不住新的提问者。** 访问策略按「人来查」设计；Agent 拿着用户的全权凭证进来，默认继承一切——包括生产库写权限和 ACCOUNTADMIN 级角色（虚线，Snowflake 官方文档）。

三个症状往下挖是三个**不可自愈的病灶**：口径散落——「收入是什么」没有唯一权威定义处，每个消费者自带一份副本，漂移只是时间问题；执行算错——join 顺序、聚合方式、粒度对齐任何一环走样，合法 SQL 照样产出业务上的错数（fan trap、平均的平均、distinct 双计、半可加跨天相加）；门禁穿透——策略长在应用层或 BI 层，绕开这个应用就等于绕开策略，数据一导出、口径一复制，保护即失效。§1 登记簿的九簇是这三病灶在供给、运行时、接线等更多失效面上的展开；本蓝图全部结构都按「哪条轴、哪一段堵住哪条失效」组织。

失效不全是技术问题，组织面早有先声：MIT《State of AI in Business 2025》的结论——「most fail due to brittle workflows, lack of contextual learning, and misalignment with day-to-day operations」——经 a16z 转述（虚线，转引——原报告未直接核读；MIT 中立机构，引文以 a16z 页为准）；Redis 调查口径：97% 认为上下文决定 AI 成败、只有 4% 建成了相应系统（虚线；n=1000 在报告落地页与公开文本零披露、方法论未公开——引用永久全限定）。ownership 真空与组织运营失效的完整簇见 §11。

### 2.2 形式锚：上下文与上下文工程的定义

（一手锚：arXiv:2510.26493 v1，2025-10-30 提交、2026-10-09 快照为唯一版本——实线。010 的转述仅作对照，不入锚。）

Context Engineering 2.0 给出一组可用符号推演的定义。定义 1（实体与表征）：实体空间 ℰ、表征信息空间 ℱ，表征函数 Char: ℰ→𝒫(ℱ)（式 1）——Char(e) 返回刻画实体 e 的信息集。定义 3（上下文）：对一次用户-应用交互，C = ⋃_{e∈E_rel} Char(e)（式 2），其中 E_rel⊆ℰ 是与该次交互被视为相关的实体集合；论文明确式 2 正是 Dey 2001 经典定义（「任何可用来刻画相关实体情况的信息」）的形式化。定义 4（上下文工程）：对上下文采集、存储、管理与使用的系统化设计与优化，以提升机器理解与任务表现；形式化为 CE: (C,𝒯)→f_context（式 3），f_context(C)=ℱ(φ₁,φ₂,…,φₙ)(C)（式 4）——𝒯 为目标任务域，ℱ 为算子 φᵢ 的组合函数。

论文对 Context Engineering 2.0 的操作集给出 may-include 清单（原文自标非穷举枚举）：①采集 ②存储管理 ③一致可互操作表示 ④多模态处理 ⑤整合复用过去上下文（"self-baking"，原文引号）⑥选取最相关元素 ⑦跨代理/系统共享 ⑧依反馈动态适配。

这组定义给本蓝图三样东西。其一，式 2 把 instruction、memory、knowledge、tools+skills、session 装进同一个定义域——它们都是某类实体（用户、应用、环境、工具、记忆模块）的表征，不必按「数据类型」另立顶层分类。其二，𝒯 进入定义使「上下文的好坏」成为任务相对量：同一段内容对 A 任务是信号、对 B 任务是噪声（本蓝图读法）——这是 §6 预算纪律的形式化出处。其三，八算子是覆盖度核对表：§3.5 的投影表覆盖其中六项（存储/表示→资产、选取/压缩→装配、采集候选面→检索、self-baking/适配→复利），多模态与跨系统共享两项跨轴未单列——核对结论是「主类操作有落位」，非完备证明（清单原文自标 may-include 非穷举）。工程侧口径（Anthropic 官方定义，虚线）与形式化定义说的是同一件事：上下文＝「从 LLM 采样时所纳入的 token 集合」，上下文工程＝「在推理期间策划并维护最优 token 集合的一组策略」——形式化的 C 在工程口径里就是「本轮窗口内容」，这正是下一节的分析单元。

### 2.3 产品侧定义：a16z 三动词与 Atlan 五层

a16z 定名文（投资人观点文，利害已标；截至 2026-10-09 无修订、无续篇）给出 context layer 的三动词链定义，逐字：

> Tie together all of an enterprise's messy data, add a contextual layer on top that helps agents understand business logic, and package it such that the context can be supplied to agents.

接起来（tie together）、加一层（add）、打包供给（package）。末环「供给封装」在二手转述里最常被丢掉，而它恰恰把 context layer 与「又一本数据字典」区分开。同文两处边界声明随行：其一，**两半声明**——"This piece will primarily focus on data context that ties together traditional systems of record. An equally important and overlapping opportunity is also capturing an organization's decisions and workflow logic…"（本文只写打通传统记录系统的 data context 半边；捕获组织决策与工作流逻辑的另一半同等重要、交叠、未展开）。其二，context ⊃ semantic——现代上下文层是语义层的超集：指标定义可硬编码，但 Agent 自主性还需要 canonical entities、identity resolution、tribal knowledge 指令与治理指引（a16z 原文列举）。命名未收敛（context OS / context engine / contextual data layer / ontology 并存，a16z 自认概念同一）。本蓝图立场：术语收 a16z 宽定义；工程落位不按任何产品分类法，而按 §3 三面五轴；a16z 留白的另一半——Agent 运行时上下文——正是本文的第一性对象（此迁移为蓝图立场，非 a16z 原义）。

Atlan 官方 guide 给出五层口径（厂商营销内容、导向自家产品，利害已标；截至 2026-10-09 五层口径现行、页面仍在活跃维护）：system context / session context / memory / artifacts / on-demand retrieval。其中 artifacts 层的纪律逐字：

> External files and objects that can't be directly copied over with the prompt, but are essential for context — design files, data models, architecture diagrams, etc. Artifacts are referenced at runtime, not copied, and must be reliably accessible when the agent needs them.

「运行时引用、不拷贝、需时可靠可达」被本蓝图采纳并泛化为 G5 指针不副本法则（§9）。五层为何不作顶层，在 §3.5 投影表中处理：名词（memory、artifacts）与副词（on-demand）并列、权威与复利缺位——不是正交分解，降为装配轴的时序投影。

### 2.4 分析单元：每轮装配事务

把对象与定义落到可验收的单元，本蓝图取**每轮装配事务**：从「本轮输入到达」到「上下文窗口内容定型」之间发生的全部取数、过滤、排序、分段与预算分配。用 §2.2 的语言说：式 4 的 f_context(C)=ℱ(φ₁..φₙ)(C) 每被实调用一次，就是一次装配事务（式 3 的 CE:(C,𝒯)→f_context 是映射关系而非事件；「一次求值＝一个事务」是本文的分析单元约定）。

三个互相独立的证据指向同一结论——正确性与安全性的最终防线在每次装配时求值，而非入库一次定终身（入库门管结构与身份、装配门管当下行为，两道独立生效，见 G2）：

- M1 查询期重算：语义视图不存任何算好的数字，问一次按定义现算一次（011 §2 M1，冻结）；反面的结构性理由是存量必陈旧——今天算对的数，明天新数据一到即成旧账，且没有任何机制提醒它旧了。
- Claude Code 每轮重装配：工具面取自注册表、记忆段按运行时事实铺设、静/动分段与缓存前缀每轮重算——模型每轮「看见什么」由装配过程决定，不是模型自己说了算（170–175 转锚，证据分级见彼处）。
- 本仓实况：记忆注入的真实通道是 NegentropyPreloadMemoryTool——每轮以用户消息为检索词执行记忆检索并注入，挂载于 root agent 工具面（[`agents/tools/memory.py`](../../../apps/negentropy/src/negentropy/agents/tools/memory.py) :127、[`agents/agent.py`](../../../apps/negentropy/src/negentropy/agents/agent.py) :248，as-of b2fbb51f5，实心）；而设计上更完整的 ContextAssembler.assemble() 生产调用为 0（实心，as-of b2fbb51f5）——分析单元必须取实际发生的装配事务，不是设计文档里的装配函数。

由此三条推论：三症状全部发生在装配事务内部（错口径被装配进窗口、错证据被装配进窗口、越权数据被装配进窗口）；D1–D10 破坏实验（011 §6）大多是对装配事务的单点干预（D8 在 L1 摄取门、D6/D4/D10 落 L2 铸形段——段位对账见 §9.2）；§12 映射表以装配事务为对账口径。装配面实况的完整宿主更正（负发现＋正锚五挂点）由 §6 承载。

## 3. 总纲：三面蓝图

§2 立起了第一性对象与分析单元；本章给出组织全部设计的总纲。结构是三个互相独立的面——验收面（失效登记簿）、结构面（五条正交轴）、时间面（六段两环）：机制落在轴与轴的接缝上，失效落在段与段的转换上。本章同时完成两组投影：把业界既有分解（Horizon 四信号/Atlan 五层/CE2 三支柱等）与本文既有术语（三轴/五源/五层口诀/CGAVE——014/015/191 等下游文档沿用）一并对到三面——后者是下游改锚的依据。ADR 台账随之更新。

### 3.1 三面：各自回答一个问题

先看三面各自的载荷与承载章：

| 面 | 回答的问题 | 承载 | 组织方式 |
| :-- | :-- | :-- | :-- |
| 验收面 | 防住了什么坏法 | §1 登记簿 | 失效×证据锚×徽×堵住机制×验收判据×接线态六列，九簇组织 |
| 结构面 | 设计沿哪几条独立维度组织 | §4–§8 五轴 | 每轴有专属坏法与专属设计参数 |
| 时间面 | 对象一生怎么流动 | §9 六段两环＋G 法则 | 段＝单对象流转阶段；环＝错答案回流路径 |

读法：设计先问「防什么」、再问「怎么实现」。验收独立成面的直接收益，是登记簿可以跨结构修订长期存活——失效登记延续、结构轴可换，登记簿本身不动。结构与时间分成两面，因为它们是两种分解：轴是设计参数的稳态分类（换检索算法时五轴定义不变），段是单个对象的流转时序（一条 verified 问答对从沉淀到重验走完六段）；把两者压进同一套名词（用一套「层」同时当结构和流程），每个概念就得同时承担两种变化——§3.5 投影表里 Atlan 五层正是败在这里。

### 3.2 结构面：五轴与独立性

五轴一览（各轴设计细节在 §4–§8）：

- 资产轴 Asset（§4）：经营什么——受治理、可寻址、带权限的语境对象（definitions 四类、记忆、技能目录、KB、血缘边、verified 问答对、标签与策略对象）。
- 权威轴 Authority（§5）：真值在哪、执法点在哪、谁在问——SSOT 与引用不拷贝、执法点谱系（注册期门→装配期注册表→执行期引擎求值→编译期极端形态）、身份与权限天花板。
- 装配轴 Assembly（§6）：这一轮进窗什么、什么形态、什么顺序、花多少——时序四档（常驻/渐进披露/JIT/仅引用）、两级预算带、缓存感知分段、压缩四步。
- 检索轴 Retrieval Economics（§7）：候选从哪来、怎么排、怎么截——候选集性质、混合＋重排、VQR 路由、截断信噪闸门。
- 复利轴 Compounding（§8）：怎么随使用变好并守住不变量——巩固、冲突裁决、自供链、回滚。

独立性的可操作判据是「换 X 不动 Y」——变更影响面互不波及，而非名词差异。四例：

| 变更 | 不受影响 | 为什么 |
| :-- | :-- | :-- |
| 换检索算法/排序权重 | 权威：策略对象与求值点 | 权威以过滤器形态前置进候选流（检索面即治理面）；换的是过滤器之后的排序，不动「过滤是否发生」 |
| 换披露层级（常驻↔渐进↔JIT↔仅引用） | 资产：对象清单与 schema | 披露是装配时序属性；对象定义与注册门不变 |
| 移执法点（应用层→引擎层） | 检索：候选生成与排序 | 执法位置变、候选集不变——两件正交的事；旧式分层常把「过滤」与「排序」捆在同一层里一起改 |
| 加巩固环/进化环 | 装配：每轮装配事务 | 复利是异步回路（触发器/消费者/水位），装配是同步事务——失败形态不同（真值衰减 vs 本轮噪声）、守卫不同（裁决闸与水位 vs 预算与顺序不变量） |

五轴与旧五层名称相近（资产↔对象、权威↔治理、装配↔激活、检索↔目录、复利↔富化），但成立依据不是改名，而是**每条轴有自己专属的坏法**——拆掉它有具体、可复现的退化，别的轴替补不了：

| 轴 | 专属坏法 | 证据 |
| :-- | :-- | :-- |
| 资产 | 非法结构静默入库（垃圾定义进运行时） | D6（实心，011 §6） |
| 权威 | 拆执行层即泄露；快照式权限留越权窗口；虚构血缘边入账 | D5 / D9 / D8（实心，011 §6） |
| 装配 | tool_use/tool_result 配对拆裂；缓存边界画错（易失内容进稳定前缀） | 170–175 转锚（虚线，Anthropic 口径、证据分级见彼处） |
| 检索 | 中文关键词腿零召回（english tsvector 整段单 token） | ISSUE-196 本仓实测（实心，as-of b2fbb51f5） |
| 复利 | 供给链断在最后一环：已分类未绑策略仍明文出楼（D10，实心）；巩固环零生产调用（三在线律判例） | D10（实心，011 §6）；ISSUE-195（实心，wf3 as-of b2fbb51f5） |

> [!WARNING] **正交不是无关**：「五轴独立定义」容易被读成「五轴互不相干」。预算是装配与检索共享的稀缺约束（同一枚 token 从进入候选到进窗消耗同一预算）；权威以过滤器形态组合进检索（检索面即治理面）与装配（enabled_tools 取自注册表）。轴的定义各自独立，接缝正是机制所在（§3.3）——把正交读成孤立，会漏掉全部跨轴机制的验收位。

### 3.3 机制＝接缝组合

Horizon 七个机制（M1–M7 的内容与实验键 D1–D10 冻结于 [011](./011-horizon-context.md)，本表只标轴归属、不重定义）没有一个是「单层功能」：每个机制是一组轴上的组合（轴向量）加一组验收判据。这也是 §12 映射表的形态——每行标轴组合，而非「层×机制」的功能清单行。

| 机制 | 轴向量 | 接缝理由（一句） |
| :-- | :-- | :-- |
| M1 语义视图 | 资产×权威×装配 | 定义铸成五段式对象（资产）；全公司唯一权威定义＋注册期结构校验门（权威）；查询期现算、不存成数（装配）——口径打架由资产/权威维（定义唯一＋注册期门）堵住、执行算错由装配维（查询期重算）堵住 |
| M2 行列级策略 | 权威 | 四类策略的全部强制力来自「查询执行那一刻由引擎求值」；策略文本只是登记在库的 schema 对象，拆掉求值点策略即失效（D5） |
| M3 语义级治理 | 权威×检索 | 检索面即治理面：PRIVATE 资产在候选集层被过滤（检索，体验），执法点在引擎（权威，底线）——双层防线横跨两轴 |
| M4 VQR 验证锚定 | 检索×复利 | 可信来自候选集性质（全人工核验、错误面窄——检索经济学的核心判据）；题库沉淀、优化回路与随口径重验是「越用越准」的复利回路 |
| M5 列级血缘 | 资产×权威 | 血缘边是登记在账本里的经营对象（资产）；三道闸与执行自动沉淀的入账纪律是真值门（权威）；只记「谁喂谁」、不判「这么算是否合法」，故不跨验证（§10） |
| M6 Agent Identity | 权威 | 入口识别、归因审计、权限天花板∩实时求值——三个问题都只在求值点回答；天花板只减不增、会话期锁死（D9） |
| M7 分类标签 | 复利×权威 | 分类→一次性映射→tag-based 策略是自动供给回路：新列自动纳管、覆盖面随使用扩张（复利）；映射闸把机器判断与组织规则显式分开（权威，G3 裁决权不自动化的供给面实例） |

读法：两个单轴机制（M2/M6）都落在权威轴——治理执法不依赖其余四轴即可成立；没有「全轴机制」——不存在必须五轴齐动才能落地的设计，与 §3.2 独立性矩阵互为印证。反过来，落不进任何轴组合的「功能」不是机制而是解释装置——按机构称谓组织治理叙事即属此类。

### 3.4 时间面：六段两环与 G 法则（概览）

时间面按单对象的一生组织六段：L1 采集纳管（出身有出处）→ L2 铸形裁决（机器发现、人类定规）→ L3 装配执法（每轮重装、实时求值、指针不副本）→ L4 应答锚定（三条出路、无静默瞎猜）→ L5 沉淀回灌（短期→长期的工程化）→ L6 衰减退役（死亡段）。两个环一等化：验证环（L4 产物回流对账）与进化环（L5→L2 回写）。Snowflake 三阶段（Collect→Enrich→Activate）与 CGAVE 流水线叙事的共同结构缺口是单程无环：错答案回不到定义层，供给缺口只能等下一次人工重建——三阶段可对位 L1/L2/L3+L4，两环是显式补齐。段间转换由 G1–G7 落位法则钉住：执法点绑定、两道独立保险、裁决权不自动化、治理-验证分落位、指针不副本、死要有葬礼、闭环可观测（判据句详 §9）。

时间本身是嵌套的：轮内（压缩、可恢复占位）⊂ 会话内（分段、缓存前缀）⊂ 跨会话（巩固、复利）⊂ 组织级（口径治理）；Claude Code 五层依赖链（执行/规划/记忆/时机/协作）是这套嵌套尺度上已验证的可对位结构（170–175）。本节只立命名与总纲，段级入口/出口判据与「拆掉这段转换坏什么」的逐段对账在 §9。

## 4. 资产轴（Asset）：语境资产清单与注册门

| 标签与策略对象 | 系统标签 → 治理标签一次性映射 → tag-based 策略 | 011 M2/M7 · 实验键 D10 | ⏸ 无分类策略链 |

读法：第三列是每类资产的机制载荷锚——M1–M7、D1–D10 等稳定键的定义都在 011（冻结），本文只引用不重定义；第四列的 ✅/🔶/⏸ 判定符号图例见 §0.5 末（与接线三态分属两个维度），全部为实心复算口径。血缘边不单独设检索外的轴：它是资产内容 + 权威真值门（D8 三道闸）+ 事后回溯的组合，升轴会双计。

**ADR-5（投影注记）**：五源分类法（instruction / memory / knowledge / tools+skills / session）按其原定义沿用，在新结构中为上表的子集投影——instruction→定义对象与指令版本、memory→记忆、knowledge→KB/KG、tools+skills→技能目录与工具定义、session→会话状态（五源中唯一自产新上下文的源，沉淀链在 §8/§9）；血缘边、verified 问答对、标签策略对象落在五源之外（同 §3.5 换算表）。「每源有独立信任信号与治理面」的原则不变；信号归一落 §7，换算总表落 §3。

三条设计纪律随之确定。其一，**引用不拷贝**：资产在运行时被引用而非复制进各消费端——Atlan 对 artifacts 层的口径是外部对象「运行时引用而非拷贝、须在需要时可靠可达」（虚线，厂商 guide，S7b），S6 的轻量引用路径（大块信息存于外部、窗口内只留标识符按需取回）与之同构；这与 ADR-1（§4.5）互为表里。其二，资产自述充分性：描述是检索精度的第一要素，LLM 推不出专有术语（011 §6 生产护栏表，虚线·官方 guideline），synonyms 与 instructions 因此是受治理的字段面。登记有纪律——无别名即检索面隐形，C4 实测推出：缺 synonym 时正确口径 top1 落败（推论标注）。使用有克制——前沿模型下 synonym 增益小、白耗 token，自动生成的常降质（官方指南，护栏行见 §13.4；字段纪律详 §4.2）。其三，M1 双不变量在五轴上的落位要拆开：声明半边的口径单点属本轴（资产：定义对象唯一），其注册期校验门的求值属权威轴（§3.3 同判）；执行半边（查询期重算、物化 staleness 纪律）属装配轴（§6）——机制跨轴的接缝组合总表见 §3。

### 4.2 通用对象模型：字段即治理面

七类资产的公共形态可以写成一个对象模型，任何「Agent 推理所需的受治理含义」都按此铸形，格式对齐 Apache Ossie YAML（示意）。Ossie 截至 2026-07 已有 50+ 组织参与，携带是定义跨引擎移动的现实通道；但携带不等于别处被验证，官方导出桥还会静默丢 ASOF/RANGE 非等值关系——保真度边界详 [011 §3.3](./011-horizon-context.md)，虚线·官方生态口径。铸形如下：

```yaml
# 对齐 Apache Ossie YAML 风格示意
id: metrics/net_revenue
kind: metric                      # definition | metric | doc | skill | qa | policy
synonyms: [净收入, net sales]      # 召回别名是受治理上下文
spec: {metrics: [{name: net_revenue, agg: sum, expr: "gross*(1-discount)", non_additive_by: [day]}]}
instructions: "聚合先于 join；默认走 buyer 关系"   # 随定义分发的 agent 指令
verified_queries: [{question: "net revenue by month", verified_by: "data-team@…", verified_at: 2026-08-20}]
visibility: {level: public}       # public | private | roles
tags: {domain: finance, owner: data-platform}
provenance: {source: governed, authority: 1.0}    # governed | inferred | legacy
version: 12
```

三条字段纪律（继承旧文，锚随行）：① synonyms 必填意识——无别名即检索面隐形；② instructions 随对象走——指令随定义分发才能随定义治理，写死在 prompt 里等于在治理之外另立第二个口径源；③ verified Q&A 带溯源——谁核的、何时核的随对象携带。结构校验门同口径：非法结构（外键不指向键列、关系成环、指标缺聚合函数等，规则全集见 011 M1）在注册期被拒、不进运行时——实验键 D6 是这条纪律的反事实（§4.4）。

#### 4.2.1 Data Contract 五件套

数据类资产的契约由五件构成：schema + 质量阈值 + 语义（绑 canonical 实体）+ lineage + 访问策略；per-agent 授权在交付点执行。破坏性变更走弃用纪律，不许静默改口径。边界如实：目前没有结构性工具在推理时原生强制语义契约——契约的强制力只能落在权威轴执行点（§5）与装配轴路径（§6）上，Data Contract 本身是声明。

### 4.3 常驻记忆对象的设计取舍：Core Block 三问

记忆资产里最特殊的一类是常驻画像块（Core Block）——它每轮在场、直接影响窗口构成，其设计取舍必须先答三问（承接 [191](../agent-harness/191-hermes-agent-mapping-negentropy.md) M2，数字与锚原样继承；本仓侧 as-of b2fbb51f5 复核未变）：

1. **由谁写**——三条写入路径：Agent 自编辑（`core_block_replace` 工具，`updated_by="agent_self_edit"`）、管理端 REST、append 追加。开放 Agent 自编必须后置于写入防注入之后——「开放可自编的常驻记忆而没有写入扫描，等于给注入开一条常驻通道」（本仓 191 映射报告的判语，非 Hermes 原文；`core_block_replace` 当前零调用方，实心——as-of b2fbb51f5 全仓复验，调用仅在定义模块 `engine/tools/memory_tools.py:236` 内部）。
2. **上限多少**——两级预算：存储级单块 2048 token（`MAX_BLOCK_TOKENS = 2048`，[core_block_service.py](../../../apps/negentropy/src/negentropy/engine/adapters/postgres/core_block_service.py) `:36`；显式选位在普通段落 256 与 Letta 4000 之间，防单块主导窗口）+ 组装级记忆预算 30% 硬帽（`_DEFAULT_MEMORY_RATIO = 0.3`，[context_assembler.py](../../../apps/negentropy/src/negentropy/engine/adapters/postgres/context_assembler.py) 预算常量段）。
3. **写满怎么办**——按 token 比例 ×0.95 截断并标 `metadata.truncated` 留痕（core_block_service.py `:77-83`），不拒写、不静默。

两级预算 + 截断留痕合起来是「常驻内容不挤占检索内容」的可复用范式；衰减豁免锚见 [025 §5.1](../../concepts/subsystems/025-the-memory-system.md) λ 表（core=0.0 不衰减）。设计语境锚：`core_block_service.py` 设计取舍段、memory-integration.md §4。

### 4.4 注册门：结构校验的注册期防线

资产出生即过门。Horizon 侧的形态是语义视图五段式 DDL 过结构校验门（011 M1）；本仓的对应物是 definitions 的注册期 422 门——create 与 update 双路生效：解析/格式失败与领域校验失败抛 `DefinitionParseError`（[registry.py](../../../apps/negentropy/src/negentropy/agents/definitions/registry.py) `:30`；解析/格式 raise 点 `:129/:131/:133/:138/:140`，领域校验经 validator `:144`），API 层 `_parse_or_422` 映射为 HTTP 422 拒入库（[definitions_api.py](../../../apps/negentropy/src/negentropy/interface/definitions_api.py) `:75-80`，create `:192`、update `:246`；实心，as-of b2fbb51f5，wf3 §1）。反事实实测（实际运行日志，2026-10-09 `--selftest` 全绿重跑）：D6——拆结构校验门，非法 relationship（指向非键列）被拒入库（逐字摘录见 §13.3）。

注册期校验与运行期重算（§6）是两条可各自独立失效的底线，互不替代——只修一道的系统，另一道坏掉时静默出错（011 §7.1 规律 3；§9 以 G2 承接）。

注册门有一条它管不到的缝：它校验定义的结构，不校验上游的数据形态——上游 grain 已塌缩时，合法定义照样产出 477 对 48 的错数（虚线＋实心；完整因果链与 grain 契约验收位详 §10.1）。

> [!WARNING] **注册通过 ≠ 算得对**：422 门与结构校验保证「定义结构合法」（外键指向键列、关系无环、指标带聚合），不保证「定义在当前数据形态上算得对」。上游 grain 已塌缩时，合法定义照样产出 477 对 48 的错数；把「注册通过」读成正确性背书，会把 §10 的验证缺口误认为已闭合。grain 契约的独立验收位在 §10，不在注册门。

### 4.5 ADR-1：目录是引用层，不是第二存储

**ADR-1（保留）：Context Catalog 用 PostgreSQL VIEW 实现，不新建物理表。** 元数据已在 PG 内，新建物理表等于制造副本，两边各自演化即 Split-Brain；引用一律轻量指针；Horizon Catalog 本身也是元信息层（011 §4.1）。OpenViking 对照：`viking://` 的寻址语法可借鉴（scope 前缀推导类型、确定性 ID、位置即语义），但其副本式 AGFS 存储与 ADR-1 正面冲突——只取格式、不取存储（[015](./015-openviking-mapping-negentropy.md) 结论）。本仓实况（实心，as-of b2fbb51f5）：三视图（`context_catalog_unified` / `context_trust_signals` / `context_access_log`）至今未落地——迁移目录与主代码零命中（今日复验）；信任信号的归一设计落 §7，判定总表落 §12。

## 5. 权威轴（Authority）：执法点谱系、身份与供给面威胁模型

资产轴铸好了对象，权威轴决定这些对象在哪几个时点、被谁、以什么强度强制——真值在哪（SSOT 与引用不拷贝）、强制力在哪求值（执法点谱系）、谁在问（身份与权限天花板）。本章依次给出执法点谱系（§5.1）、双层防线与身份正交（§5.2）、实时求值法则的双实例（§5.3）、供给面威胁模型（§5.4）、记忆供给面的新威胁与写入端时序约束（§5.5）；本仓判定面统一 as-of b2fbb51f5（2026-10-09），外部状态截至 2026-10-09。

### 5.1 执法点谱系：强制力来自求值点

治理的强制力来自执行点，而非定义点——策略写在哪里不重要，**求值发生在哪里**才决定强制力（执行点律：[011 §7.1](./011-horizon-context.md) 规律 2）。由此得出本轴的第一个可操作判据（绕开测试）：看一个治理宣称，先问「绕开这个点会发生什么」；答得出「什么都拦不住」的，就是装饰性治理。按强制时点排开，执法点是一条四层谱系：

| 谱系层 | 强制发生在何时 | 机制锚与范本 | 本仓接线态（实心，as-of b2fbb51f5） |
| :-- | :-- | :-- | :-- |
| 注册期门 | 对象入库前，非法结构拒收 | 011 M1 声明半边 · 实验键 D6（§4.4） | ✅ definitions create/update 双路 422（registry.py `:129-144`：解析/格式 raise :129-140＋领域校验经 validator :144——与 §4.4 注册门同锚） |
| 装配期注册表 | 每轮装配时，可达性由挂载面决定 | Claude Code system prompt 按真实状态组装：`enabled_tools` 取自实际注册的工具表（[172](../agent-harness/172-claude-code-planning-coordination.md) §6，证据分级【一】·课程固定提交实测）；本仓 `TOOL_REGISTRY` 白名单 | ✅ 挂载面真实（[registry.py](../../../apps/negentropy/src/negentropy/agents/tools/registry.py) `:105`、[agent.py](../../../apps/negentropy/src/negentropy/agents/agent.py) `:248`）；🔶 高风险审批门 `should_request_approval` 非测试调用仅 2 处（ingest.py `:119`、paper.py `:343`），root `before_tool_callback` 仅遥测（agent.py `:239-240`）——清单内 10 个高危工具仅 2 个有拦截调用、其余 8 个与清单外工具同样裸奔（ISSUE-197 开放，wf3 §5） |
| 执行期引擎求值 | 查询/动作执行那一刻，引擎内生效 | 011 M2/M3 · 实验键 D5；M6 天花板查询期实时求值 | 🔶 检索层过滤在场（scoped∩accessible 交集机制已实装——主锚 [`hybrid_planner.py`](../../../apps/negentropy/src/negentropy/agents/tools/hybrid_planner.py) 模块头「权限红线」＋[`unified_search.py`](../../../apps/negentropy/src/negentropy/knowledge/retrieval/unified_search.py) 的 `accessible_corpus_ids`；集合来源的粗粒度限定见 §12.4 #5）；执行层出口守卫缺：`engine/context/` 目录不存在（wf3 §6） |
| 编译期极端形态 | 意图编译为执行计划时即失败 | Colrows：RBAC/ABAC/行列谓词在 compile time 求值——"unauthorized queries fail compilation, not in production"（虚线，S7d，治理语义层厂商博客、利害已标） | ⏸ 本仓非 SQL 编译栈，无对应物；路线之争（描述 vs 执行）入 §11 争议 1 |

读法：四层不是高下分级，而是强制时点从「对象出生」推进到「动作发生」的谱系——越靠后，绕过面越窄、强制越刚性；一个系统的权威面通常是多层叠加，单层都不足以闭合。同一谱系也能读出跨层接力的失效面：M7 供给链（分类扫描→一次性映射→tag-based 策略）横跨其中三层，映射关口是「机器判断 → 组织规则」之间唯一的人工裁决位；实验键 D10 实测映射置空的形态——已贴系统标签的列仍以明文出库，「发现→标记→执行」断在最后一环（011 M7，实心）。执法点绑定的落位法则由 §9 G1 承接。

### 5.2 双层防线与身份正交

执行期那一级内部还有一道双层结构：检索层过滤是体验（无权者不见 PRIVATE 对象），执行层拒绝是底线（必经 RBAC）——只把对象从检索结果里藏起来、执行层照样放行，是外挂式治理的标准失效形态（011 M3）。原型双通道实测（键＋结果值，逐字摘录见 §13.3）：C2——检索层对 intern 过滤 PRIVATE plan 建议、直闯执行层 AccessDenied（引擎是最后防线）；T5——引擎层 RBAC 经 MCP 通道仍生效（plan is a PRIVATE fact）。

T5 的价值在通道：它实测的是引擎层拒绝经 MCP 通道仍生效（工具列表层的 PRIVATE 过滤由 T2b 的语义覆盖——MCP 原型 tools/list 返回恒等四工具、无私有项可滤），换入口不换结果——执法点只有一个时，「绕开客户端」不构成绕开策略。

身份问题与可见性正交。`agent_type` 表达「用什么运行时形态装配」（构造期元数据），不表达「被允许做什么」（运行期权限）——本仓复验（实心，as-of b2fbb51f5）：[permissions.py](../../../apps/negentropy/src/negentropy/interface/permissions.py) 与 [permissions_api.py](../../../apps/negentropy/src/negentropy/interface/permissions_api.py) 全文零 `agent_type` 引用；权限的判定锚是 required_tools 集合差（skills 链：skills_api / skill_registry / skills_injector）+ owner/visibility 过滤（permissions.py `:74/:90-91`）+ TOOL_REGISTRY 白名单（registry.py `:105`）。把类型字段当权限捷径，等于绕开求值点另立权威面。边界的另一半是隔离：子代理的独立上下文隔离的是上下文，不是权限也不是副作用；worktree 不是安全沙箱（[170–175](../agent-harness/170-claude-code-harness-overview.md)）。

### 5.3 权限天花板与实时求值法则：同一法则的两个实例

M6 给出 Agent 身份的第二层：会话权限天花板 = 用户 RBAC ∩ Restricted Session Scope 允许面，**只减不增**、每次查询实时求值（不存权限快照）、会话期内锁死（机制定义详 [011 M6](./011-horizon-context.md)；独立第三方实测 Classmethod 2026-09-04：同一用户同一角色，Agent 会话内 INSERT/DDL/角色切换全被拒、人工工作表全放行，实线）。天花板正面实测（键＋结果值，E2b/D9 逐字摘录见 §13.3）：E2——代理身份：会话权限=用户∩代理面 ['select:orders', 'use:sales_sv']（只减不增），IS_AGENT_ACTIVATED 下 select:customers 被拒（用户本人可查）；E2b——回收 select:orders 后既有会话判定即刻失去、其余权限不受牵连（查询期实时求值，无快照过期窗口）。

「实时求值」不是 M6 的实现细节，是一条跨范本成立的法则，有两个方向相反的实例。反证（Horizon 原型，实验键 D9，实心）：D9——拆权限天花板（快照冻结）→ 回收后旧会话仍持 select:orders（越权窗口）（逐字摘录见 §13.3）。

正证（Claude Code 装配面，[172](../agent-harness/172-claude-code-planning-coordination.md) §6，证据分级【一】）：system prompt 每轮调用模型前按当轮 context 重拼——`enabled_tools` 取自当前实际注册的工具表、memories 段看记忆文件当前是否存在且有内容；缓存只是状态键（`json.dumps(context, sort_keys=True)` 的序列化文本）命中时的复用，状态一变即失效重拼。装配判定不落在任何历史时点的快照上。

两个实例合起来是一句话：**权威判定必须落在使用时点的当前状态上**——快照式判定（D9）留下「状态已变、判定未变」的越权窗口；每轮重装配（172）把判定锚在当轮事实上，缓存只省计算、不冻结判定。权限回收如此，工具挂载与记忆在场性如此（ISSUE-194 的教训同根：目录承诺的可达性必须以实挂为准）；§9 G1 与 §12 的接线态判定共用这条法则。

### 5.4 供给面威胁模型：自述不可信与拦截位

经 MCP/技能开放供给，攻击面前移到对象入库之前；本轴的供给面纪律第一条：**供给内容的自述默认不可信**。MCP Security Best Practices Tool Safety 节原文（2026-07-28 版本组；该 revision 截至 2026-10-09 仍为最新正式 revision，S8 探针）："descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server"。生态实测数字（继承旧文，徽随行）：技能生态 98,380 个扫描出 157 恶意、632 漏洞、平均每恶意技能 4.03 个漏洞（USENIX，arXiv 2602.06547，实线——abs 页一手快照 2026-10-10 直证 98,380/157/632/4.03——样本为两大 registry 收录技能，非全生态统计）；Snyk 抽样 3,984 个社区技能：76 个确认恶意、36.82% 存在任意级别安全问题、其中 13.4% 达 CRITICAL（虚线——厂商扫描口径、抽样非全生态普查；整条 Snyk 引用承旧文、一手页未定位＝未决，同 §1.8）；四家头部客户端（Gemini CLI / Claude Code / OpenAI / VS Code）零家验签（虚线——承 2026-09 实测口径，本轮未复测；不外推 showcase 46 家）。

据此排开拦截位（前五行继承旧文，末行为本版新增）：

| 威胁 | 拦截位 |
| :-- | :-- |
| 工具/技能描述投毒（含隐形字符、伪字段注入） | 元数据按不可信输入处理：行级清洗 + 激活工具枚举约束；定义哈希钉住 + 注册期评审 |

读法：左列是威胁形态，右列是拦截位——注意每行的拦截位都不同，威胁与对策一一对应，不可互换（§5.5 的 WARNING 展开）。

同一 revision 的授权硬化增量（继承旧文口径；S8 复核 2026-07-28 版本未变，截至 2026-10-09）：无状态核心（SEP-2575，能力/版本/身份每请求自描述）；MRTR 取代服务器主动请求（SEP-2322）；废弃 OAuth 2.0 Dynamic Client Registration（RFC 7591）改用 Client ID Metadata Documents（PR #2858；同批 SEP-2468 授权响应 iss 参数校验、SEP-2352 凭证按发行方绑定）；特性三态 + 弃用注册表（能力演进治理模板，§9 复用）；deterministic `tools/list` 直接服务 prompt cache 命中率——缓存确定性是接口契约、不是实现细节（装配侧承接见 §6）。2026-07-28 文档树另新增《Local Server Security》教程（本机安全运行 MCP server 的实用默认值，S8）。

技能分发的完整性边界由 SEP-2640 定死（Final，Extensions Track，2026-04-23 创建；现行文本位于 Integrity and verification 小节，S8）："Hosts MUST NOT treat a digest match as a security boundary"——digest 未签名且与内容同源，匹配只证明一致、不证明可信，路径上的中间人（如 gateway）可同时改写 listing 与内容。可移植的对应模式是 content-bound approval：持久批准绑定批准时刻的 resources 全集 digest，此后任何文件的增删或轮换都使批准失效、须重新获批。「幸运而非设计」判定：本仓当前无外部下载面，传输完整性攻击面为零（实心，as-of b2fbb51f5，继承旧文、wf3 无反证）——这是部署形态的偶然结果，不是设计成果；接入外部技能分发之日，该缺口即刻兑现，写成显式触发条件。

### 5.5 记忆供给面：intent legitimation 与写入端时序约束

供给面新增的第三个记忆侧威胁面不来自攻击者。个性化使攻击成功率相对无状态基线提升 **15.8%–243.7%**（实线，arXiv 2601.17887，S4）。全限定随行：这是 PS-Bench base setting 下 10 个角色平均 ASR 的相对提升（%↑ 口径，非绝对百分点差）；评测规模为 5 个记忆增强框架（LDAgent / Amem / Mem0 / MemOS / MemU）× 5 个基座 LLM；区间两端分别是 GPT-4o-mini × Mem0 平均 ASR 26.79 对无状态基线 23.13（+15.8%）与 DeepSeek-V3.2 × LDAgent 30.93（+243.7%，其块内无状态基线更低故相对倍数更大）；hard 子集（1,986 条 persona-grounded 有害查询）不在此区间内、数字更高；Privacy 是例外类别——其退化额外依赖记忆库中是否存在显式 PII。ASR 口径：被有害响应检测器（Do-Not-Answer）判定为有害的测试查询占比，值越高安全性越差。

类型边界必须钉死：该失败模式不是提示注入、也不是记忆投毒。论文提出的失败模式是 intent legitimation——良性个人记忆偏置意图推断，使模型把固有有害查询合法化；检索到的记忆真实、来自日常交互的自然积累（原文："the retrieved memories are truthful and organically accumulated from everyday interactions"）。论文的对策是 detect-and-reflect：在记忆使用点识别可能使当前意图合法化的记忆——不删改、尽量保个性化——插入简短反思提醒，指示模型不得用个人信息为安全关键请求辩护、软化或正常化；平均 ASR 降约 27.4%、安全大体回到无状态水平（论文自测口径）。对蓝图的直接约束是论文开篇判语：既往工作 "treating memory as a neutral component and largely overlooking its safety implications"——**记忆不是中立组件**；复利轴（§8）的任何巩固/记忆增益评估必须双指标（效用 + ASR 退化），单看效用的巩固环会把安全退化当成本沉淀进长期资产。

读取端的新威胁不取代写入端的旧约束，两者并存且拦截位不同（§5.4 表中间接注入行与 intent legitimation 行）：间接注入的拦截在写入端与信任边界段，intent legitimation 的缓解在读取端检测-反思。由此产生一条时序约束：写入端威胁模式扫描必须先于会话巩固上线。本仓断链实况（三件缺两件，ISSUE-195 开放，实心 as-of b2fbb51f5）见 §8.1 详解；时序约束因此尚有兑现窗口：扫描与巩固必须同批落地，巩固单独先行等于在无扫描的写入面上开放常驻注入面。

> [!WARNING] **类型边界：两套数字不可互换叙事**。intent legitimation 的 +15.8%–243.7% 出自良性记忆，写入端扫描与注入防护拦不住它；注入/投毒类数字（如技能生态 157 恶意）的拦截位在写入端与信任边界段。引用任一侧数字时必须携带类型限定——混用会同时误导对策选型（检测-反思 vs 写入扫描）与风险评估（谁在攻击、能不能防）。

## 6. 装配轴（Assembly）：时序、预算、缓存与压缩

资产轴（§4）回答经营什么、权威轴（§5）回答谁说了算，装配轴回答的是每一轮请求里「什么内容、在什么时刻、以什么形态进窗口」。这条轴的全部判定服从同一约束：上下文是边际收益递减的有限资源，**每轮装配是一次预算分配决策**——进入窗口的每个 token 都有机会成本。本章把装配拆成五个可独立验收的判定面：时序四档与预算带（§6.1）、倒 U 填充率红线（§6.2）、缓存感知分段（§6.3）、压缩分级（§6.4）、本仓装配面实况（§6.5）。

> **ADR-6（沿用旧义）：上下文供给是成本结构决策。** 五个设计旋钮按「窗口免费后是否仍承重」分两类：注意力质量类（预算分配、披露语义、检索质量）恒承重——context rot（窗口越大召回越差）是注意力架构属性而非价格属性（Anthropic 官方口径，虚线）；成本类（缓存排序的直接省钱动机）随 token 单价下降而失效。设计按前者对齐。旧文五旋钮（预算分配 / 渐进披露 / JIT 边界 / 缓存排序 / 压缩分级）在本章分别落位 §6.1–§6.4，判定语义不变。

证据分级注记：本章 Claude Code 范本断言按 170–175 四级证据分级标注（【一】固定提交实测 /【二】课程正文 /【三】闭源分析带归属 /【官】官方文档；定义见 [170 §3](../agent-harness/170-claude-code-harness-overview.md)）。与三级徽的对应（定版见 §0.1）：【官】=虚线（官方自报）；【一】【二】【三】=虚线带归属（课程实测=一手课程仓库、闭源分析=带归属的第三方分析）；仅本仓复跑的 lcc/090 原型产物=实心。

### 6.1 时序四档与两级加载预算带

内容进窗口有四个时刻档位，档位之间差的是进窗成本与恢复成本：

| 档位 | 进场时机 | 形态 | 范本锚 |
| :-- | :-- | :-- | :-- |
| 常驻 | 每轮在场 | 身份段、技能目录、Core Block、记忆索引 | CC【官】MEMORY.md 索引以「前 200 行或 25KB 先到者为准」常驻 |
| 渐进披露 | 目录常驻、正文按需 | L1 目录行 + L2 正文（进场后成为对话历史） | CC 两级加载（本节） |
| JIT | 当轮按需检索 / 加载 | 运行时加载器、每轮检索注入 | 本仓 NegentropyPreloadMemoryTool（§6.5，实心） |
| 仅引用 | 永不整份进窗 | 路径 + 预览占位、视图 + 指针 | CC 大结果落盘（§6.4）；ADR-1 指针纪律（§4.5 同根） |

读法：档位越靠下，进窗体积越小、按需恢复的成本越高；四档不是四选一——同一资产可在生命周期里沿档位下移，压缩（§6.4）就是系统化的下移动作。

两级加载的预算带以 Claude Code 为范本。课程口径：目录每技能约 100 tokens 常驻、全文每技能约 2000 tokens 按需——两级相差一个数量级，常驻项要尽量小（170–175【二】课程估计；限定：官方文档能印证的是机制形态与 1536 截断，不能印证这两个数，[172 §11](../agent-harness/172-claude-code-planning-coordination.md) 边界第 4 条）。真实 CC 的口径：目录预算被控制在上下文窗口的约 1%（上限 8,000 字符）【三】；frontmatter 的 description 与 when_to_use 合计在技能清单里截断到 1,536 字符以控制上下文开销【官】（虚线）。目录要短，是因为目录自己是常驻内容——它为所有技能的「可被发现性」付每轮成本。

两层寿命不同，是渐进披露最容易被漏掉的属性：正文进场后不是 system prompt 的一部分，而是对话历史的一部分，后续每一轮都在场，直到被压缩、截断或会话结束清出；目录则常驻不随压缩消失——「已激活 ≠ 仍在场」，须配重激活。官方幸存表把恢复制度化：压缩后按预算重读最近改过的文件（至多 5 个、每个 5,000 token）、按限额重注入技能正文（单技能 5,000 / 总 25,000 token，最旧先丢）【官】（虚线）。「按需加载解决了不该提前带的不要带，压缩解决该丢的怎么丢」——两级加载与 §6.4 是同一经济学的两半。

常驻面的守护有本仓实测支撑（均实心，[090 技能规范实验室](../agent-infra/090-agent-skills-spec.md)）：渐进披露会话账本 2,321 vs 全量预载 39,222 tokens（16.9×，chars/4 近似口径只证方向；破坏实验 B1 同构复测 16.3×）；一条 12,159 字符的膨胀描述令目录从 1,206 涨到 4,285 tokens（+255%，单条等于其余 20 条之和的 2.4×，B3）——描述长度上限守护常驻面。进化面同守此界：本仓 prompt_template 有界变异约束即按「Decagon 4x 压缩经验：精炼优先」设界（[`engine/evolution/handlers/skill.py`](../../../apps/negentropy/src/negentropy/engine/evolution/handlers/skill.py):76/:233，厂商工程经验转引，虚线）。

JIT 与预取的决策边界要显式声明，不要默认：静态约定与规范 up-front 入窗（如 CLAUDE.md 朴素入窗）、大体量事实走 JIT（轻量标识符 + 运行时加载器——引用元数据本身是行为信号，模型调用加载器这个动作已携带意图）；小知识库 <200K token（约 500 页）直接全量入窗并配 prompt caching（延迟 >2x、成本至多 −90%，Anthropic 口径，虚线）。判定依据只有一条：被用到的前提概率 × 每轮携带成本。

### 6.2 倒 U：预算即质量

预算不是省钱的手段，是质量的手段——填充率、工具数、目录规模、粒度都有最优点，过与不及都伤质量，曲线形状是倒 U。这条轴的公理：上下文是边际收益递减的有限资源（n 个 token 产生 n² 两两注意力关系，Anthropic 官方口径，虚线）；即便模型能力扩张，把上下文当珍贵有限资源仍是核心（官方结论句，虚线）。

三条红线各有实证。其一，填充率：窗口填充超过约 50% 时 AI 编码性能常下降——过多与过少上下文都会损害效果（CE 2.0 综述转引 Osmani 2025 经验观察，虚线，非受控实验；「注意之前的注意」同出此处）。其二，供给规模：Snowflake 官方建模最佳实践要求整视图控制在 ~100,000 token 内（guideline），超限触发 prune——视图 + 指令 + 会话历史逼近窗口，延迟与质量双伤（虚线，详 [011 §6](./011-horizon-context.md) 护栏表）。其三，工具面：16K 窗口挂 46 个工具时该查询失败、只挂 19 个工具时同一查询成功（arXiv 2411.15399，实线）。限定必须随行：被测模型是 Llama3.1-8B 的 q4_K_M 量化版、跑在 Jetson AGX Orin 边缘设备上；46/19 是单条查询的动机示例（同表 8K 窗口 19 工具亦成功），失败归因「可选工具太多令 LLM 混淆」是作者的解释性论断、非受控消融——工具面预算的方向成立，具体阈值不可外推。

任务规约是装配面自己的供给物，其失效形态有独立实证：把完整任务规格分片到多轮对话逐轮揭示（Sharded），相对单轮全规格（Full）平均退化 −39%（15 个 LLM × 六任务的 Full→Sharded 均分，arXiv 2505.06120，实线；论文图 1 题注另有 −35% 口径，引用取正文口径并注明出入；多轮欠规格对话平均成绩 65%，比单轮全规格的 90% 低 25 个百分点）。要点在分解：能力（aptitude）平均只降 16%、不可靠性（unreliability）平均涨 112%——模型不是不会做，是多轮欠规格下更容易丢线索、跑偏。装配面对策（本蓝图设计判定，非论文原文主张）：任务规约保持单点——一处 SSOT、不随轮散落漂移；派发与执行前显式复诵完整规约——直接对冲失效大头（方差），这比「换更强模型」便宜且正交。

### 6.3 缓存感知分段

分段的目标只有一个：会变的排在不变的后面，稳定前缀不被动态内容打散。真实 CC 的落法【三】：以 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 把 system prompt 切成静态段与动态段，静态段命中全局 prompt cache、不因动态内容失效；动态内容的边界，恰好画在「会随轮变化的状态」上——`mcp_instructions` 是唯一易失 section，因为 MCP 服务器可以在轮间连接和断开。配套三层缓存（会话级 memoize、section 注册缓存、API 级 boundary 切分）与两类 section（静态恒载 / 动态按状态）【三】；标准交互模式下 system prompt 核心约 20–30KB、极简模式约 150 字符，同一装置两种模式体量差两个数量级【三】。

组装侧的确定性是可工程验证的。课程实现用 `json.dumps(context, sort_keys=True)` 的序列化文本做组装缓存比对键，不用内置 `hash()`——进程随机化、嵌套结构不可哈希（170–175【一】，[172 §6](../agent-harness/172-claude-code-planning-coordination.md)）。执行侧的极端形态是 Fork 模式【三】：不创建全新上下文，而是构造与父对话字节级一致的缓存前缀——system prompt、tools、model、messages 前缀、thinking 配置五件必须完全相同，错一件前缀即断、缓存即失。隔离与缓存效率是一对真实权衡，设计时须显式选择。

记忆注入的位置服从同一纪律：索引常驻 system 前缀（小而稳），召回正文放当前用户消息侧（大而变，不连累前缀）——CC 官方口径为 MEMORY.md 索引常驻、话题文件按需读取【官】，教学侧给出同构论证【一】。本仓对应判定：启用前缀缓存之日，检索记忆须移到用户消息侧或按会话冻结；Hermes 的三载体接力（对话记录 → 压缩重建 → 新会话快照，写回永不随写随见但永不丢失）是会话冻结的现成范本（[190](../agent-harness/190-hermes-agent.md)）。

装配纪律两条收束本节（CC 范本，170–175）。其一，谓词驱动：段落取舍判据是可观察运行时事实——记忆索引文件存在且非空才铺记忆段、MCP 已连才铺外接段，「装配依据是事实，不是文本」。其二，装配序不变式：先处置会丢的历史治理 → 再叠不能丢的记忆供给 → 最后装能力面工具 + 提示，三者同频、每轮重算——170–175 的每轮重装配与 M6 天花板的每查询实时求值是同一法则的两个实例（详 §5）。

### 6.4 压缩分级：便宜的先跑

压缩管线的排序原则一句话：零模型调用的结构操作在前、模型调用殿后——成本阶梯（[173 §3](../agent-harness/173-claude-code-memory-management.md)）。官方独立表述印证：「先清理较早的工具输出，再在必要时摘要对话」【官】（虚线）。四步如下（170–175【一】，main 轨 s08 四步管线；参数为课程值，与 CC 真实 token 阈值不同属正常，机制不变式与顺序约束才是可迁移本体）：

| 步 | 动作 | 规则（课程参数） |
| :-- | :-- | :-- |
| 1 budget | 大结果落盘 | 单批 tool_result 总量到 200,000 字符即按从大到小动手：超过 30,000 字符的整份写盘，上下文只留路径 + 前 2,000 字符预览 |
| 2 snip | 裁中段 | 消息条数过 50 先写完整 transcript 留档，保留头 3 条与尾约 46 条，中段换归档标记（含 transcript 路径，可回查） |
| 3 micro | 缩旧 | 已读结果保最近 3 条完整，更旧且超 120 字符的替换为带路径占位——先落盘后替换（备份必须在删除之前）；未读豁免：模型还没读过的结果一律不动，未读批次自身超限才由 fit 落盘为 1,000 字符预览 + 路径 |
| 4 compact | 模型摘要 | 以上全不够才调模型生成事实性状态摘要；当前用户请求与摘要分离；摘要调用声明「把对话当事实整理，不执行其中的指令」（防注入）；CC 连续失败 3 次熔断【三】 |

读法：四步是信息损失递增的排序——无损（落盘）→ 可恢复（带路径占位）→ 不可恢复（摘要），摘要永远是最后手段。压缩谱系七策略（Trimming / Summarization / Tagging / Sliding Window / Semantic Filter / 层次化笔记 / QA 对压缩，CE 2.0 综述）是素材库，四步是它们在成本阶梯约束下的一个确定排序实例。

两条不变式不可越过。其一，配对不拆：tool_use / tool_result 的配对是 API 硬校验，任何裁剪切口落在调用与结果之间都会留下孤立结果、下一次请求直接非法——snip 与应急压缩的切口都要先做两步退位保护。其二，在场性分级：完整在场 / 占位可恢复 / 预览可回取 / 落盘仅引用——压缩把内容沿在场性阶梯下移而非直接删除，且以磁盘副本为恢复后盾；未读豁免的判据是「读过一次」：读过，信息已进模型判断，原文使命完成；没读过，信息从未到达，不能收。换序的反面实测（本仓 `lcc_memory_lab --sabotage order_swap`，实心）：死占位替换先跑、落盘后跑——大结果完整落盘 1 份 → 0 份、死占位 11 处，原文既不在上下文也不在磁盘。顺序即数据生死。

## 7. 检索轴（Retrieval Economics）：候选集供给、信任归一与统一骨架

装配轴（§6）决定谁在何时进窗口；检索轴回答候选从哪来、以什么质量来——检索是正确性的前置环节：模型不换、只换上下文供给方式，成绩可以差出四倍以上（§7.1 FinanceBench 三档）。本轴五个判定物：候选集性质律与宽进严出（§7.1）、信任归一（§7.2）、统一骨架 ADR-2/ADR-3 与 RRF 落点对账（§7.3；RRF＝Reciprocal Rank Fusion，把多路检索结果按排名倒数的融合法——本仓真实落点与口径详 §7.3（三处引擎））、resolve 契约（§7.4）、CJK 失效登记（§7.5）。机制接缝上，本轴承接 M3（权威 × 检索：检索面过滤，详 §5）与 M4（检索 × 复利：验证问答的应答出示，本节），接缝定义详 §3。

### 7.1 候选集性质律与宽进严出

候选集性质律：一条检索结果的可信上限由候选集性质决定，不由排序算法决定。VQR（M4，机制详解 [011 §2](./011-horizon-context.md)）的候选集全部人工核验过——错误面窄，故可作验证锚定、命中即采用已验证 SQL；通用检索的候选集是全目录——错误面宽，排序与过滤只是兜底。011 §3.2 同口径：检索的定位是候选集供给，它决定「哪些上下文被端到 Agent 面前」。两条路径在 resolve 契约分流（§7.4）。

供给方式的档位差有一组三档证据（FinanceBench，arXiv 2311.11944，实线；Patronus 官方公告页以「GPT-4 Turbo 带检索系统 81% 失败」作头条、与 19% 互为表里，一手在线核验截至 2026-10-09）：

| 检索实现 | 同一 GPT-4-Turbo 成绩 | 口径限定 |
| :-- | :-- | :-- |
| 共享单一 vector store（全部文档一库） | 19%（150 题仅 29 题正确，68% 拒答） | 最差档——19% 是「共享单库」这一档的结果，不是「检索」的通名成绩 |
| 每文档独立 vector store | 50% | 论文同段明确的中间档 |
| Oracle 证据页（直接给到正确 evidence extract） | 85% | 证据仅 1 到数页——供给正确证据时的上界参照 |

读法：模型没换、考卷没换，换的只是上下文供给方式——检索实现方式的档位差，是「检索是正确性的前置环节」最硬的单件证据。建错表比写错 SQL 更致命的断崖证据由 §1.4 登记簿行承载。

工程形态是宽进严出的三段管线：初检索宽进（top-150 候选）→ rerank 严出 → top-k 截断（评测取 top-20）（Anthropic 参考实现与评测口径，虚线）。截断不是省事，是信噪比控制——候选喂得再多，进上下文的只有被重排认可的一小撮，与 §6.2 倒 U 互证。方法论证据：检索增强把 top-20 失败率 5.7%→2.9%（相对 −49%），加重排 −67%（口径 1−recall@20，Anthropic contextual retrieval，虚线；2024 年数字只作机制有效性证据）。分层增益同向：关键词 0.22 → 向量 0.49 → 混合 0.53 → 混合 + 重排 0.59（NDCG@10），hit rate@1 0.79→0.86——混合 + 重排是检索侧的标准形态（Cortex Search 内部基准，Snowflake 自报，虚线；详 011 §3.2）。

供给结构的保留证据补一件（实线）：240 条消息多主题会话设定下，AgentRM 三层 Context Lifecycle Manager 保留 99.6% 关键信息、无管理对照 54.3%（arXiv 2603.13110）。限定随行：这是论文多主题 240-msg 细分表，论文头条是单主题口径（100% / 65.1%）——转引时勿混写；基于模拟 agent 工作负载评测、非真实部署直接测量；「结构化记忆管理」的机制实名是上下文生命周期管理（AgentRM-CLM），勿与 MemGPT 类记忆管理混称。

### 7.2 信任归一：四因子、三纪律与五源信任分

排序本身是治理表态——什么该被看见由权重决定。四因子（relevance / authority / popularity / freshness：权威压过声量、新鲜压过陈旧，详 011 §3.2）落到跨源归一是三条纪律，每条都有反证：

| 纪律 | 内容 | 反证 |
| :-- | :-- | :-- |
| ① authority 区分 governed / inferred | 受治理定义权重高于推断口径 | 011 §3.1「受治理的语义视图 authority 最高」（四因子官方口径；lab 侧佐证为 C3b 人工裁决 governed 胜出后恢复——C5 本身是 freshness 实验、两侧 authority 同值，不充当本行反证），[horizon_context_lab.py](./assets/horizon_context_lab.py):987 |
| ② popularity log1p 有界 | 防多数派错误放大；lab 实现为 log1p(pop)/log1p(POP_CAP)，禁全局 max 归一 | D4（011 §6）：冲突交 popularity 自动选，错误口径碾压正确口径胜出（热度 200:5 见 lab 源码字面量，实心） |
| ③ freshness 单一 staleness 口径 | 跨源可比 | 本仓 freshness 语义不对称（见下） |

实际运行日志（2026-10-09 复跑）：D4——冲突改 auto_popularity，推断层 [6,1,2] 胜出（对照 [3,1,2]，热度 200:5；逐字摘录见 §8.4）。读法：热度 200 的错误推断口径压过热度 5 的正确 governed 口径——「习惯不等于真理」，与 §9 G3（裁决权不自动化）同根。

归一层不发明新信号，只做 per-source 标准化——五源现成信号清单：Memory=retention / importance / access_count；Fact / KG / canonical=confidence + valid_from / valid_until + supersede 链（KG 另有 PageRank + 社区 + 证据支持）；KB=retrieval_count + is_enabled + quality（现多 NULL）；Tools=成功率 / 延迟；Skills=active_version / visibility。跨源 freshness 语义不对称是归一层最硬的设计题：KG 有双时态 as_of、Memory 仅 last_accessed_at（非 bi-temporal）、KB 连 last_accessed_at 都没有——单一 staleness 口径必须先补齐这三档落差。

### 7.4 resolve 契约与 M4 双落位

M4 双落位口径不变：验证问答的字段登记在资产轴（§4 verified 对象在册），应答出示在检索轴（本节）——在册是资产事实、出示是应答行为，两侧独立验收。agent 侧唯一入口是 resolve 契约：

`resolve(question, role) → ContextPackage{top-k, instructions, verified_query?, warnings, conflict_card?}`

三条出路、无静默瞎猜：命中题库 → 以已验证查询为生成依据、透出 confidence 与所用条目；未命中 → 走现算路径、显式标注未经核准；无 governed 覆盖 → 显式返回 `no_governed_coverage` 而非静默用推断。命中路径与引擎重算对账一致（键＋结果值，2026-10-09 复跑）：A1——verified 短路重放＋溯源（逐字摘录见 §13.3）；A1b——引擎重算==验证答案 [200, 150, 300]（对账一致）——锚定的意义在背书与确定性。冲突不走投票：`conflict_card` 并列两定义、无数值、拒答待人工裁决（C3——CONFLICT 卡片 governed/inferred 并列、agent 拒答；裁决权不自动化，§9 G3）。

题库两条红线：其一，>20 条反噬——优化会真跑你的 verified SQL（每条至多执行 4 次）、超过 20 条显著拖慢（官方手册，虚线）；其二，题库会腐化——口径变了题库要跟着重验，否则锚定住的是过时答案（011 M4 红线；重验触发归 §9 L6 死亡段）。

subagent 探查隔离是候选集供给的一种形态：探查类污染（大输出 / 死胡同）留在用完即弃的子上下文，只回蒸馏摘要（1,000–2,000 token，Anthropic 口径，虚线）；「隔离的是上下文，不是权限也不是副作用」。本仓 `lcc_planning_lab` 原型实测（实心，[172 §4](../agent-harness/172-claude-code-planning-coordination.md)）：同一探查任务，子代理只回结论时主对话 4 条 / 147 字符，改成回传全部子历史涨到 16 条 / 2,649 字符（约 18 倍）——只回摘要是主对话上下文体积的存亡线。

## 8. 复利轴（Compounding）：回路三在线、裁决不投票与 6+1 进化杠杆

前四轴回答的都是「这一轮怎么把上下文供给对」：资产轴定经营对象，权威轴定真值与执法，装配轴定这一轮进窗口什么，检索轴定候选从哪来、怎么排。复利轴换一个问题：**下一轮凭什么比这一轮好**。这一轴经营的不是对象，是回路——把系统的使用过程本身变成新资产的供给线：会话沉淀成记忆、错误答案反哺定义、行为信号调整参数。回路的判定口径只有一条：复利三在线律。这条轴独立变化——换检索算法不动复利回路，改披露层级不动沉淀纪律；反过来，机制常常跨轴组合（M4 是检索×复利的接缝，Snowflake 的富化双轨是资产×复利的接缝，机制=轴向量组合的总纲见 §3）。

### 8.1 复利三在线律：存在、接线、在线

一个回路算数，当且仅当三件东西都在生产路径上：触发器（什么条件下启动）、消费者（谁真正执行）、水位线（做到哪了的记账）——**三件缺任何一件，回路不存在**。这不是实现细节，是判定口径：「代码里有这段逻辑」只证明第一态（存在）；被生产调用方引用是第二态（接线）；三件齐备跑在生产路径上是第三态（在线）。外部证据把这条律的代价标得很直白：Redis State of Context Engineering 落地页口径，94% 的受访者称复利式系统智能对生产成熟度必不可少，只有 4% 做到了（虚线；厂商落地页口号，样本量 n=1000 在公开页面零披露，该口径永久全限定，截至 2026-10-09）——想要与做到之间的落差，主要就断在这些不在线的回路上。

本仓的主实例是会话巩固回路（ISSUE-195，实心，as-of b2fbb51f5）：`add_session_to_memory` 在 [`memory_service.py:84`](../../../apps/negentropy/src/negentropy/engine/adapters/postgres/memory_service.py) 有定义、有集成测试，但全仓生产调用方为零；`consolidation_jobs` 的唯一写路径是调度器入队（[`memory_automation.py:173-192`](../../../apps/negentropy/src/negentropy/engine/schedulers/handlers/memory_automation.py)），出队消费者不存在；水位列 `consolidated_at_event_seq` 在 migrations 与 models 中全仓零命中。三件缺两件——回路不存在，交互式会话的内容不会沉淀为长期记忆。16+4 映射表第 17 行（§12）承载这条判定。

复利轴还有一个冷启动问题：回流的原料从哪来。Snowflake 自家数据团队给 9,685 张表建语义视图，覆盖不到 5%（虚线，[011](./011-horizon-context.md) §3.1 厂商自报）——显式轨道（人写定义）追不上数据增长，这就是隐式轨道（从查询历史与使用模式里挖工作理解）的触发条件。本仓对应判定：显式定义的覆盖面停滞时，隐式挖掘轨道才值得投入，不是一开始就双轨齐开。隐式轨道启用时须带一条本文的合规边界承诺：**只摄取元数据与使用模式，不碰数据行**——挖掘对象是查询习惯与信号，不是数据本体。

### 8.2 巩固三件套：会话到长期记忆的修复设计

会话在资产轴的经营对象里是唯一一条持续自产新上下文的来源——「会话→长期记忆」是复利轴的供给入口。断链实况已在 §8.1 交代。修复设计不新建表，复用 `title_inspector` 已验证的水位范式（[`title_inspector.py`](../../../apps/negentropy/src/negentropy/engine/title_inspector.py)）：

1. **trigger 触发器**——「事件水位差 ≥Δ 且会话空闲 ≥T」选中候选会话（与 `title_generated_at_event_seq` 同构）；
2. **consumer 消费者**——`FOR UPDATE SKIP LOCKED` 出队执行 `_simple_consolidate`（`consolidation_jobs` 表与部分索引已存在，迁移 0043/0044，无需新建；实心，as-of b2fbb51f5）；
3. **watermark 水位线**——`threads.metadata.consolidated_at_event_seq`，提交点最后写：两步都成功才落水位。这是 OpenViking `.done` 的提交点语义（[014](./014-openviking.md) §6）：至少一次投递下，没有提交点的事件会被重复提炼——实测 B6 拆掉 `.done` 后一条事件落两张卡（「上线了支付服务 v2」与「…（复述）」并存，实心，014 配套原型实测）；水位只记「到哪了」不记「做了什么」，重跑靠内容去重兜底（[015](./015-openviking-mapping-negentropy.md) §6）。

> [!WARNING] **「写面已销账」不是「回路已接线」**
> ISSUE-195 的销账口径分两面：写面（文档与状态表把断链如实登记、修复设计落位）已收口；做面（消费者、水位、UI 消费方）截至 as-of b2fbb51f5 全部未动工。读 §8.2 不得把「设计已给出」读成「回路已闭合」；任何新回路上线前，按三在线律逐件核到生产调用方那一层——「函数存在 ≠ 链路存在」是 ISSUE-194/195 共同的教训。

### 8.3 沉淀什么、判「同一条」靠什么：self-baking 与身份判据

沉淀的理论底座是 CE2 的分层记忆三定义（实线，arXiv 2510.26493 :650–691 一手论文）：短期记忆 M_s 按时间相关性权重选入（式 5），长期记忆 M_l 恰恰要求时间权重已低且重要性高（式 6），迁移函数 f_transfer: M_s→M_l（式 7）由重复频度、重要性与既有知识结构的相关性门控。本文从式 5 与式 6 读出一组对偶选择（此读法为本文解读，非论文自述）：**长期记忆是熬过时效者**——被迁移的判据（w_temporal≤θ_s）与被短期持有的判据（w_temporal＞θ_s）在时间维度上相反，所以迁移必须带显式门控，不能「新到的顺手都存」。同一论文给这条轴最短的定义（:712，实线）：self-baking「把记忆存储与学习区分开——没有它，agent 只是回忆；有了它，才积累知识」。存储不等于学习：把会话原样存进库里是存储，经 f_transfer 消化成持久知识结构才是复利。

工程上第二个判定是「两条沉淀算不算同一条知识」。OpenViking 的照鉴（[014](./014-openviking.md) §6.3）：**相似只提名候选，同一性由 schema 身份字段裁决**——URI 由身份字段确定性生成，「是否同一条记忆」降维成「文件名是否相同」。拆掉身份判据的实测：B3 把会话 ID 混进卡片名，同一用户三次来访落三张矛盾卡（美式/拿铁/拿铁并存，实心，014 配套原型实测）——没有身份判据，一个月后记忆库自相矛盾。落到本仓：按 memory_type 定合并算子——events/trajectories 只增不改（宁可重复不可错并），experiences 走 replace+supersedes；阈值去重（cos≥0.85/0.90）为主干，LLM 裁决只值得用于模糊带 0.80–0.90。

### 8.4 冲突浮出不投票：裁决纪律与 eval 自纠环

复利轴最危险的失效不是「不积累」，是「把错的积累成对的」。纪律三条，每条都有实测反证：

- **冲突浮出人工裁决，禁按热度投票。** 起草定义与民间口径打架时，并列两定义、不出数值、拒答待裁。反证是 D4（实心，[011](./011-horizon-context.md) §6）：冲突改交 popularity 自动选，错误口径以热度 200:5 碾压正确口径胜出——「习惯不等于真理」。（477 vs 48 判例的玩具版是 D3 而非 D4，见 §10.1；「D4＝477 玩具版」的修辞错挂在 lab 源码 D4 消息字符串与本文旧稿，011 冻结件内的 D4 引用本身无误。）实际运行日志（selftest-lab-full.log，2026-10-09，D4 逐字摘录全文唯一保留位）：`[PASS] D4: 冲突改 auto_popularity → 推断层(count events) 胜出 [6,1,2]（对照 [3,1,2]）—— 477 vs 48 事故的玩具版`；正向形态同日志：C3——冲突浮出（CONFLICT 卡片 governed/inferred 并列、无数值、agent 拒答）、C3b——人工裁决（governed 胜）后恢复 [3, 1, 2]。

## 9. 时间面：生命周期六段两环

五条轴都是横截面：换掉检索算法不动权威模型，改披露层级不动对象清单（独立性矩阵见 §3）。时间面拉出纵贯的一维——一个上下文对象从哪来、经什么手续变成可装配的受治理对象、每一轮怎么被用、答案怎么被锚定、用法怎么回流、最后怎么退场。主轴六段：**L1 采集纳管 → L2 铸形裁决 → L3 装配执法 → L4 应答锚定 → L5 沉淀回灌 → L6 衰减退役**；两条一等环（验证环、进化环）叠在主轴上；治理不另立平行章，以 G1–G7 七条落位法则钉在段间转换上（§9.5）。

### 9.1 Snowflake 三阶段为什么不够：单程、无死、无闸位

Collect → Enrich → Activate（[011](./011-horizon-context.md) §3）是当下最完整的供给侧叙事，但作为时间轴有三个结构性缺口，六段两环各补一刀：

- **单程无环。** 验证与进化在 Snowflake 产品里只是 Enrich 段内的厂商特性（VQR 优化回路用题库反推语义层缺什么、Sense 自纠环），不是阶段的固有一环；评测闭环（Cortex Agent Evaluations）更是与 Autopilot 并列的独立发布环节、不在 Horizon Context 之内（虚线，官方口径）。后果有判例：477 vs 48 这类活在语义层边界之下的错数（上游 grain 已塌缩），两条环都够不着。CE2 论文把 adapt 列为八算子之第 (8)（may-include 口径，arXiv 2510.26493 :408，实线）——三阶段的名字里没有它。
- **无死亡段。** MAX_STALENESS（最低 120 秒）管的是物化数据新鲜度（虚线，官方文档）；定义级腐化只有警示没有机制——「题库是资产也会腐化，口径变了要跟着重验，否则锚定住的是过时答案」（011 M4 红线）；Sense 四因子的 freshness 只降权不清退。对象只生不死，目录只进不出。
- **无治理落位。** 阶段名描述对象的移动，不描述对象的状态与闸位。「Collect」可以被读成「复制」——恰是 M3「不复制不缓存」要消灭的形态。强制力来自执行点而非定义点（011 规律 2）——治理不是流水线的一段工序，而是横切在各段转换上的落位法则（§9.5）。

三阶段的归宿不是丢弃而是收窄：Collect≈L1、Enrich≈L2、Activate≈L3+L4——011 自己的降级判断（三阶段是供给侧骨架、正确性承重在 M1–M7）由此结构化。

### 9.2 六段主轴：入口、出口与段级反事实

下表是六段的判据面：每段给入口判据（什么能进来）、出口判据（出去时必须成立什么）、以及「拆掉这段转换坏什么」的段级反事实。反事实列是验收判据，不是修辞——每一条都有对位实验键或本仓实证。

| 段 | 入口判据 | 出口判据 | 拆掉这段转换坏什么 | 对位 |
| :-- | :-- | :-- | :-- | :-- |

表后读法：六行反事实没有一行是「效果变差」级别的诉苦，每行都是可复现的具体坏法——这是反事实存在性律在段级的落地（机制级 D1–D10 见 [011](./011-horizon-context.md) §6）。逐段展开如下，各段只讲段级增量，机制细节回指 §4–§8。

#### L1 采集纳管：出身有出处

任何对象进目录前先过门。外部管道走 OpenLineage 三道闸（鉴权/只收 COMPLETE 事件/对象可解析，任一不过整事件拒绝——与 §4 资产表同口径），本仓定义走注册期 422 门（[`registry.py:129-140`](../../../apps/negentropy/src/negentropy/agents/definitions/registry.py)、[`definitions_api.py:75-80`](../../../apps/negentropy/src/negentropy/interface/definitions_api.py)，create/update 双路，实心 as-of b2fbb51f5）。入口判据只要求裸信号存在，出口判据要求带出处入账——「这条边是谁在何时因何记下的」可追。ghost 零容忍的实测（selftest-lab-full.log，2026-10-09）：D8——拆血缘解析闸 → 虚构对象入账（raw.y→ghost.x），账本与真实数据流脱钩（速查表见 §13.3）。载体决策在此段绑定：目录用 PostgreSQL VIEW 不建物理表（ADR-1，见 §4）——出生进目录不产生第二份存储。

#### L2 铸形裁决：机器发现、人类定规

原始信号变成受治理对象要过两道手续：结构校验（外键指向键列、关系不成环、指标带聚合函数——D6：无门则垃圾定义静默入库），与语义裁决（供给双轨 + 冲突浮出人工裁决 + M7 一次性映射闸——机器判断到组织规则之间唯一的人工关口，D10：断在最后一环，分类就不等于保护）。供给双轨的分工：显式轨道（Autopilot 起草、人审后发布）出受治理定义，隐式轨道（Sense 从查询历史挖工作理解）抬长尾的地板，冲突一律浮出人工（C3/C3b 实测形态见 §8.4）。G2 两道独立保险与 G3 裁决权不自动化在此段落位。

#### L3 装配执法：每轮重装、实时求值、指针不副本

装配段守三个不变量：

- **每轮重装**——窗口内容每轮重建，不存冻结成品：enabled_tools 每轮从注册表取、记忆段存在且有内容才铺（CC 同构，详见 §6）；
- **实时求值**——策略在装配与执行那一刻求值，不取权限快照（D9 反证：快照式权限是越权窗口）；
- **指针不副本**——持久层存指针、大块留外部、按需取回（G5；Atlan artifacts 层同口径：运行时引用而非拷贝）。

执行点双层防线（检索层过滤=体验，执行层拒绝=底线）在此段求值，实测（selftest-mcp-full.log，2026-10-09；键＋结果值，逐字摘录见 §13.3）：T2b——PRIVATE 指标对 intern 不下发；T5——引擎层 RBAC 经 MCP 仍生效。轮内还有一层微观生命周期——四步压缩把在场内容分阶段降级（先落盘、再裁中段、再缩旧、最后才模型摘要），配对不拆、占位可恢复——它是嵌套尺度（§9.4）的最内圈，装置细节在 §6。

#### L4 应答锚定：三条出路，没有静默瞎猜

答案出口只有三条路：命中核准题库短路重放（A1：verified 短路+溯源；A1b：引擎重算与验证答案对账一致——锚定的意义在背书与确定性）；未命中走 M1 现算；无 governed 覆盖显式告警。实测（selftest-lab-full.log，2026-10-09；键＋结果值，A1 逐字摘录见 §13.3）：A1b——引擎重算==验证答案 [200, 150, 300]（对账一致）；C1——新表无 SV：inferred 条目胜出＋警告 no_governed_coverage，覆盖 4/5 表。三条出路都不含「静默瞎猜」这个选项。治理与验证在此分落位（G4）：L1–L3 保证定义对、算得对、管得住，但「结果是否真的对」是另一件事——477 vs 48 判例（虚线＋实心，详解 §10.1）说明治理半边再完备也拦不住活在边界之下的错数，所以验证必须有自己的环（§9.3）。

#### L5 沉淀回灌：f_transfer 的工程化

CE2 式 5–7 的对偶选择（M_s 按时间权重高选、M_l 恰要求时间权重低——长期记忆是熬过时效者）与 self-baking 的「存储≠学习」（arXiv 2510.26493 :712）已在 §8.3 展开；本段只钉时间面的事实：迁移边必须显式存在且三件在线（trigger/consumer/watermark），否则它只是架构图上的一个箭头——ISSUE-195 是迁移边「定义了、从未被走过」的实证（实心，as-of b2fbb51f5）。进化环从这里起跳：用法沉淀成新对象回灌 L2（查询历史喂 Autopilot 草稿、eval 错一道修一处），本仓实例是 §8.5 的 6+1 进化面。

#### L6 衰减退役：死要有葬礼

理论侧：优先级衰减让旧者降权、outdated 自然失势（arXiv 2510.26493 :830，实线）；CE2 把「主动地增、改、忘」列为系统能力目标（:916，实线）。工程侧的现状是三个失效（全部实心，as-of b2fbb51f5）。下表三行是本仓死亡段缺口的全部登记，读法是每行看「谁该负责让对象退场、现在卡在哪」。

| 失效 | 形态 | 锚 |
| :-- | :-- | :-- |
| 物化只写不删 | 定义禁用/删除后盘上旧目录残留；`_write_to_disk` 幂等写入（:129-131 跳过已存在），全文件无 unlink/rmtree/delete | [`harness_materializer.py:114-134`](../../../apps/negentropy/src/negentropy/agents/definitions/harness_materializer.py)（实心）· [091](../agent-infra/091-agent-skills-mapping-negentropy.md) M13 |
| 挂载收回双向悬空 | 目录末行指令承诺 expand_skill 激活路径，三件工具从未进 TOOL_REGISTRY、任何 Agent 未持有；(a) 挂载/(b) 收回承诺均未落地 | ISSUE-194（实心，wf3 §2） |

表后读法：前两行是「对象已失势但未退场」，第三行是「对象在场但内容已过期」——两类都要显式的退役/重验路径；降权只延缓、不清退。

两级死亡、两种口径，不能混：轮内死亡是可恢复的（四步压缩把内容降级为占位、配对不拆、需要时可复活——窗口治理，详见 §6）；目录级死亡必须显式且有账（superseded 登记前后继、物化清理带生成标记安全删除、题库重验触发）。行业同构是声明化管理：DCM Projects 的 DEFINE SEMANTIC VIEW 已 GA、ATTACH MASKING POLICY 进 Preview（虚线，官方 release notes，2026-09-30）——定义的生与死都收进声明式项目管理的版本控制。

> CC 的压缩管线让窗口内容体面退场，但这不产生任何目录级退役记录。把「压缩很健康」读成「死亡段已就位」，会恰好漏掉上表三个缺口——死亡段的验收对象是目录与账本，不是窗口。

### 9.3 两条一等环：验证环与进化环

单程流水线的判定性缺陷是「错了回不去」。六段两环把两条回流升为一等公民：

**验证环（L4 → L2/L6）**：答案错误反哺两处——回 L2 修定义（VQR 优化回路用题库反推语义层缺什么，自动建议补过滤器与描述），回 L6 检出腐化（引擎重算与验证答案对账不一致即告警，A1b 的对账形态；口径变更触发题库重验）。注意这条环在 Snowflake 产品里只有厂商特性级别的实现，一般性计算正确性验证仍是开放面（011 §8 第 4 条）；本仓对应物是 patrol/Judge 自纠环（§8.4）与 §10 的 grain 契约验收位。

**进化环（L5 → L2）**：用法沉淀成新的受治理对象——查询历史喂 Autopilot 草稿、eval 错题修信号、进化面在线信号回流为提案依据（§8.5）。这条环的成立条件仍是三在线律；skill 面在线门悬空（ISSUE-194 连累）说明环上单个采样点断掉，整段灰度就退化成只看离线。

两环一等化的设计含义：验收一个 Context Layer，除了问六段每段的闸位，还要问两条环各自「断在哪、怎么接回去」——验证环断则错误静默积累，进化环断则系统永远停在初始定义的质量水平。

### 9.4 嵌套时间尺度：轮内、会话内、跨会话、组织级

六段是对象的一生，不是系统运行的节奏；同一套段结构在四个时间尺度上嵌套出现。下表四行按尺度从内到外，读法是每行看「这个尺度上谁是生灭的主体、死亡口径是什么」。

| 尺度 | 生灭主体 | 典型机制 | 死亡口径 |
| :-- | :-- | :-- | :-- |
| 轮内（单次装配事务） | 窗口内容 | 四步压缩、占位降级、配对不拆、enabled_tools 每轮取注册表（§6） | 可恢复：占位可复活 |
| 会话内（分钟–小时） | 会话状态与中间产物 | 巩固触发（水位差 ≥Δ 且空闲 ≥T，§8.2）、title_inspector 水位 | 水位推进：重跑不重做 |
| 跨会话（天–周） | 记忆与定义对象 | supersedes/replace、Core Block 更新、verified 题库 | 显式替代：有前后继账 |
| 组织级（季度） | 口径体系与所有权 | 成熟度标尺、owner/steward 分工、审计（详见 §11） | 目录级显式退役（L6 全段） |

表后读法：尺度分层的价值集中在「死亡口径」一列——同一个「让内容退场」的问题，四层各有不同的正确答案；跨层套用（比如拿轮内占位机制充当目录级退役）就是 §9.2 反事实表第六行的坏法。

Claude Code 的五层 Harness 是这套嵌套尺度上现成的可对位结构（[170](../agent-harness/170-claude-code-harness-overview.md)）：执行（主循环与权限闸）落在轮内；规划（待办与子代理）落在会话内的任务跨度；记忆（上下文压缩+持久记忆文件）一套机制横跨会话内与跨会话两个尺度——压缩管当轮窗口，持久记忆文件管跨会话留存；时机（后台任务与 cron）把执行搬到「不等它、到点触发」的时间结构上；协作（多 Agent 平台）到组织级。170 自己的读法——「每一层的存在理由，都写在上一层的失败里」——与 §9.2 的段级反事实是同一种纪律的两个视角。

## 10. 治理≠验证与批判边界

§4–§9 把五轴与生命周期讲完之后，必须回答一个更根本的问题：这套治理设计能证明什么、证明不了什么。本章做三件事——解剖 477 vs 48 的完整因果链（治理≠验证的实证）、把上游 grain 契约立为独立验收位（争议③处置）、给出置信纪律三句与全文材料的批判边界。

### 10.1 477 vs 48 全链路：每一步都对，整体是错

先把这条链完整摆出来（机制载荷详 [011](./011-horizon-context.md) M1/§8；生产实例为 typedef 转述，赛道创业公司、利害已标，虚线——玩具复现 D3 为实心，见第 4 步）：

1. 上游转换层（dbt）把明细数据塌缩成日汇总——grain 决策发生在语义层视野之下，是合法的转换决策；
2. 语义视图里 distinct 用户数的算式完全合法，口径单点也对——M1 两条不变量都成立；
3. 引擎查询期重算忠实执行：distinct 计数按天相加得 477（重复计数），按底层明细重算得 48——**错因不在任何一步的执行，而在上游粒度已经丢了**；
4. 玩具复现（实心，2026-10-09 复跑日志）：D3 拆 `NON ADDITIVE` 后月值 [11,6,7]（对照 [5,6,7]）、全期口径：按月求和得 24（重复计数）、NON ADDITIVE 取末快照得 7（正确——477 vs 48 的同机制）；011 §5 的最小版本为「每日 2+2 相加得 4 vs 去重 3」。

链上每一环各自「没错」，整体却是错的——grain 塌缩不可逆：粒度一旦在上游丢失，下游任何合法算式都无法恢复它。三个「治理管不到」的位置随之显形：`NON ADDITIVE BY` 是人填声明、非系统推导（声明半边依赖人知道「这个指标跨时间不可加」）；lineage 是「谁喂谁」的观察记录、不校验「这么算是否合法」；M4 的 Verified Query Repository 只补了验证缺口的锚定一角——命中题库走背书路径，题库外的长尾与一般性计算正确性仍是开放面（评测闭环 Cortex Agent Evaluations 是与 Autopilot 并列的独立发布环节，不属 Horizon Context，011 §8）。

> [!WARNING] **「有治理 + 有题库」不等于可信**。最常见也最危险的读法是把 M4 的存在当成验证半边已交付——477 vs 48 恰好发生在治理、血缘、题库三者都在场而上游 grain 已塌的位置。VQR 锚定的是「有人签字的题答对了」，不是「一般性计算是对的」；两者混读会把治理绿灯误当数字正确。

### 10.2 上游 grain 契约的独立验收位（争议③处置）

验证缺口归属承接 011 §7.2 争议 3（两派原文：Snowflake FAQ 互补定调——dbt 管转换、语义视图管解释；typedef 指责责任真空——grain 决策在转换层、正确性承诺在语义层）。本文把该争议引申到验证维度：VQR 只补「锚定」一角（011 §8 第 4 条同判），一般性验证仍需独立验收位与上游 grain 契约。处置：grain 契约接口立为独立验收位——grain 决策权留在转换层（dbt 地盘、Out-of-Scope），但 grain 契约接口在研究范围内。三条验收判据（设计要求，非已实现）：

1. 注册期可校验的 grain 声明：每个聚合类资产声明最小粒度；上游供给粒度粗于声明粒度时注册期拒绝（与 422 门同构）——把「跨时间可不可加」从人填声明变成可对账字段；
2. 装配期塌缩警示：语义资产引用的上游列若来自预聚合表，装配期必须携带 grain 警示（对齐 M4 的 `no_governed_coverage` 显式告警形态——三条出路无静默瞎猜）；
3. verified Q&A 作出口对账资产：验证答案与引擎重算不一致即告警（原型 A1/A1b 已演示题库路径与现算路径对账一致的同构闭环，011 §6）。

如实承认边界：编译期推导计算合法性尚无成熟方案，以 eval 环兜底，不假装解决（对策概括命名：compiler in the loop）。

### 10.3 置信纪律三句（Jev 口径同构，[200/201](../agent-infra/200-jev-system-one-model.md) 承载）

1. 量纲分组：供给面每个置信字段须声明来源量纲——LLM 口头、正则常数、启发式常数不可比，聚合前必须分组；
2. 缺省向低置信：字段缺失不得自动高置信。本仓实测反例：KG 抽取 confidence 缺省 1.0 叠加 0.5 阈值，等于字段缺失自动满置信通过——**方向反了**（实心，本仓核验）；
3. 阈值绑分布锚点：0.9 这类阈值须绑定校准分布——两组第三方实测（ECE＝Expected Calibration Error，置信度校准误差的常用度量，越小越准）：分布内 ECE 0.031（Hume 黑盒探测·MMLU）、密封集 ECE 0.220 且 conf≥0.9 只对 42%（JevBench）（实线）。

## 11. 业界格局、范本与组织面

设计判定的正当性要放回业界坐标系检验。本章回答四件事：治理落位的路线谱系（描述还是执行，争议①）、分析师与厂商的两场论断怎么读、语义层增益窗口用什么指标判读、组织面卡在哪；四范本矩阵经两处重锚后收尾。

### 11.1 描述还是执行：治理落位的路线谱系（争议①）

（编号说明：圈号①②③为本文骨架自编的争议序号，与 011 §7.2 的「争议 1/2/3」不一一对应——011 争议 1 是「不可绕过」边界、争议 3 是语义层与转换层职责边界；本文 ①③ 各有自己的落位，引用 011 处随文注明。）

先立判据（执行点律，011 规律 2）：看一个治理宣称，先问治理求值发生在哪一层——答不出求值点的，是描述而非执行。按此判据，业界四条路线排成一条谱系（厂商清单为 2026-09 公开口径综述承袭，个别条目未逐一独立核验）：

| 路线 | 治理发生处 | 代表 |
| :-- | :-- | :-- |
| 平台内嵌 | 引擎内 | Databricks UC+Genie；Fabric IQ；Looker；AWS Context+开源 Accelerator |
| 定义即代码 | 转换层 | dbt MetricFlow（YAML 版本化、PR 评审；已并入 Fivetran） |
| 独立可执行层 | SQL 生成前 | Cube（主张治理须在 SQL 产生之前——事后扫描可被子查询/CTE 绕过；口径承袭社区共识转述、非逐字引文）；AtScale |
| 跨系统元数据平面 | 元数据平面（描述不执行） | Atlan（Enterprise Data Graph / Context Lakehouse）；Alation；DataHub |

读法：四条路线的功能清单越来越像，分野只在治理这道工序发生在哪一层——装错层的路线各自预置了失败模式（内嵌绑死引擎；定义即代码不在执行路径、价值后置；元数据平面只描述不执行；独立层要自己挣采用）。异类 Palantir Ontology：semantic（描述世界）+ kinetic（做动作）双层、decision lineage 贯穿。四条路线在同一处收敛：把治理往 SQL 生成之前挪。

争议①的 2026 增量把谱系两端拉得更开（截至 2026-10-09，一手探针）：描述端——Forrester 给出 context layer 提案定义（semantic layer 与知识图的下一代演进，兼具前者的业务语义与治理、后者的本体建模；原文自标 proposed definition、非定稿），Atlan 的目录/图谱路线以表示建模为中心；执行端——Cube 的「SQL 产生之前」立场，加 Colrows 的 compile-time 极端形态（治理在编译期铸死，谱系最右端；执法点谱系四层详见 §5）。

本蓝图自身落位在谱系第三条（独立可执行层），理由两句：其一，不绑引擎才服务任意平台（平台内嵌路线把治理与单一引擎锁死，本仓与混合栈用户承担不起）；其二，治理在 SQL 生成之前才防得住绕行（事后扫描可被子查询与 CTE 绕过——Cube 立场，011 §2 同判）。同时吸收各家长处：版本化纪律（定义即代码路线的 PR 评审）、四层信号（Horizon，§12.2 承接）、出口治理与动作思想（Palantir 双层——非四范本席位，其「语义+动作双层」思想由 §11.1 谱系判据与 §5 执法点谱系承接）。

- 传输之战 vs 含义之战（Colrows 判词，销售 governed semantic layer 的厂商、利害已标）：MCP 赢下的是传输之战而非语义之战——它给了 Agent 触达数据的标准通道，但生产环境 Agent 真正失败在含义这一层。Colrows 引 dbt Labs 2026 基准作其最硬单件证据：Claude Sonnet 4.6 裸写 90.0%→语义层编译 98.2%、GPT-5.3-Codex 84.1%→100.0%（受覆盖题口径，虚线，品类卖方基准）。

> [!WARNING] **Gartner 60% 与 Redis 97/4 是最常被转述、也最容易读错的两个数字**。前者是 projection（预测口径、二手转引、付费墙），后者 n=1000 在落地页零披露（方法论不可核，§11.5）。引用时不随行全限定，传递的就是「分析师已判定 / 业界已证实」的错误确定性。

### 11.3 增益窗口双指标判读（不立争议条目）

模型代际跃迁下语义层边际价值是否收窄，骨架裁定不立争议条目、改用双指标判读（数字详 011 §7.2 争议 2）：

- 准确率指标：受覆盖题上语义层逼近满分且确定性生成（98.2%/100% vs 裸 text-to-SQL 90.0%/84.1%，dbt 基准、虚线）；全题集差距收窄到 8 个点（72.7% vs 64.5%），且裸模型三年间从 32.7% 涨到 64.5%、可答题集达 84–90%（虚线，品类卖方基准）。
- 失败形态指标：语义层 27.3% 未得分为显式拒答，裸 text-to-SQL 35.5% 未得分为自信错数——**错法从自信错数变成显式拒答**，这一半不随准确率收敛而收敛。

读法：窗口是否收窄取决于考卷更接近受控集还是企业工作流端；两个指标必须分开读——准确率收敛不等于失败形态收敛，报错优于错数（KPI 唯一）正是在失败形态这一半上立得住。

### 11.5 组织运营面

技术路线之外，落地断层是组织问题（框架可引、数字不入承重）。所有权真空的判词：上下文工程横跨 data/platform/AI/product 四类团队而无单一 owner——「问五个人谁拥有 Agent 运行所依赖的上下文，会得到五个不同的答案，很少有『是我』」（Redis who-owns 博文开篇句，2026-09-01；直链 2026-10-09 复测仍 404、经搜索索引二手重建，虚线）。

治理的组织形态（承袭，Atlan/Redis 框架）：metric owner=Accountable、steward=Responsible，Propose→Certify 全程留审计；反模式是 glossary theatre、影子查询、无主 metric；采用处方 5–10 指标起步、业务方 day one 参与、按基础设施运营。语义层失败史三死因：BI 厂商激励相悖、迁移数学不成立、不在执行路径上（最结构性的一条与执行点律互证）。解法方向 shared ownership——本蓝图的职责面（供给/治理/装配/验证，对应五轴与时间面）本身就是分工面；本仓落位即 §12.3 的子系统契约表。

### 14.1 修复序（伤害降序）

修复不是按价值排序，是按「不修时持续产生的信任伤害」降序——三类失败形态各对应一步：

1. 断边先接（ISSUE-195）：给 consolidation_jobs 接消费者、补 threads.metadata 水位列（trigger/consumer/watermark 三件套＋015-D3 修复，独立 PR 先行，且写入端防注入扫描先于其上线——时序约束，§5.5/§14.3 WARNING；设计承载 §8）。伤害最大的是这种形态——回路不存在而系统表象正常，记忆供给停滞且不可观测（复利三在线律三件缺二）；每一段没有沉淀的会话都是静默丢失的供给。
2. 执法点统一（ISSUE-197）：把审批收进单一 before_tool_callback 拦截位、收窄 HIGH_RISK 清单。装饰闸（存在但不接线）比没有闸更糟——「有审批」的记录制造虚假安全感，事后审计还无法分辨。
3. 死亡段立规（materializer 回收 + ISSUE-194 收回侧）：物化只写不删（`harness_materializer.py:114-134` 全文件无删除路径，091 M13）与挂载的单向承诺同族——永生对象让目录与磁盘慢性漂移，对应 G6（死要有葬礼）。

三步的共同点：都不是新能力，是把已宣告的承诺接完——这也是它们排在一切新能力之前的原因。

### 14.2 轴依赖序

新建能力按轴依赖排序：资产+权威 → 装配 → 检索 → 复利。理由分四句：装配面要装的资产必须先在册（definitions 注册与 422 门，#1/#2）、要过的门必须先在引擎（权威轴执法点）；检索排序依赖装配面给出的候选集与信任归一的信号口径；复利环的产物要过注册门入库、经检索供给才能形成回路——前三轴不立，复利环接上也是空转。此序同时解释 §12.4 16+4 映射表里 ✅ 行的分布：已对齐项集中在资产与权威两轴（#2/#3），另有一处复利同构（#7）。全部改动沿交付安全承诺：**additive + 特性开关 + fail-soft**——每步可回退，热路径先开关渐进再默认开。

### 14.3 前置项排序（Phase 1 概念保留）与交付形态注记

前置项排序（191:82 的「013 前置项排序…二者取先」引用面由此承接）实质是：凡被其他项依赖的项排前（会话巩固独立 PR 先行、目录与归一随后），与修复序×轴依赖序同向。交付形态一句注记：对象层落 PostgreSQL、装配面以单进程 stdio/HTTP MCP server 起步——「可独立部署」的兑现形态保留；施工隐喻不用于路线表述，零依赖种子原型已交付，实验室与日志由 §13 承载。

> [!WARNING] **巩固消费者上线前必须先修写入端防注入**（映射表 #20：写入端零扫描+注入块头无数据声明）。时序约束反了，等于给注入开一条经巩固进入长期记忆的常驻通道；修复序第一项因此是「会话巩固三件套＋015-D3 修复（独立 PR 先行），且写入端防注入扫描先于其上线」整体交付，不是单独把消费者接上。

### 14.5 验收问答（3 道，先答后对）

1. 三面（验收面 × 结构面 × 时间面）为什么必须独立？拆掉独立性会先坏什么？
2. 修复序为什么把 ISSUE-195 排在 ISSUE-197 与 materializer 之前，而不是先做检索或出口守卫？
3. 有人向你宣称「我们有语义层、治理不可绕过」——如何用失效登记簿三步审计这个宣称？

答案要点：①三面回答三个不同问题——验收面给证伪判据（防住什么坏法）、结构面给五轴独立变化（换检索算法不动权限模型）、时间面给段与环的执法位（对象一生走哪段、错答案怎么回到定义层）；独立性可测（换 X 不动 Y），机制跨轴组合（M1=资产×权威×装配）不破坏它——每个轴仍可单独演进，拆掉独立性则机制组合无处登记、验收判据无从挂靠。②伤害降序：断边是回路不存在而表象正常（三在线律三件缺二、静默丢失供给）；装饰闸制造有审批的虚假记录；永生对象是慢性漂移——且轴依赖上巩固产物是检索与装配的未来供给，断边不接、后续轴都在存量上优化；另有时序约束：接消费者前必须先修写入端防注入。③三步：把宣称翻译成失效形态、在登记簿（§1）找同形簇与已登记反例；逐条要「拆掉有什么具体坏法」的可复现证据（反事实存在性律——答不出拆掉会坏的机制不存在）；核接线三态到生产路径（存在/接线/在线：挂载点、调用方计数、消费者与水位），引擎外承诺按周界口径限缩——三步任一不过，登记为新条目并挂徽。
